# Недостающие данные: файл требований и его приём

## Когда читать

- Читать, когда `make check` вернул `BLOCKED` и в папке ИС появился `DATA-REQUIREMENTS.md`.
- Читать, когда неясно, что означает вход, где его взять и у кого спросить.
- Читать, когда `make enrich` отклонил лист и нужно понять причину.
- Читать, когда данных нет совсем и нужно исключить ИС из расчёта.
- Читать, когда нужно понять, откуда брать значение: Confluence, Grafana или экспертное решение.

## Кратко

- `BLOCKED` больше не «сухой» вердикт: гейт сам создаёт `DATA-REQUIREMENTS.md` и `DATA-REQUIREMENTS.yaml` — по одному на ИС.
- `make collect-apply IS=<код>` добавляет `RESEARCH-PLAN.md`: какие страницы Confluence и дашборды Grafana проверить, какие запросы выполнить, кто подтверждает.
- `make services-apply IS=<код>` добавляет `SERVICE-FINDINGS.md`: что говорит документация клонов сервисов (`docs/`, `openspec/`) о назначении, нормативах, потоках и данных.
- `make links-apply IS=<код>` добавляет карту обхода `LINK-MAP.md` + `LINK-MAP.yaml`: все ссылки ИС (SSoT `links.yaml`, `catalog.yaml`, компоненты) с `id`, видом, `expand` и кандидатами на входы; обход по карте делает MCP-агент и пишет `SOURCES-FINDINGS.yaml`, а `make sources-apply IS=<код>` принимает факты в `INFORMATION.yaml` (статус — из `findings[].status`: `confirmed` по умолчанию или `derived` для формулы; `unit` — из `findings[].unit`, если он допустим по критериям; отклонение — код 1). После записи `LINK-MAP.md` перерисовывается из `LINK-MAP.yaml`, поэтому статусы узлов в них всегда совпадают.
- Сценариев расчёта два: простой (4 входа калькулятора) и сложный (те же четыре + `time_to_impact`, `axes_scores`, `cia`); фолбэк со сложного на простой запрещён.
- Источники значений: клоны сервисов (`docs/`, `openspec/`) → Confluence → Grafana; SSoT — для идентификации ИС. `axes_scores` и `cia` из документов не выводятся.
- Сервисы с `lifecycle: closed` не клонируются и не служат основанием для входов.
- `.md` — для человека: что это, зачем, где взять, у кого, как подтвердить, пример.
- `.yaml` — лист для заполнения: `value`, `source`, `status` у каждого недостающего входа.
- Заполняет человек (TL / PdM / SRE / ИБ), принимает `make enrich-apply`: значения переезжают в `INFORMATION.yaml`, лист перегенерируется с остатком.
- `check` безопасен для заполненного листа: значения **открытых** полей сливаются (`value`, `source`, `status`, `bucket`/`unit`/`notes`), вычисляемые поля пересчитываются — порядок «заполнить → `enrich-apply`» не обязателен. `NO_REQUIREMENTS=1` — лист не трогать вообще.
- Лист производен от `INFORMATION.yaml`: вход, уже закрытый (значение + `status: confirmed`/`derived`, а также `legacy`), в лист не попадает. Принятое значение из листа исчезает; ручное, но ещё не принятое — остаётся.
- Значение без `source: {type, ref}` и `status: confirmed` не принимается: ошибка, `INFORMATION.yaml` не меняется.
- Данных нет совсем — ИС исключается из расчёта: `make exclude IS=<код> REASON="<причина>" [EXCLUDE_SCOPE=catalog]` → вердикт `SKIPPED` с источником исключения.

## 1. Зачем файл

Гейт (`make check`) останавливает расчёт, если не хватает blocking-входа. Раньше
в этом случае печатался список `id` — и дальше человек должен был сам догадаться,
что это за поле, где его искать и у кого спрашивать. Теперь гейт **сразу
материализует запрос**: в папке ИС появляются два файла, и оба — про одно и то
же, но для разной аудитории.

| Файл | Кому | Что внутри |
|------|------|------------|
| `DATA-REQUIREMENTS.md` | человек | по каждому недостающему входу: что это, зачем, допустимые значения, где взять, у кого, как подтвердить, пример; в конце — готовый фрагмент `INFORMATION.yaml` |
| `DATA-REQUIREMENTS.yaml` | человек + `enrich` | лист для заполнения: `value: null`, `source: null`, `status: missing` + `#`-комментарии «что/где/у кого» |

Оба файла — **производные**: их генерирует `criticality.py requirements` из
`criteria/criticality-criteria.yaml` и `INFORMATION.yaml`. Руками `.md` не
правят; заполняют только `.yaml`.

## 2. Кто заполняет

| Роль | Что закрывает |
|------|---------------|
| TL | пиковая нагрузка, сбор оценок по осям, техническая часть влияния |
| PdM | тип клиентов, характер влияния при простое, финансовые потери |
| SRE | допустимое время простоя (SLA), время до последствий |
| ИБ | оценки CIA, классификация данных |
| архитектор | спорные архитектурные факты, ADR |
| TL / SRE (Grafana) | пиковая нагрузка: снять пик RPS с панелей трафика папки E001 |

Адресат указан у каждого входа в поле «У кого» — и в `.md`, и в `#`-комментарии
`.yaml`. Общих формулировок «нужно больше данных» быть не должно.

## 3. Справочник по входам

Полный перечень — в
[`criteria/criticality-criteria.yaml`](../criteria/criticality-criteria.yaml)
(`inputs.required`). Ниже — та же информация в человеческом виде.

| id | Что это | Зачем | Где взять | У кого | Как подтвердить |
|----|---------|-------|-----------|--------|-----------------|
| `peak_hour_load` | клиентов/час в пик, целое > 0 (`запросов/час`, если пик снят как RPS шлюза; единица — `findings[].unit`) | blocking экспресс-метода: множитель в `E = коэф. типа × коэф. влияния × клиентов/час`; без него `E = 0` и уровень не считается. Также заполняет `object_workload` | Grafana: папка E001 → подпапка ИС → панели трафика шлюза; вторично — страницы трафика в Confluence. Формула `peak_rps × 3600` | TL + SRE | `source: {type: grafana, ref: 'dashboard uid, panel, expr'}` + `status` |
| `consumers_type` | тип клиентов, дословно из `enum_selection.consumers_type.values` (7 значений) | blocking экспресс-метода: задаёт коэффициент типа клиентов (`express_method.client_coefficients`) — первый множитель `E`. Также заполняет `object_consumers_type` | Confluence: страница ИС, раздел «Пользователи продукта»; вторично — карточка ИС в SSoT (`ssot_get`, секция `base`) | PdM + TL | `source: {type: confluence, ref: '<page_id>, раздел'}` + `status: confirmed` |
| `outage_impact` | характер влияния при недоступности, дословно из `enum_selection.outage_impact.values` (6 значений) | blocking экспресс-метода: задаёт коэффициент влияния (`express_method.impact_coefficients`) — второй множитель `E` | Confluence: DR-страница (`catalog.yaml → dr_page_id`), раздел влияния; затем E2E; решение PdM при отсутствии цитаты | PdM + TL | `source: {type: confluence, ref: '<page_id>, раздел'}` + `status: confirmed` |
| `object_sla` | допустимый простой в минутах, целое `>= 0` (`0` = простой недопустим) | blocking экспресс-метода: прибавляется к каждому `t = порог/E×60 + SLA`, сдвигая все четыре времени последствий | Confluence: Support-страница («SLA решения»), DR-страница (RTO); договор SLA. RTO в часах и `99.x %` ≠ минуты простоя | SRE | `source: {type: confluence, ref: '<page_id>, таблица'}` + `status: confirmed` или `derived` с формулой |
| `axes_scores` | четыре целых 0..4 по осям legal/economic/reputational/client | blocking детального метода: max по осям — строка `impact_matrix` | экспертно: финансовая модель, юридическая оценка, ИБ/PR, клиентские метрики; **из документов не выводится** | TL + ИБ + финансы | `source: {type: manual, ref: '<роль: логин>'}` + `status: confirmed` |
| `time_to_impact` | одна корзина из `time_buckets.order` (`<1h`, `1-12h`, `12-24h`, `>24h`) | blocking детального метода: колонка `impact_matrix` | Confluence: DR-сценарии (кеш, репликация, очередь), разбор инцидентов | SRE + TL | `source: {type: confluence, ref: '<page_id>, сценарий'}` + `status: confirmed` |
| `cia` | три значения `low`/`medium`/`high` для C, I, A | blocking детального метода: `V = 6·(F(C)+F(I)+F(A))` → уровень защищённости → `final_matrix` | ИБ: классификация данных и модель угроз, `facts.data_classification`; **из документов не выводится** | ИБ | `source: {type: manual, ref: 'ИБ: <логин>'}` + `status: confirmed` |

Что означает каждая оценка 0..4 по осям — `axes.items[].scale`; что означает
каждый уровень CIA — `cia.descriptions`. Значения не дублируются в этой
документации намеренно: единственный источник — файл критериев.

### 3.0. Формула экспресс-метода и требование к полноте

```text
E   = коэф. типа клиентов × коэф. характера влияния × клиентов/час
t   = порог / E × 60 + SLA        (порог: 100 / 1 000 / 10 000 / 50 000)
уровень = max(балл по интервалам) → score_to_level → levels.dochub_to_ssot
```

Из формулы следует требование: для экспресс-оценки обязаны быть указаны **все
четыре** поля — `peak_hour_load`, `consumers_type`, `outage_impact`,
`object_sla`. Любое из них отсутствует → `E` или `t` не определены → гейт
возвращает `BLOCKED` и лист требований, а не «примерный» уровень. Коэффициенты,
пороги, интервалы и матрица — в `express_method` файла критериев; исходный
файл-артефакт — [`docs/reference/calculator/`](reference/calculator/) (описание
в [reference/README.md](reference/README.md)).

Как именно собрать значение (какие страницы открыть, какие панели и запросы
выполнить) — `RESEARCH-PLAN.md` в папке ИС и §4–§9 ниже.

### 3.1. Почему в листе бывает больше входов, чем блокирует гейт

Гейт блокирует только входы **выбранного сценария**. Лист требований содержит
только **незакрытые** входы: обязательные входы простого сценария (blocking)
плюс detailed-входы (advisory). Так человек видит полную картину и может закрыть
сложный набор целиком (тогда сценарий сменится на сложный). У `gi.mm` (простой
сценарий, 3 из 4 обязательных заполнены) лист содержит 4 записи: 1 blocking +
3 advisory; `blocking n/m` в таблице гейта при этом показывает только входы
простого сценария (`0/4` … `4/4`).

### 3.2. Два сценария расчёта

Сценарии описаны в `.opencode/skills/criticality-gen/criteria/criticality-criteria.yaml`
→ `scenarios` (`kind: convention`, `status: validated`). Сценарий выбирается по
данным, а не флагом CLI (`scenarios.selection.rule`).

| Сценарий | Метод | Обязательные входы | Правило блокировки |
|----------|-------|--------------------|--------------------|
| простой | `express` (калькулятор критичности) | `peak_hour_load`, `consumers_type`, `outage_impact`, `object_sla` — 4 входа | отсутствие любого из четырёх или `status: missing` → `BLOCKED` |
| сложный | `detailed` (оси × время + CIA) | все семь входов `inputs.required`: четыре входа калькулятора + `axes_scores`, `time_to_impact`, `cia` | отсутствие любого из семи → `BLOCKED`; **фолбэк на простой сценарий запрещён** |

Правило выбора: если хотя бы один вход, относящийся только к сложному набору
(`time_to_impact`, `axes_scores`, `cia`), содержит непустое значение — сценарий
сложный. Иначе — простой. Частично заполненный сложный набор нельзя «закрыть»
простым сценарием: это понизило бы уровень молча.

Заполнение **любого** detailed-входа переключает ИС на сложный сценарий — даже
если это было сделано «для полноты паспорта» по advisory-пункту листа
требований. После переключения обязательными становятся все семь входов,
включая `time_to_impact`; если его нет, гейт даёт `BLOCKED`, а не возвращается
к простому сценарию. Лист требований (`DATA-REQUIREMENTS.md`/`.yaml`)
предупреждает об этом в шапке блока `inputs` и помечает каждый advisory
detailed-вход (`switches_scenario: true`). Обратный переход возможен только
удалением значения из `INFORMATION.yaml` — это осознанное действие, а не
побочный эффект дозаполнения.

## 4. Источники значений

Входы расчёта берутся из разных мест, и это не взаимозаменяемо. Карта
источников — в
[`references/data-sources.md`](../references/data-sources.md);
ниже — сводка.

**Порядок сбора — всегда один и тот же:**

1. **Клоны сервисов ИС** — `apps/<код ИС>/<сервис>/docs/` и `openspec/`
   (основная документация: назначение, потребители, заявленные нормативы,
   потоки данных). Появляются после `make prepare-apply` / `make services-apply`;
   разбор — `is/<код ИС>/SERVICE-FINDINGS.md`.
2. **Confluence** — дерево страниц ИС: «Пользователи продукта», DR-страница,
   Support/SLA, страницы трафика.
3. **Grafana** — измеренная нагрузка: папка продукта E001 → подпапка ИС →
   панели трафика шлюза.
4. **SSoT** — только идентификация ИС: название, продукт, команда,
   критичность, список компонентов и их репозиториев. Карточка читается
   `ssot_get` (доступ — `ssot_status: authorized`); значений входов там нет.

Цитата из клона — это **основание**, а не значение: `source.type` принятого
значения остаётся `confluence`, `grafana` или `manual`, а значение подтверждает
человек.

| Поле | Где искать в первую очередь | Затем | Формула / правило | Кто подтверждает |
|------|-----------------------------|-------|-------------------|------------------|
| `peak_hour_load` | клоны: `docs/`, `openspec/` (заявленный трафик, назначение); измерение — Grafana: папка E001 → подпапка ИС → панели трафика шлюза | Confluence: страницы трафика/RPS | `peak_hour_load = peak_rps × 3600` | TL (+ SRE) |
| `consumers_type` | клоны: `docs/`, `openspec/` (кто потребитель); затем Confluence: страница ИС, «Пользователи продукта» | SSoT (`ssot_get`, секция `base`: title, description) | дословно из enum (7 значений) | PdM |
| `outage_impact` | клоны: `docs/`, `openspec/` (что ломается); затем Confluence: DR-страница, раздел влияния | решение PdM | дословно из enum (6 значений) | PdM |
| `object_sla` | клоны: нормативы в `docs/`, SLO-конфиг (`slo-kit.yaml`, `slo.yaml`, `alerts.yaml`, `sloth.yaml`); затем Confluence: Support/DR — SLA решения, допустимый простой | договор SLA | минуты, целое `>= 0` (`0` = простой недопустим) | SRE |
| `time_to_impact` | клоны: сценарии отказа, кеш, репликация, очередь в `docs/`; затем Confluence: DR-сценарии | разбор инцидентов | одна корзина `time_buckets.order` | SRE |
| `axes_scores` | экспертно: финансовая модель, юридическая оценка, ИБ/PR, клиентские метрики | — | **не выводится из документов** | TL + ИБ + финансы |
| `cia` | ИБ: классификация данных, модель угроз, `facts.data_classification` | — | **не выводится из документов** | ИБ |

`ssot` даёт атрибуты ИС (название, команда, критичность, компоненты), но не
нагрузку, не SLA и не характер влияния: этих полей в карточке ИС нет.

### 4.1. Пропуск закрытых сервисов

Правило — `criteria.service_lifecycle` (`kind: convention`,
`status: validated`): сервис с `lifecycle: closed` выведен из эксплуатации и не
участвует в функционировании ИС.

| Что | Как |
|-----|-----|
| Что считается закрытым | компонент, у которого `components[].lifecycle` (в `INFORMATION.yaml` — поле `status`, значение то же) входит в `service_lifecycle.skip` — сейчас это `closed` |
| Что делает скилл | не клонирует (`git clone`/`pull` не выполняется), не читает файлы, не строит находки и основания |
| Почему нельзя использовать как основание | `docs/`, нормативы и код закрытого сервиса описывают прошлое состояние, а не текущее (`service_lifecycle.evidence_rule`) |
| Где видно | `SERVICE-FINDINGS.md` §2 «Пропущенные сервисы (lifecycle)»: таблица `сервис / репозиторий / lifecycle / причина`; в сводке — `пропущено (lifecycle): N`; в frontmatter — `services_skipped: N` |
| Компонент без `lifecycle` | анализируется как активный, в отчёте помечается `lifecycle не указан` |

### 4.2. Запрет сборки и запуска клонов

`apps/` — чужой код в неизвестном состоянии. Внутри разрешены **только** `git`
(`clone`, `checkout`, `pull`, `rev-parse`) и чтение файлов:

| Разрешено | Запрещено |
|-----------|-----------|
| `git clone` / `git pull --ff-only` / `git checkout` / `git rev-parse` | `install` / `build` / `test` / `docker` / `make` из клона |
| чтение `docs/`, `openspec/`, конфигов SLO, манифестов | запуск скриптов и сервисов клона, установка зависимостей |
| цитирование строки как **основания** для входа | выдача найденного в коде за подтверждённое значение (R12, R14) |

Движок форсит это в коде (`_git_only`), а `SERVICE-FINDINGS.md` §8 повторяет
ограничение в отчёте. Причина — не только безопасность: прогон сборки менял бы
окружение и делал результат невоспроизводимым.

### 4.3. Известные ловушки источников

Сводка из
[`references/data-sources.md`](../references/data-sources.md)
(полные таблицы — там):

| Ловушка | Симптом | Что делать |
|---------|---------|------------|
| Метрика событий Kafka | одно событие кажется «клиентом»; offset/счётчик дублируется по брокерам | событие ≠ клиент, а сумма по брокерам ≠ число событий: брать уникальные ключи или не использовать как нагрузку |
| Datasource в панели не существует | панель ссылается на удалённый datasource (404) | брать datasource из ответа панели; при 404 — другая панель/дашборд, а не «примерное» значение |
| SLO только на feature-ветке | в `master`/`main` SLO-конфига нет, а в клоне он «найден» | ветка клона фиксируется в `SERVICE-FINDINGS.md` §1; норматив с непромерженной ветки требует подтверждения SRE |
| `99.8%` ≠ минуты | процент доступности выглядит как SLA | в `object_sla` идут только минуты простоя; процент пересчитывает SRE, а не скилл |
| `alerts.enabled: false` | в конфиге есть блок алертов, но он выключен | это каркас, а не действующий норматив: основанием для `object_sla` не служит |
| PDB / `maxUnavailable` | выглядит как гарантия доступности | это механизм rollout, а не SLA: в `object_sla` не идёт |
| Страницы нового редактора (ADF) | `confluence_get_page` вернул пустой `content.value` | `confluence_get_page_history(page_id, version)` — история отдаёт полный текст версии |
| Лимит Confluence | `Rate limit exceeded … Remaining: 0` | батчи не больше 10 страниц с паузами; лимит общий на ключ |
| Тяжёлый запрос Grafana | `Request timed out` на `max_over_time(...[30d:5m])` | уменьшить разрешение (`[30d:15m]`) или сузить окно |
| Фильтр папки Grafana игнорируется | `folderUids` вернул все папки org | фильтровать результат на клиенте по uid папки |
| Аббревиатура внутри слова | `translator` даёт «SLA», `slow` — «SLO» | искать по границам слова; ложные находки в отчёт не попадают |

## 5. Процедура Confluence

1. **Стартовые страницы.** `links.yaml` карточки ИС (`title: page`) и
   `catalog.yaml` → `confluence_page_id`, `criticality_source_page_id`,
   `dr_page_id`, `decision_log_page_id`.
2. **Обход.** `confluence_get_page(page_id, convert_to_markdown=True)` + дети
   через `confluence_get_page_children`; BFS до глубины 2, не больше 40 страниц
   на ИС.
3. **Приоритет страниц:** DR → Support → SLA → трафик → архитектура → E2E →
   ИБ → Decision Log.
4. **Ключевые слова:** `SLA, RTO, RPO, доступность, 99., простой, нагрузка,
   RPS, QPS, клиент, влияние, критичн, E2E, зависим, ПДн, конфиденциальн,
   целостн`.
5. **Фиксация:** `page_id`, заголовок, название раздела, дословная цитата, URL.

Ловушки:

- **Страницы нового редактора (ADF)** отдают пустой `content.value` — читать
  `confluence_get_page_history(page_id, version)`: история возвращает полный
  текст версии.
- **Лимит 30 запросов** на общий ключ: батчи не больше 10 страниц с паузами,
  на `Rate limit exceeded` — пауза и повтор.
- Пересказ не является значением: нужна дословная формулировка раздела.

## 6. Процедура Grafana

1. **Папка продукта:** uid `feuw533xc1hq8c` (E001), внутри — подпапки по ИС.
2. **Поиск:** `grafana_search_dashboards` по коду ИС и именам
   компонентов-шлюзов (`*-gateway`, `krakend`, `nginx`, `vts`). Фильтр
   `folderUids`/`folderUIDs` игнорируется — фильтровать результат на клиенте.
3. **Панели:** `grafana_get_dashboard(uid)` → искать `rate(`, `requests`, `rps`,
   `http_requests_total`, `nginx`, `vts`.
4. **Выполнение:** `grafana_query_from_dashboard_panel` или
   `grafana_query_prometheus` (параметр называется `expr`, не `query`), окна
   7d и 30d, брать пик.
5. **Фиксация:** `uid` дашборда, панель, точный PromQL, datasource, окно,
   результат.

Тяжёлые `max_over_time` на 30d могут отваливаться по таймауту — уменьшать
разрешение подзапроса (`[30d:15m]`) или сузить окно.

## 7. Формулы и статусы

| Что | Правило |
|-----|---------|
| Нагрузка | `peak_hour_load = peak_rps × 3600`; пик — `max_over_time(<expr>[7d:5m])`, сверяется с окном 30d |
| Контроль объёма | `max_over_time(sum(increase(<counter>[1h]))[7d:10m])` — запросов за самый нагруженный час |
| SLA | минуты; RTO в часах и `99.x %` доступности не равны простою в минутах |
| `confirmed` | значение дословно в источнике и подтверждено владельцем роли |
| `derived` | вычислено по формуле (формула обязательна) или выведено из enum-правила |
| `missing` | данных нет или значение не подтверждено — blocking-вход блокирует расчёт |

## 8. Запреты

- RTO «часы» нельзя подставлять в `object_sla` (минуты) без подтверждения SRE.
- Норматив доступности другой ИС/уровня критичности переносить нельзя.
- Метрика событий Kafka — не число клиентов.
- `axes_scores` и `cia` из документов не выводятся: это экспертное решение.
- Значение «по аналогии с другой ИС» запрещено: провенанс указывает на чужой
  источник.
- Latency, errors, `up`/probe-метрики и число соединений — не нагрузка.

## 9. План сбора (`collect`)

`make collect IS=<код>` (план) / `make collect-apply IS=<код>` (запись) считает
гейт и рендерит `is/<код ИС>/RESEARCH-PLAN.md`:

| Раздел плана | Что внутри |
|--------------|------------|
| «Открытые поля» | таблица: поле, роль, допустимые значения, где искать, кто подтверждает; ниже — закрытые входы одной строкой и «маршрут исчерпан» |
| «Confluence» | `page_id`, что это за страница, что на ней искать; ключевые слова и ловушки |
| «Grafana» | папка E001, дашборды из карточки ИС, поиски по компонентам-шлюзам, готовые PromQL и окна — только если вход, измеряемый в Grafana, ещё не закрыт |
| «Что считается ответом» | формат `value` / `source` / `status`, требование формулы и цитаты |
| «Куда записать» | путь к `DATA-REQUIREMENTS.yaml`, команды `enrich` и `check` |

Свойства: идемпотентен (дата — `--date` → `catalog.review_date`, не `now()`),
исключённые ИС пропускаются (`SKIPPED`), при отсутствии незакрытых входов файл
удаляется. Закрытый вход (значение заполнено и `status: confirmed|derived`)
не даёт инструкций: в плане остаётся одна строка «`<вход>` уже подтверждён:
<значение> (<source.type>)». План ничего не собирает сам: значения вписываются в лист и
принимаются `enrich`.

Второй артефакт маршрута — `make links-apply IS=<код>` →
`is/<код ИС>/LINK-MAP.md` + `LINK-MAP.yaml`: какие узлы обходить (страницы
Confluence, дашборды Grafana, репозитории GitLab, Jira, внешние ссылки), что у
них раскрывать и под какие незакрытые входы они могут дать факт. Карту
заполняет не скрипт, а MCP-агент: результат он пишет в
`is/<код ИС>/SOURCES-FINDINGS.yaml`, принимает `make sources-apply IS=<код>`;
он же обновляет статусы узлов в `LINK-MAP.yaml` и перерисовывает `LINK-MAP.md`
из того же состояния.

Третий артефакт — `make services-apply IS=<код>` →
`is/<код ИС>/SERVICE-FINDINGS.md`: какие сервисы есть у ИС, где у них `docs/` и
`openspec/`, какие нормативы и потоки упомянуты, что даёт основание для какого
входа и чего в клонах нет. Основание — совпадение с формулировкой из критериев;
совпадение только по слову вынесено в отдельную секцию «прочие совпадения по
слову» и вход не закрывает. Сервис без клона помечается «не анализировался:
клон отсутствует», а не «в клоне нет строк». Порядок: `collect` → `links` → обход по карте через
MCP → `sources` → `services` → `check` → `enrich`.

## 10. Как заполнять лист

1. Открыть `is/<код ИС>/RESEARCH-PLAN.md` (маршрут сбора),
   `is/<код ИС>/LINK-MAP.md` (карта обхода: узлы и кандидаты на входы),
   `is/<код ИС>/SOURCES-FINDINGS.yaml` (что нашёл агент) и
   `is/<код ИС>/SERVICE-FINDINGS.md` (что говорит документация клонов), затем
   `is/<код ИС>/DATA-REQUIREMENTS.yaml` (лист для заполнения).
2. У нужного входа заменить `value: null` на значение; `source: null` — на блок:
   ```yaml
   source:
     type: manual
     ref: "TL: Ivanov"
   ```
   `type` — из перечня `ssot | is_yaml_override | catalog | confluence | gitlab | jira | grafana | attachment | ssot_links | manual`.
3. Поставить `status: confirmed`.
4. Запустить `make enrich IS=<код>` — dry-run: покажет, что будет перенесено.
5. Запустить `make enrich-apply IS=<код>` — значения уедут в `INFORMATION.yaml`,
   лист перегенерируется с остатком.

У составных входов (`axes_scores`, `cia`) заполняются все под-оси: частично
заполненный составной вход отклоняется.

### 10.1. Порядок работы с листом

`check` больше **не затирает** заполненный лист: перед записью он читает
существующий `DATA-REQUIREMENTS.yaml` и переносит из него пользовательские
значения (слияние) — но только у полей, которые ещё **не приняты** в
`INFORMATION.yaml`.

ИНВАРИАНТ: лист содержит только открытые входы и производен от
`INFORMATION.yaml` (источник истины), а не накопителен. «Закрыт» = значение
полное и `status` ∈ {`confirmed`, `derived`} (плюс `legacy` — значение по
документированному старому пути в `INFORMATION.yaml`); это тот же критерий,
которым гейт считает `blocking filled`. Закрытое поле из листа исчезает —
после `enrich-apply`, после `sources-apply` (обход закрыл вход), после расчёта
(`derived`) и после ручной правки `INFORMATION.yaml`. Если открытых полей не
осталось, лист (`.md` и `.yaml`) удаляется.

Проверка инварианта — `make validate`: поле, закрытое по `INFORMATION.yaml`, но
оставшееся в листе → ERROR («удалите его: make requirements IS=<код> APPLY=1»);
`blocking_count`/`advisory_count` ≠ числу открытых полей → ERROR.

| Что переносится | Правило |
|-----------------|---------|
| `value` | сохраняется, если непустое (никогда не превращается обратно в `null`), — только у открытого поля |
| `bucket`, `unit`, `notes` | сохраняются, если заданы |
| `source` | сохраняется, если `ref` непустой |
| `status` | сохраняется, если не `missing` (`confirmed`/`derived` остаются) |
| `switches_scenario`, `scenario_note` | **всегда** пересчитываются по критериям — это вычисляемые поля |
| комментарии `#` | не сохраняются: сохраняются значения, а не разметка |
| поле, закрытое в `INFORMATION.yaml` | **не переносится**: лист — производное, а не история |

Отсюда правило: **порядок не важен**. Заполнили лист — можно запускать
`make check` сколько угодно, значения останутся на месте; принимает их
по-прежнему `make enrich-apply`.

Три предохранителя:

1. **Непринятые значения видны.** Если в листе есть `status != missing` и
   значения, которых ещё нет в `INFORMATION.yaml.criteria_inputs`, `check`
   печатает:
   `faq.mm: лист требований содержит заполненные значения, не принятые через
   enrich — выполните make enrich-apply IS=faq.mm`.
   Это предупреждение, а не `ERROR`: вердикт гейта и код возврата не меняются.
2. **Потеря значений — ошибка целостности.** Если рендер даёт меньше
   заполненных значений, чем было в файле (и значения нет в
   `INFORMATION.yaml`), лист **не перезаписывается**: новый вариант пишется в
   `DATA-REQUIREMENTS.yaml.new`, печатается
   `ОШИБКА: рендер листа потерял N заполненных значений (IS=<код>); файл не
   перезаписан`, код возврата — ненулевой. Проверка идёт по факту сравнения
   «до/после», а не по флагу.
3. **Битый YAML не роняет прогон.** Если существующий лист не разбирается,
   печатается `WARN: … существующий DATA-REQUIREMENTS.yaml не разобран,
   значения не перенесены`, исходный файл сохраняется рядом как
   `DATA-REQUIREMENTS.yaml.broken`, а лист пишется заново.

Read-only прогон (лист не пишется, не обновляется и не удаляется):
`make check NO_REQUIREMENTS=1` (`--no-requirements`). Тот же флаг действует у
`start` (`make start … NO_REQUIREMENTS=1`), включая удаление листа при `OK`.
`collect` лист не пишет вообще — он создаёт только `RESEARCH-PLAN.md`.

## 11. Как работает `enrich`

| Шаг | Что делает |
|-----|------------|
| 1 | читает `DATA-REQUIREMENTS.yaml` и `INFORMATION.yaml` |
| 2 | для каждого заполненного входа проверяет: `value` не пусто, `source` = `{type, ref}` с допустимым `type`, `status: confirmed` |
| 3 | проверяет само значение теми же валидаторами, что и гейт (`_value_problems`): enum, диапазон 0..4, целое > 0, корзина времени |
| 4 | ошибки — списком, код возврата 1, `INFORMATION.yaml` **не меняется** |
| 5 | без `--apply` — dry-run: печатает diff секции `criteria_inputs` |
| 6 | с `--apply` — заменяет секцию `criteria_inputs`, остальные секции (`facts`, `conflicts`, `notes`) сохраняются дословно |
| 7 | перегенерирует `DATA-REQUIREMENTS.*`; если входов не осталось — файлы удаляются (заполненные значения при перегенерации сохраняются) |

Формы ошибок, которые точно встретятся:

```text
object_sla: source не заполнен: нужен блок {type, ref} (type: ssot | ... | manual)
object_sla: value заполнено, но status='missing' — требуется status: confirmed
axes_scores: заполнены не все поля значения: не хватает economic
cia: cia.a = 'critical' вне допустимого множества: low, medium, high
```

## 12. Что происходит после

```text
make check            → BLOCKED, создан DATA-REQUIREMENTS.yaml
make collect-apply    → RESEARCH-PLAN.md: страницы Confluence, дашборды и запросы Grafana
make links-apply      → LINK-MAP.md/.yaml: карта обхода ссылок (узлы, expand, кандидаты)
   (обход по карте через MCP Confluence/Grafana → SOURCES-FINDINGS.yaml)
make sources-apply    → INFORMATION.yaml: принятые факты (status: confirmed | derived); LINK-MAP.md перерисован из .yaml; отклонения — код 1
make services-apply   → SERVICE-FINDINGS.md: клоны сервисов, docs/ и openspec/, «вход → основание»
   (человек заполняет лист)
make enrich           → dry-run: что будет принято
make enrich-apply     → INFORMATION.yaml обновлён, лист перегенерирован
make check            → OK (или снова BLOCKED, если остались блокирующие входы)
make start            → артефакты; в §7 появится ссылка на остаток требований, если он есть
make start-apply FORCE=1
make validate         → 0 ERROR
```

Если после `enrich` гейт всё ещё `BLOCKED` — это нормально: лист просто содержит
остаток. Повторяйте, пока входов не останется.

## 13. Если данных нет совсем

Расчёт невозможен, и это не повод заполнять «примерно». Два пути:

| Ситуация | Действие |
|----------|----------|
| Решение общее: ИС не оценивается для всей команды (нет владельца / выведена из периметра) | `make exclude IS=<код> REASON="<причина>" EXCLUDE_SCOPE=catalog` — `excluded: true` + `reason` в `catalog.yaml`, ИС получает `SKIPPED`, `--strict` из-за неё не падает; решение видно всем и живёт в git |
| Решение локальное: проверить/отложить на этой машине | `make exclude IS=<код> REASON="<причина>"` — запись в `is.yaml` (не версионируется) |
| Данные появятся позже | оставить `BLOCKED` и лист требований; вернуться, когда данные будут |

Приоритет: `is.yaml` > `catalog.yaml`. Если в каталоге ИС исключена, а локально
нужно её посчитать — `excluded: false` в записи `is.yaml` включает её обратно.
`validate` требует непустой `reason` при `excluded: true` в каталоге (иначе
`ERROR`): исключение без причины не принимается.

Вернуть ИС в расчёт — `make include IS=<код> EXCLUDE_SCOPE=catalog` (для
каталога) или `make include IS=<код>` (для `is.yaml`).

Если ИС не должна попадать даже в гейт (не только в расчёт), её не добавляют в
список `is:` — тогда `check`/`start` её не видят вовсе. Это отличается от
`excluded: true`: исключённая ИС остаётся в таблице гейта со статусом `SKIPPED`.
