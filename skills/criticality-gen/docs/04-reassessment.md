# Runbook переоценки критичности

## Когда читать

- Читать, когда `make due` показал просроченную или ближайшую переоценку.
- Читать, когда нужно провести переоценку от триггера до подтверждения SRE.
- Читать, когда заполняете паспорт legacy-ИС, у которой нет треда подтверждения.

## Кратко

- Переоценка запускается пятью триггерами; просроченный `due_date` — тоже повод, но не нарушение процесса.
- Порядок: `make due` → `make reassess IS=<код>` (план) → `make reassess-apply IS=<код>` (файл + `review_date`) → пересчёт → правка паспорта → `make validate` → MR → пост → подтверждение SRE → `make index`.
- `assigned_date` при переоценке не меняется; `review_date` и `approve_link` обновляются всегда. Источник истины для `review_date` и `assigned_date` — `catalog.yaml` (в паспорте копия).
- SSoT при переоценке читается `ssot_get` (снимок — `make ssot-import` в `INFORMATION.yaml → ssot_snapshot`), а пишется только через MCP-форму (`severity.type`/`severity.confirmation`): MR создаёт SSoT; клона SSoT, ветки и push у скилла нет. Статусы — `mr_pending` → `mr_created` → `mr_verified`.
- Исход «критичность не изменилась» требует тех же действий: MR, пост и подтверждение обязательны.
- Даты в legacy-ИС не выдумываются: нет источника — `null` и статус `draft`.

Все команды выполняются из корня репозитория.

## Быстрый путь (TL;DR)

```bash
make due                              # 1. что требует внимания
make reassess IS=erm.mm               # 2. план переоценки (dry-run)
make reassess-apply IS=erm.mm         # 3. файл переоценки + review_date в catalog.yaml
# 4. правим criticality-passport.yaml + CRITICALITY.md + reassessment-*.md
make validate                         # 5. проверить
# 6. MR в dochub с меткой criticality
# 6b. SSoT: ssot_get → ssot-plan → MCP-форма severity → ssot-record → ssot-verify
# 7. пост в #Criticality_assessment
# 8. подтверждение SRE → 9. approve_link → 10. make index
```

## 1. Когда запускать

### Триггеры переоценки (5)

| # | Триггер | Кто обычно замечает |
|---|---------|---------------------|
| 1 | Изменение состава клиентов или их количества (рост пиковой нагрузки) | PdM, TL |
| 2 | Изменение SLA / RTO / RPO | SRE |
| 3 | Инцидент с простоем, повлиявший на клиентов | SRE, дежурный |
| 4 | Изменение ландшафта зависимостей: новая критичная upstream/downstream | TL |
| 5 | Плановое напоминание репозитория (`make due`) или запрос SRE/ИБ | SRE |

### Напоминание `make due`

```bash
make due
# или с параметрами:
python3 .opencode/skills/criticality-gen/scripts/criticality.py due --months 12 --today 2026-11-11 --soon-days 30
```

Команда считает `due_date = review_date + период переоценки` (период —
`--months`, иначе `review_period_months` системы, иначе
`review_period_months_default` из `catalog.yaml`, по умолчанию 12) и делит ИС на
три группы: **просроченные** (`due_date < today`), **ближайшие** (`due_date` в
пределах `--soon-days`), **не оценено** (`review_date: null`).

`review_date` — дата **текущей** оценки, а не дата, к которой переоценка должна
быть сделана. Поэтому вчерашняя переоценка не становится просроченной сегодня:
просрочка наступает только когда `due_date` ушла в прошлое. Ровно в день
`due_date` переоценка ещё не просрочена, на следующий день — просрочена. Это же
правило применяет `make validate` (WARN «переоценка просрочена» показывает
`due_date` и `review_date`).

> **Ключевое ограничение.** Календарного срока переоценки процесс D6.1.1
> **не устанавливает**. 12 месяцев — это **конвенция этого репозитория**
> (`review_period_months_default` в `catalog.yaml`), введённая, чтобы
> напоминания вообще существовали. Отдельная ИС может переопределить период
> полем `review_period_months` в своей записи `catalog.yaml`. Просроченный
> `due_date` — повод запустить переоценку, а не формальное нарушение процесса.
> Если бизнес решит, что период должен быть другим (6 или 24 месяца) — меняется
> одно число, и все напоминания пересчитываются.

## 2. Пошаговый runbook

| Шаг | Действие | Команда / место | Результат |
|-----|----------|-----------------|-----------|
| 1 | Понять, что переоцениваем | `make due` | Список ИС и причин |
| 2 | План переоценки (dry-run) | `make reassess IS=<код>` | Старый/новый `review_date`, следующий срок |
| 3 | Создать файл переоценки и обновить `review_date` | `make reassess-apply IS=<код>` | `reassessment-<дата>.md` + `catalog.yaml → review_date` |
| 4 | Собрать данные и пересчитать | `CRITICALITY.md`, раздел 7 | Черновик новой оценки |
| 5 | Обновить паспорт | `criticality-passport.yaml` | 9 полей актуальны |
| 6 | Проверить | `make validate` | 0 ERROR |
| 7 | Создать MR в dochub | `architecture/app/.../criticality-passport.yaml` | MR с меткой `criticality` |
| 8 | Опубликовать в канале | `#Criticality_assessment` по [`templates/publication.md`](../templates/publication.md) | Пост с ссылкой на MR |
| 9 | Дождаться подтверждения SRE | тред в канале | Подтверждение |
| 10 | Зафиксировать подтверждение | `approve_link`, `status` | `status: confirmed` |
| 11 | Обновить индекс и SSoT | `make index` + MCP-форма SSoT (`severity.*`) | INDEX.md обновлён, `ssot_status: mr_created` |

Порядок этапов инструмента — `publish` (MR в dochub) → `ssot` (правка
`severity.type`/`severity.confirmation` через MCP-форму, MR создаёт SSoT) →
`handoff` (тред в `#Criticality_assessment` со ссылками на оба MR): канон —
[`references/workflow.md`](../references/workflow.md). Таблица выше — ручные шаги
процесса, она не заменяет канон.

### Шаг 1. `make due`

Смотрим, что попало в «просроченные» и «ближайшие». Для каждой ИС проверяем,
есть ли один из пяти триггеров. Если триггера нет, а «просрочено» — всё равно
делаем переоценку: напоминание существует именно для этого.

### Шаг 2. `make reassess IS=<код>` — план

```bash
make reassess IS=erm.mm
# или:
python3 .opencode/skills/criticality-gen/scripts/criticality.py reassess --is erm.mm --date 2026-11-11
```

Dry-run: печатает старую критичность, текущий `review_date`, новый
`review_date` (= дата переоценки) и следующий срок (`дата +
criteria.staleness.review_period_months`). Ничего не пишет. Это проверка «когда
следующий раз», а не сама переоценка.

### Шаг 3. `make reassess-apply IS=<код>` — файл и `review_date`

```bash
make reassess-apply IS=erm.mm
# или:
python3 .opencode/skills/criticality-gen/scripts/criticality.py reassess --is erm.mm --date 2026-11-11 --apply
```

Создаётся `is/erm.mm/reassessment-2026-11-11.md` и **атомарно обновляется
`catalog.yaml → review_date`** датой переоценки. Без этого шага `make validate` и
`make due` продолжали бы показывать просрочку, а подсказка `next_step` — снова
советовать `reassess` (дефект C2). Скрипт **не перезаписывает** существующий
файл: каждая переоценка — отдельный документ, история сохраняется; повторный
`--apply` печатает WARN и приводит `review_date` к той же дате (идемпотентно).
В файле уже есть:

- исходное состояние (старая критичность и все поля паспорта);
- чеклист 5 шагов D6.1.1;
- заготовка публикации в `#Criticality_assessment`;
- таблицы для новой оценки и итога.

> `review_date` в паспорте — копия. Источник истины — `catalog.yaml`; при
> расхождении `validate`, `index` и `due` читают реестр, поэтому просрочка не
> маскируется датой генерации паспорта (дефект C1). Расхождение копии с реестром
> `validate` не скрывает: печатает `WARN: review_date в паспорте (<A>) не
> совпадает с реестром (<B>) — перегенерируйте make start-apply IS=<код>`.

### Шаг 4. Собрать данные и пересчитать

Заполняем раздел 3 файла переоценки: оси 0–4, время до неприемлемого ущерба,
CIA. Методика — [02-methodology.md](02-methodology.md). Если сомневаетесь между
двумя уровнями — переходите в детальный режим и опишите второй сценарий.

### Шаг 5. Обновить паспорт

Правим `is/<код ИС>/criticality-passport.yaml`:

- `object_workload`, `object_sla`, `object_consumers_type`,
  `object_outage_impact` — если изменились;
- `object_criticality_estimation` — новая критичность;
- `review_date` — **дата переоценки** (её уже записал `make reassess-apply`; правьте только если ставите другую дату — тогда синхронизируйте с `catalog.yaml`);
- `assigned_date` — **не трогаем**;
- `approve_link` — пока оставляем старым или `null`, заполним после подтверждения.

И `CRITICALITY.md`: раздел 1 (сводка), раздел 7 (обоснование), раздел 9
(история оценок — добавляем строку).

### Шаг 6. `make validate`

```bash
make validate
```

Ожидаем `Результат: OK` и 0 ERROR. WARN про незаполненные поля допустимы,
но перед MR их стоит закрыть: подтверждение SRE всё равно потребует ответов.

### Шаг 7. MR в dochub

Файл копируется в `architecture/app/<актив>/<код ИС>/criticality-passport.yaml`.
Обязательно:

- ссылка на файл добавлена в `_root.yaml` в секцию `imports`;
- в заголовке MR — код ИС;
- метка MR — `criticality`.

### Шаг 8. Публикация в `#Criticality_assessment`

Текст — строго по [`templates/publication.md`](../templates/publication.md).
Для переоценки в поле «Старая критичность» указываем прежний уровень и, если он
`Business critical`, доп. критерий (`PERIOD` / `CONTACT` / `INCIDENT`).

### Шаг 9. Подтверждение SRE

SRE читает MR и пост, сверяет расчёт и подтверждает в треде. Если не
согласен — возвращает на шаг 4 с конкретными замечаниями. Оценка считается
действующей только после подтверждения.

### Шаг 10. Зафиксировать подтверждение

```yaml
approve_link: https://rocketchat.samokat.ru/channel/Criticality_assessment?msg=...
```

`review_date` уже обновлён на шаге 3 (`reassess-apply`). Если переоценка
затянулась и подтверждение пришло позже, дату не сдвигаем: `review_date` — дата
переоценки, а не подтверждения.
В `CRITICALITY.md`: `status: confirmed`, строка в истории оценок.
В `catalog.yaml`: `review_date`, `criticality`, `criticality_ssot`, `status`.

### Шаг 11. `make index` и SSoT

```bash
make index
```

Затем критичность переносится в карточку ИС SSoT по маппингу из
[05-mapping.md](05-mapping.md). Карточка читается ответом MCP `ssot_get`
(снимок — `make ssot-import IS=<код> ENTITY_JSON=-` в `INFORMATION.yaml →
ssot_snapshot`), цель и шаги формы считает `make ssot-plan IS=<код>`, а меняются
только `severity.type` и `severity.confirmation` формы base через MCP
(`ssot_entity_open` → `ssot_form_fields` → `ssot_ui_select`/`ssot_ui_fill` →
`ssot_form_save`). MR создаёт SSoT; `mrUrl` и `version` фиксирует
`make ssot-record IS=<код> MR_URL=<mrUrl>`, независимую проверку выполняет
`ssot_verify_change` → `make ssot-verify IS=<код> VERIFY_JSON=-`. Клона SSoT,
ветки и push у скилла нет. Пока перенос не сделан, SSoT и dochub расходятся — а
дежурные и мониторинг читают именно SSoT; `catalog.yaml → ssot_status`
показывает состояние (`mr_pending` → `mr_created` → `mr_verified`).

## 3. Что меняется при переоценке

| Поле | Меняется? | Комментарий |
|------|-----------|-------------|
| `assigned_date` | **Нет** | Дата первой оценки — исторический факт |
| `review_date` | **Всегда** | Дата текущей оценки, даже если уровень не изменился. Источник истины — `catalog.yaml` (обновляет `make reassess-apply`), в паспорте копия |
| `generated_at` | При перегенерации | Дата генерации паспорта (`make start-apply`); на просрочку не влияет |
| `approve_link` | **Всегда** | Подтверждение нужно при любой переоценке, а не только при изменении уровня |
| `object_criticality_estimation` | Если изменилась | Должно совпадать с `catalog.yaml` |
| `criticality_ssot` | Если изменилась | По маппингу, см. 05 |
| `status` | `draft` → `confirmed` | После подтверждения SRE |
| `object_workload`, `object_sla` | Если уточнились | Даже при том же уровне |
| `extra_criteria` | Если изменились | `CONTACT`/`PERIOD`/`INCIDENT` для Business critical |

## 4. Чеклист: критичность не изменилась

Это самый частый исход. Он всё равно требует действий.

- [ ] `review_date` обновлён на дату переоценки.
- [ ] `approve_link` обновлён на новый тред подтверждения.
- [ ] `status` переведён в `confirmed`.
- [ ] В `CRITICALITY.md` добавлена строка в раздел 9 «История оценок».
- [ ] Создан `reassessment-<дата>.md` с обоснованием, почему уровень прежний.
- [ ] MR в dochub создан и помечен `criticality` (пусть без изменений уровня —
      фиксируется сам факт переоценки).
- [ ] Пост в `#Criticality_assessment` опубликован: «критичность не изменилась».
- [ ] `make index` выполнен.
- [ ] В SSoT через MCP-форму записаны `severity.type`/`severity.confirmation`
      (или зафиксировано `ssot_status: no_change`), `ssot-verify` подтвердил значение.

## 5. Чеклист: критичность выросла

Дополнительно к предыдущему чеклисту — проверить, что ИС соответствует новому
уровню. Требования берутся из
[3823234487](https://space.samokat.ru/pages/viewpage.action?pageId=3823234487);
ниже — рабочий минимум.

**Если Business operational → Business critical:**

- [ ] Нагрузочное тестирование подтверждает пиковую нагрузку из паспорта.
- [ ] Мониторинг покрывает ключевые пользовательские сценарии (не только хост).
- [ ] Определены RTO/RPO и они согласованы с SRE.
- [ ] Есть дежурство, покрывающее часы работы клиентов.
- [ ] Отработан план коммуникации при инциденте (кто пишет клиентам).

**Если Business critical → Mission critical:**

- [ ] Всё из предыдущего блока.
- [ ] Поддержка L3/L4: известно, кто и как эскалирует, есть контакты 24/7.
- [ ] Круглосуточное дежурство (24/7), а не только рабочие часы.
- [ ] Проведены учения по восстановлению (DR), результат зафиксирован.
- [ ] Есть резервирование на уровне инфраструктуры, проверенное на практике.
- [ ] SLA/RTO/RPO закреплены формально, а не «на словах».

**Если Mission critical → Mission critical+:**

- [ ] Всё из предыдущего блока.
- [ ] Изоляция отказов: отказ ИС не тянет за собой соседние системы.
- [ ] Регулярные (не реже раза в квартал) учения с разбором.
- [ ] Ручное подтверждение рискованных изменений (change management).
- [ ] Согласование с ИБ и системным архитектором продукта.

Отдельно: рост критичности почти всегда означает рост требований к обработке
ПДн/КТ/КИ. Проверьте раздел 5 паспорта и матрицы в
[02-methodology.md](02-methodology.md), раздел 9.

## 6. Первичная оценка vs переоценка

| Признак | Первичная оценка | Переоценка |
|---------|------------------|------------|
| Триггеры | 3 (новая ИС, изменение архитектуры, передача команде) | 5 (клиенты, SLA, инцидент, зависимости, напоминание) |
| Jira-метка | `Mission_Assesment` | `Reassessment` |
| Метка MR | `criticality` | `criticality` |
| Файл | `criticality-passport.yaml` создаётся | `reassessment-<дата>.md` + правка паспорта |
| `assigned_date` | Заполняется | Не меняется |
| `review_date` | Заполняется | Всегда обновляется |
| Старая критичность в посте | «при наличии» | Обязательна |
| Метрика | Покрытие паспортами | Доля своевременных переоценок, время до подтверждения |

## 7. Первичное заполнение legacy-ИС

Legacy-ИС — система, которая уже в эксплуатации и у которой критичность когда-то
была зафиксирована (на странице критичности, в треде подтверждения, в SSoT или в
старом реестре), но треда подтверждения в `#Criticality_assessment` нет. Для
продукта E001 это все шесть ИС на момент первичного заполнения репозитория.

Правило простое: **даты не выдумываются**. Если источника даты нет — поле
остаётся `null`, а ИС — `draft`.

| Поле | Что ставим | Когда |
|------|------------|-------|
| `object_criticality_estimation` | значение со страницы критичности (приоритет) или из SSoT | сразу, это факт источника |
| `criticality_ssot` | по маппингу dochub → SSoT ([05-mapping.md](05-mapping.md), §1) | сразу |
| `review_date` | **дата фиксации значения на странице критичности Confluence** (или дата треда подтверждения, если он есть) — со статусом `⚠️` | если дата известна |
| `review_date` | `null` | если нет ни треда, ни даты на странице критичности |
| `assigned_date` | **дата первой оценки критичности** (когда критичность впервые зафиксирована) | если дата известна |
| `assigned_date` | `null` | если дата первой оценки неизвестна |
| `approve_link` | ссылка на тред | после подтверждения |
| `status` | `draft` | пока подтверждения нет |
| `status` | `confirmed` | после подтверждения SRE |

**Приоритет источников даты.** `review_date` — это дата **текущей оценки**, а не
дата, когда репозиторий её переписал. В репозитории источник истины — `review_date`
в `catalog.yaml`; паспорт хранит копию (при расхождении побеждает реестр). При
восстановлении даты из внешних источников порядок такой:

1. **Тред подтверждения в `#Criticality_assessment`** — высокая уверенность:
   в нём есть автор, дата и содержание подтверждения. Если тред доступен и дата
   в нём читается — берём её.
2. **Страница критичности Confluence** (`criticality_source_page_id` из
   `catalog.yaml`) — средняя уверенность: дата фиксации значения на странице
   (или дата обновления страницы). Ссылка «Jira-задача по оценке критичности ИС»
   на странице может вести на неверифицированный тред — API RocketChat требует
   аутентификации.
3. **Карточка ИС в SSoT** (ответ `ssot_get`; снимок — `INFORMATION.yaml →
   ssot_snapshot`) — низкая уверенность, вторичный источник: дата там может
   отражать последнюю правку карточки, а не оценку критичности. Используется
   только если первых двух источников нет, и обязательно помечается `⚠️`.

Поставить сегодняшнюю дату значило бы объявить переоценку, которой не было.
Статус `⚠️` в `CRITICALITY.md` показывает, что дата — административная, а не
результат пересчёта по методике.

**Что уже восстановлено (4 из 6 ИС).** У `erm.mm`, `faq.mm`, `gi.mm` и `ts.mm`
`approve_link` и `review_date` восстановлены со страниц критичности Confluence
(**источник №2, средняя уверенность**): в строке «Jira-задача по оценке
критичности ИС» там стоит ссылка на сообщение в `#Criticality_assessment`
(`rid=649f0147c5f991cbb1b4c709`), а дата обновления страницы — 2025-07-14; она и
записана как `review_date`. Тред в RocketChat не открывался, поэтому источник
№1 не проверен; карточка SSoT как источник даты не использовалась. Статус при
этом **остаётся `draft`**: подтверждение по новому процессу D6.1.1 не
проводилось, а `assigned_date` по-прежнему неизвестен. У `cc-exchanger.mm` и
`cc-exchanger.smkt` строки Jira на странице критичности пустые, ссылки на тред
нет — там `approve_link` и `review_date` остаются `null`.

Порядок действий для legacy-ИС:

1. Взять критичность и атрибуты со страницы критичности Confluence, затем из
   карточки ИС в SSoT (`ssot_get` → снимок `ssot_snapshot`) как из вторичного
   источника.
2. Заполнить 9 полей паспорта; всё, что неизвестно, — `null`.
3. В `CRITICALITY.md` проставить статусы: `✅` для подтверждённого источника,
   `⚠️` для выведенного косвенно и для административных дат, `⛔` для пустых полей.
4. `status: draft` + чеклист TODO в разделе 8.
5. `make validate` → 0 ERROR (WARN про `null` — ожидаемы).
6. Дальше — обычный runbook: `make reassess IS=<код>` (план) и
   `make reassess-apply IS=<код>` (файл + `review_date`) при первом подтверждении
   SRE, затем `assigned_date` = дата первой оценки критичности (если она ещё не
   зафиксирована), `status: confirmed`.

## 8. Известные пробелы процесса и как репозиторий их компенсирует

| Пробел | Следствие | Компенсация в репозитории |
|--------|-----------|---------------------------|
| Нет календарного срока действия оценки | Оценка может «застыть» на годы | `review_period_months_default: 12` (или `review_period_months` у отдельной ИС) + `make due` как напоминание. Явно помечено как конвенция, а не требование |
| Нет SLA на подтверждение SRE | Оценка может висеть в `draft` | Метрика «время от триггера до подтверждения» в [01-process.md](01-process.md); `status: draft` виден в `INDEX.md` |
| Не зафиксирована обязательность мержа MR | Паспорт в репозитории и dochub могут разойтись | `validate` сверяет паспорт с реестром; `approve_link` фиксирует тред; расхождение видно в `make due`/`make show` |
| Пустой RACI | Непонятно, кто решает в спорной ситуации | Роли расписаны в [01-process.md](01-process.md); спорные случаи — системный архитектор продукта |
| Нет числовых значений нагрузки в Confluence | Поля `object_workload`/`object_sla` остаются `null` | `validate` даёт WARN, а не ERROR; TODO-чеклист в каждом `CRITICALITY.md`; `make due` показывает «не оценено» |
| GitLab API недоступен из окружения | Нельзя автоматически собрать список репозиториев сервисов | В паспортах — TODO для TL; группа GitLab указана в `catalog.yaml` |
