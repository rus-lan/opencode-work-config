# Справочник полей паспорта

## Когда читать

- Читать, когда заполняете `criticality-passport.yaml` или `CRITICALITY.md`.
- Читать, когда `make validate` вернул ERROR и нужно понять формат поля.
- Читать, когда выбираете значение enum и сомневаетесь между соседними.

## Кратко

- Одна ИС описана двумя файлами: `criticality-passport.yaml` — источник истины по девяти полям, `CRITICALITY.md` — всё остальное.
- Девять канонических полей обязательны; свои ключи в YAML добавлять запрещено — dochub не примет схему.
- Даты принимаются в двух форматах: `YYYY.MM.DD` (dochub) и `YYYY-MM-DD` (Markdown).
- Значения enum и уровни критичности берутся из `.opencode/skills/criticality-gen/criteria/criticality-criteria.yaml`; этот документ объясняет выбор, а не хранит значения.
- `make validate` проверяет и YAML, и `CRITICALITY.md`, и совпадение с `catalog.yaml`.

Два файла описывают одну ИС: `criticality-passport.yaml` (канонический, для
dochub) и `CRITICALITY.md` (человекочитаемый).

> **Про колонку «Excel-калькулятор».** Подписи в `упрощенный.xlsx` могут
> отличаться от приведённых: калькулятор — вспомогательный инструмент, его
> колонки не являются контрактом. Если расхождение мешает — ориентируйтесь на
> файл со страницы [4552328348](https://space.samokat.ru/pages/viewpage.action?pageId=4552328348)
> и поправьте эту таблицу.

## 1. Канонические поля `criticality-passport.yaml`

| Поле | Тип | Обязательное | Допустимые значения | Как заполнять | Excel-калькулятор |
|------|-----|--------------|---------------------|---------------|-------------------|
| `evaluated_object` | строка | да | `sber.ecom.<контур>.<name_is>` | Собирается из кода ИС; руками не придумывать | «Код объекта оценки» |
| `object_workload` | целое > 0 \| null | да (может быть null в draft) | число клиентов за **час** пиковой нагрузки | Взять из мониторинга/ёмкостного плана; если считаете транзакции — укажите это в `CRITICALITY.md` | «Клиентов в час пик» |
| `object_consumers_type` | строка (enum) | да | 7 значений, см. раздел 2 | Один наиболее негативный тип клиентов | «Тип потребителей» |
| `object_outage_impact` | строка (enum) | да | 4 значения, см. раздел 3 | Один наиболее негативный сценарий | «Последствия простоя» |
| `object_sla` | целое >= 0 \| null | да (может быть null в draft) | минуты допустимого простоя; `0` = простой недопустим | Согласуется с SRE; это SLA, а не RTO | «Допустимый простой, мин» |
| `object_criticality_estimation` | строка (enum) | да | 5 уровней, см. раздел 4 | Результат методики, не «на глаз» | «Итоговая критичность» |
| `assigned_date` | дата \| null | да | `YYYY.MM.DD` | Дата **первой оценки** = дата генерации паспорта (`generated_at`). Заполняется при `make start-apply`, не при `finalize`; при переоценке не меняется | «Дата первой оценки» |
| `review_date` | дата \| null | да | `YYYY.MM.DD` | Дата **переоценки** = `generated_at` + `review_period_months` (резолв: запись ИС → `review_period_months_default` → `criteria.staleness.review_period_months` → 12). Источник истины — `catalog.yaml → review_date` (override), в паспорте копия. Меняется при переоценке (`make reassess-apply`) | «Дата оценки» |
| `generated_at` | дата \| null | нет | `YYYY.MM.DD` | Дата генерации паспорта (`make start-apply --date`); не дата оценки и не участвует в проверке просрочки. Отсутствие допустимо | — |
| `approve_link` | строка \| null | да | ссылка `http(s)://` на **тред согласования** в `#Criticality_assessment` (принимается и относительная `/link?rid=…&msg=…`); допускается канонический формат `https://rocketchat.samokat.ru/link?rid=<rid>&path=channel%2FCriticality_assessment&msg=<msg>` | Проставляется автоматически: `handoff` пишет `approve_link = thread_link`, `finalize` берёт `thread_link` только при `handoff_status: published`. Подтверждение фиксируется **мержем MR**, отдельного ответа SRE не ждём | «Ссылка на согласование» |

Формат дат: в YAML допускаются `YYYY.MM.DD` (как в dochub) и `YYYY-MM-DD`
(как в Markdown). Валидатор принимает оба, в `INDEX.md` приводит к ISO.

**Нельзя** добавлять свои ключи: файл копируется в MR dochub как есть, и
лишние поля ломают схему. Всё дополнительное — в `CRITICALITY.md`.

## 2. `object_consumers_type` — как выбрать

Допустимые значения (7 значений) хранятся только в `.opencode/skills/criticality-gen/criteria/criticality-criteria.yaml` → `enum_selection.consumers_type.values`. Напечатать список: `make criteria`. Обязательно выбирать одно значение — наиболее негативное из применимых.

| Категория клиента | Когда применима |
|-------------------|-----------------|
| Микро- и малый бизнес (внешние) | ИС обслуживает предпринимателей и малый бизнес |
| Крупный и средний бизнес (внешние) | Корпоративные клиенты среднего и крупного сегмента |
| Крупнейшие клиенты и финансовые институты (внешние) | Банки, финансовые организации, крупнейшие корпоративные клиенты |
| Физические лица (внешние) | Массовый розничный клиент |
| Физические лица канала «Сбербанк Первый» (внешние) | Розница премиального канала |
| Физические и юридические лица Private banking (внешние) | Private banking: и физлица, и юрлица канала |
| Сотрудники компаний Группы (внутренние) | ИС только для сотрудников, внешних клиентов нет |

## 3. `object_outage_impact` — как выбрать

Допустимые значения (4 значения) хранятся только в `.opencode/skills/criticality-gen/criteria/criticality-criteria.yaml` → `enum_selection.outage_impact.values`. Обязательно выбирать одно значение — наиболее негативный реалистичный сценарий.

| Категория сценария | Когда применима |
|--------------------|-----------------|
| Клиент не получил информацию | Отказ блокирует только получение информации; действие клиента не прерывается |
| Услуга задержана без нарушения SLA | Услуга задержана, но формальный SLA не нарушен |
| Услуга не оказана в срок SLA | Нарушен заявленный SLA — клиент ждал дольше обещанного |
| Прямой убыток клиента | Есть прямые финансовые потери клиента; применимо только к внешним клиентам |

### Как выбрать между двумя соседними значениями

Правило одно: **описывайте наиболее негативный сценарий, который реалистичен
для этой ИС**. Не «средний по больнице», не «обычно всё быстро поднимаем», а
худший из тех, что действительно может случиться при отказе.

Если отказ влияет на разные категории клиентов по-разному — выбирайте сценарий
**с внешними клиентами** и наиболее тяжёлым исходом. Внутренние клиенты
(сотрудники) в приоритете ниже: их неудобство не эквивалентно убытку внешнего
клиента.

Практические проверки:

- Если ИС обслуживает и операторов (внутренние), и внешних клиентов — это
  внешние клиенты, даже если операторов больше.
- Если при отказе есть ручной обходной путь, который укладывается в SLA —
  это «без нарушения SLA».
- Если обходной путь не укладывается в SLA — «в заявленный SLA срок».
- «Прямой убыток» ставится, только если клиент теряет деньги (не «может
  потерять», а теряет при отказе).

## 4. `object_criticality_estimation` — как выбрать

Допустимые значения (5 уровней) и их определения хранятся только в `.opencode/skills/criticality-gen/criteria/criticality-criteria.yaml` → `levels.order` и `levels.definitions`. Шкала и расчёт — [02-methodology.md](02-methodology.md), раздел 2.

| Ранг | Когда применим |
|------|----------------|
| 1 — Office productivity | Внутренний инструмент эффективности; отказ не влияет на обязательства перед клиентами |
| 2 — Business operational | Операционная эффективность страдает, обязательства в SLA выполняются |
| 3 — Business critical | Обязательства перед клиентами в SLA нарушаются либо останавливается клиентский процесс |
| 4 — Mission critical | Прямые убытки клиентов и/или остановка критичных процессов компании |
| вне шкалы — Mission critical+ | Простой недопустим; уровень существует только в dochub, методикой не производится |

Значение должно совпадать с `criticality` в `catalog.yaml` — это проверяет
`make validate`. Расчёт — [02-methodology.md](02-methodology.md).

> **Если расчёт по методике не проводился** (типично для legacy-ИС и первой
> фиксации), значение переносится из SSoT или со страницы критичности как есть,
> а в `CRITICALITY.md` раздел 7 помечается `⚠️ расчёт не выполнен`. Такой паспорт
> остаётся `draft` до подтверждения SRE — источник значения указывается в
> разделе 1 и в истории оценок.

| `criticality` | enum \| null | 5 уровней | Дублирует YAML |

| `assigned_date` | дата \| null | `YYYY-MM-DD` | Дата первой оценки критичности |
| `review_date` | дата \| null | `YYYY-MM-DD` | Дата текущей оценки |
| `status` | enum | `draft`, `confirmed` | `confirmed` только после подтверждения SRE |

| `aliases` | список | название, код, arch code | Поиск по любому из них |

Теги: `критичность`, `паспорт-критичности`, `ис`, контур (`mm`/`smkt`), код ИС,
`e001`, слаг критичности (`business-critical`, `mission-critical` и т.д.).
Теги — только строчными буквами (латиница/кириллица), цифрами и дефисом; заглавные
буквы и пробелы `validate` считает ошибкой.

## 6. Что проверяет `make validate`

| Проверка | Уровень |
|----------|---------|
| YAML парсится | ERROR |
| Ровно один объект в `ecom.criticality_passport` | ERROR |
| `id == sber.ecom.<контур>.criticality_passport.<name_is>` | ERROR |
| `evaluated_object == sber.ecom.<контур>.<name_is>` | ERROR |
| Три enum-поля в допустимых значениях | ERROR |
| `object_sla` — целое >= 0 (`0` = простой недопустим) или null; `object_workload` — целое > 0 или null | ERROR |
| Даты в `YYYY.MM.DD` / `YYYY-MM-DD` / null | ERROR |
| Запись есть в `catalog.yaml`, `criticality` совпадает | WARN `CONFLICT` (не ERROR) |
| `path` в реестре совпадает с папкой | ERROR |
| Рядом есть `CRITICALITY.md` | ERROR |
| `CRITICALITY.md`: `is_code`, `criticality`, `criticality_ssot`, `status` | ERROR |
| `CRITICALITY.md`: 10 разделов на месте и по порядку | ERROR |
| `CRITICALITY.md`: `tags` — список, строчные буквы, `[a-zа-яё0-9-]` | ERROR |
| `status: confirmed` без `approve_link` | ERROR |
| `assigned_date`/`review_date` пусты (паспорт старого формата) | — (перегенерируйте: `make start-apply … FORCE=1`) |
| Кириллическая буква в коде продукта (например «Е» вместо латинской в `001`) в любом `.md`/`.yaml` | ERROR |
| Незаполненные null-поля | WARN |
| Неканонические поля | ERROR (dochub не примет) |
| `approve_link` не на домен `rocketchat.samokat.ru` / `chat.samokat.ru` | WARN |
| ИС в реестре без паспорта | WARN |

## 7. Частые ошибки

1. **Кириллица в коде ИС.** Русская «Е» вместо латинской `E` в `E001` — код
   перестаёт находиться поиском и не совпадает с реестром.
2. **Дата в формате `11.11.2026`.** Год впереди: `2026.11.11`.
3. **`object_sla: 0`.** Ноль недопустим: либо есть допустимый простой, либо
   `null`, пока SLA не согласован.
4. **Своё поле в YAML.** Например `object_name` — dochub такую схему не примет.
   Название живёт в `CRITICALITY.md` и `catalog.yaml`.
5. **`approve_link` на задачу, а не на тред.** Нужна ссылка на сообщение в
   `#Criticality_assessment` — тред, где идёт согласование. Подтверждение
   фиксируется мержем MR, поэтому отдельного ответа в треде не требуется.
6. **Расхождение YAML и реестра.** Поправили паспорт, забыли `catalog.yaml` —
   `make validate` покажет WARN `CONFLICT` (не ERROR): расхождение легитимно,
   пока его не подтвердили TL/SRE или не обновили реестр. См.
   [07-scripts.md](07-scripts.md#2-validate).

## 9. Свободное поле публикации `publication.extra_info`

Необязательный текст для треда `#Criticality_assessment` — строка
«Дополнительная информация по оценке». Живёт в `INFORMATION.yaml` (ручная
секция, `make prepare` её не перезаписывает):

```yaml
publication:
  extra_info: "Ссылка на обсуждение архитектуры: …"
```

Правила:

- Поле **опциональное**. Нет ключа или пустое значение — буллет в публикации
  не рендерится вовсе: `⛔ не заполнено` не появляется, отправка не блокируется.
- Заполнено — буллет печатается с текстом.
- `notes` как источник **не используется**: это список служебных заметок о
  данных, а не текст для треда (fallback допускается только для строкового
  `notes` — legacy-файлы).
- Обязательные поля публикации, которые блокируют отправку: технический
  архитектор, ссылка на MR паспорта в dochub, ссылка на карточку ИС в SSoT.
  Остальные поля опциональны.
