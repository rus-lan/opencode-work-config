# Источники данных: код сервисов, Confluence и Grafana

Входы расчёта не берутся из одного места. Часть лежит в документации клона
сервиса (`docs/`, `openspec/`), часть — в Confluence-дереве ИС, часть измеряется
в Grafana, часть является экспертным решением и не выводится из документов
вообще. Файл фиксирует это соответствие и порядок сбора; значения принимает
по-прежнему `enrich`.

Порядок при `BLOCKED`: `collect` (план) → `links` (карта обхода `LINK-MAP.md`:
какой узел под какой вход) → обход по карте через MCP (Confluence/Grafana) с
записью в `SOURCES-FINDINGS.yaml` → `sources` (приём фактов) → `services` (сбор
по `SERVICE-FINDINGS.md`) → `check` → `enrich`. Маршрут (какие узлы и в каком
порядке) фиксирует скрипт, обход делает агент, значения принимает `sources` и
`enrich`.

а не значение: `source.type` для принятого значения остаётся `confluence`,
`grafana` или `manual` (R14).

## 1.1. Как значения превращаются в уровень (экспресс)

> **Копия для чтения; канон — `criteria/criticality-criteria.yaml → express_method`.**
> Формула, пороги и обе таблицы коэффициентов ниже воспроизведены для удобства
> чтения; расчёт берёт числа только из файла критериев, а наличие этой пометки
> проверяет `make docs-check`.

Экспресс-метод — перенесённый алгоритм калькулятора критичности
(`express_method`, `kind: documented`, источник —
`docs/reference/calculator/калькулятор критичности упрощенный.xlsx`):

```text
E = коэф. типа клиентов × коэф. характера влияния × клиентов/час
t = порог / E × 60 + SLA          пороги: 100 / 1 000 / 10 000 / 50 000
балл интервала = матрица[первая подходящая severity][интервал]
уровень = max(балл) → score_to_level → levels.dochub_to_ssot
```

Коэффициенты типа клиентов (`express_method.client_coefficients`):

| Тип клиентов | Коэф. |
|--------------|-------|
| Физические лица (Внешние клиенты) | 1 |
| Микро/малый бизнес (Внешние клиенты) | 1 |
| Крупный и средний бизнес (Внешние клиенты) | 10 |
| Крупнейшие клиенты и финансовые институты (Внешние клиенты) | 100 |
| Физические лица канала Сбербанк Первый (Внешние клиенты) | 10 |
| Физические и юридические лица канала Private banking (Внешние клиенты) | 20 |
| Сотрудники компаний Группы (Внутренние клиенты) | 0.2 |

Коэффициенты характера влияния (`express_method.impact_coefficients`):

| Характер влияния | Категория | Коэф. |
|------------------|-----------|-------|
| Клиент не смог узнать необходимую информацию | Незначительное | 0.2 |
| Не оказана услуга в ожидаемый срок, без нарушения SLA | Низкое | 0.5 |
| Не оказана услуга в заявленный SLA срок | Ниже среднего | 0.8 |
| Клиент не получил кредитные средства в заявленный срок | Среднее | 1.0 |
| Не получен доступ ко своим счетам, не смог осуществить сделку | Высокое | 1.5 |
| Клиент понес прямой убыток из-за недоступности сервиса | Критическое | 3.0 |

Формулировки в таблицах сокращены; дословные значения enum — в
`enum_selection.consumers_type.values` и `enum_selection.outage_impact.values`.
**Все четыре входа обязательны**: нет нагрузки или типа клиентов — `E = 0`,
нет влияния — неизвестен коэффициент, нет SLA — не сдвигаются `t`. Гейт
возвращает `BLOCKED`, а не «примерный» уровень.

## 1.2. Критичность в SSoT: где лежит и что не добавлять

Критичность ИС в SSoT хранится **только** в карточке ИС
(`information-systems/<код>`) → блок `severity`; читается ответом MCP
`ssot_get(group="information-systems", entity=<код>)`, снимок которого пишет
`ssot-import` в `INFORMATION.yaml → ssot_snapshot`. Отдельной сущности/файла
критичности нет; остальные части карточки (`components`, `links`, `resources`,
`duty`, `roles`) к уровню отношения не имеют.

| Поле | Тип | Допустимые значения | Когда обязательно |
|------|-----|---------------------|-------------------|
| `severity.type` | string | `mission-critical` \| `business-critical` \| `business-operational` | фактически у всех ИС; enum — в `schemas/information-systems/base.schema.json` |
| `severity.method` | string | `expert` \| `target` | нет |
| `severity.addon` | string \| null | `null` \| `contact` \| `incident` \| `period` | только при `type: business-critical` |
| `severity.confirmation` | string | regex `^https://rocketchat.samokat.ru/\S*$` | при `method: target` |

Правила:

- маппинг «уровень паспорта → enum SSoT» — `levels.ssot_enum` в
  `criteria/criticality-criteria.yaml` (не в коде): `Mission critical` →
  `mission-critical`, `Business critical` → `business-critical`,
  `Business operational` → `business-operational`, `Office productivity` →
  `business-operational` (в SSoT такого уровня нет);
- `confirmation` — ссылка на **актуальный** тред в `#Criticality_assessment`
  (источник — `catalog.yaml → approve_link`, а не прежнее значение в SSoT);
- `addon` не выдумывается: существующее значение сохраняется, новое не
  добавляется;
- правка точечная: в MCP-форме меняются только `severity.type` и
  `severity.confirmation`, остальные поля карточки не трогаются;
- эталон изменения — MR, созданный `ssot_form_save`, где меняются 1–3 строки
  (`severity.type` и `severity.confirmation`), других файлов в коммите нет.

**Чего в SSoT нет и куда это не добавляют:** `review_date`, `assigned_date`,
`tech_architect`, `business_criticality`, `criticality` — таких полей в
`base.schema.json` нет. Они живут в `catalog.yaml` и Confluence; SSoT получает
только `severity`.

### Запись severity: только через MCP-форму

**Гейт CI.** Для путей `entities/**` джоб `codeowners` требует минимум один апрув от ботов
`project_14598_bot_*`. Эти боты апрувят только MR, созданные через SSoT-UI, поэтому MR,
созданный напрямую в GitLab (мимо SSoT-UI), пройти проверку не может — независимо
от содержимого и от апрувов людей.

Проверено на практике: MR !5404–!5409 в data-storage упали на пункте
«МР можно создавать только через SSoT-UI», имея апрувы техлида и других сотрудников.
Все шесть были закрыты и пересозданы через UI как !5551–!5556.

**Дополнительный гейт для критичности.** Если меняется `severity.*` в карточке, бот SSOT
добавляет в MR блок `@codeowners extend`, требующий **один** апрув от SRE или руководства
технической архитектуры: `@akolomytov`, `@evolvenkova`, `@santonov`, `@schurikov`.
Точный список на конкретном MR — в артефакте джоба `codeowners.json` (поле `required`).
Этот гейт действует и на MR, созданных через UI.

| Что меняется | Кто обязан аппрувить |
|---|---|
| `links`, `components`, `roles`, `resources`, `duty` | Техлид ИС |
| `severity.*` | Техлид ИС **+ минимум один** из SRE/техархитектуры |

**Порядок записи — только через MCP-форму:**

1. `ssot_entity_open` → `ssot_form_fields` → `ssot_ui_select`/`ssot_ui_fill` →
   `ssot_form_save` — правка формы; создаётся бот-MR
   `api/information-systems/<код>/<stamp>-<suffix>`, ответ содержит `mrUrl`.
2. `ssot-record --mr-url <mrUrl>` — ссылка в `.ssot/<код>-MR.url` и поля
   `ssot_*` в `INFORMATION.yaml`.
3. Апрувы: техлид ИС и (для `severity.*`) один из SRE/техархитектуры.
4. `ssot_mr_approve(confirm: true)` → `ssot_apply_changes(confirm: true)` →
   `ssot_wait_master`.
5. `ssot-verify --verify-json <ssot_get после применения>` — сверка.

Клона SSoT и git-операций у скилла нет: MR вне SSoT-UI не пройдёт джоб
`codeowners` для путей `entities/**`.

## 1.3. Команда-владелец: ответ MCP `ssot_team`

Единственный источник контактов TA/TL (и остальных ролей команды) — ответ MCP
`ssot_team(code=<team>)`, который передаётся в `make contacts` через
`--team-json`. Код команды — `catalog.yaml → systems[].team` (например `t006`);
в SSoT каталог называется **нижним регистром**, поэтому код приводится к
`t006`.

Реестр изменений ответственных по продуктам/технологиям 2026
([4323248283](https://space.samokat.ru/pages/viewpage.action?pageId=4323248283)) —
это **журнал заявок на оргизменения, а не ростер**: актуальный ростер всегда
`ssot_team`; реестр используется как fallback при свежей передаче продукта,
когда SSoT ещё не обновлён.

| Поле | Тип | Что это |
|------|-----|---------|
| `groups[].name` | string | роль в команде: `cto`, `tl`, `ptl`, `ta`, `sa`, `s-arch`, `dm`, `po`, `qa`, `backend`, `web`, `des`, `ba`, `bo`, `l3`, `sc`, … |
| `groups[].members[]` | string | логин сотрудника (`dkozlov`, `ipilyaev`) — **не** ФИО |

Что из этого берётся:

| Куда | Из какой группы | Формат |
|------|-----------------|--------|
| `INFORMATION.yaml → contacts.groups` | все группы файла (копия ростера) | `{<роль>: [<login>, …]}` |
| `identity.ta` (публикация) | `ta` | `@dkozlov` (несколько логинов — через `, `) |
| `identity.tl` (публикация) | `tl` | `@ipilyaev` |
| `identity.sa_mention` | `sa`, иначе `s-arch` | `@tkolpakov` (в шаблонах пока не выводится) |
| `actions.jira.assignee_tl` | `tl` (первый логин) | `ipilyaev` — логин для Jira |
| `actions.jira.assignee_pdm` | `po`, иначе `dm` (первый логин) | `isadretdinov` |

Правила:

- **Соответствия login → ФИО в SSoT нет** (сущности сотрудников нет), поэтому в
  публикации стоит `@<login>`: RocketChat упоминает по логину, ФИО подставлять
  нечем и не нужно;
- логины приводятся к нижнему регистру, пустые строки и дубликаты
  отбрасываются, порядок SSoT сохраняется;
- **allowlist логина:** допустим только `[a-z0-9][a-z0-9._-]{0,31}` (после
  `strip`/lower). Остальное отбрасывается целиком: `x] @here` сломал бы
  inline-список `ta: [x] @here]`, а `a\n* TL - @all` вставил бы в публикацию
  строку-буллет с пингом канала (подстановка идёт без экранирования).
  `make contacts` печатает
  `WARN  в team.yaml пропущены некорректные логины: <…>`, в блок
  `INFORMATION.yaml → contacts` эти значения не попадают;
- **зарезервированные упоминания RocketChat:** логины `all`, `here`, `channel`
  не превращаются в `@all`/`@here`/`@channel` (это пинг всего канала) —
  печатается
  `WARN  логин <x> совпадает с зарезервированным упоминанием RocketChat — упоминание не добавлено`.
  Сам логин при этом остаётся участником `contacts.groups`: это факт SSoT,
  подавляется только упоминание;
- код команды — слаг (`t006`), а не путь: `team: "../x"` отвергается
  (`некорректный код команды`), иначе читались бы данные чужой команды;
- пустая группа — `[]`, участники не выдумываются; пустые `ta`/`tl` — `WARN`
  (`make contacts`, `make validate`), публикация соберётся без упоминания;
- пишет секцию только `ssot-import --team-json` / `make contacts`; `INFORMATION.yaml → roles`
  (ФИО, заполняется руками) остаётся fallback для `assignee_*`.

## 2. Процедура Confluence

| Шаг | Действие | Результат |
|-----|----------|-----------|
| 1 | Стартовые страницы: `links.yaml` карточки ИС (`title: page`) + `catalog.yaml → confluence_page_id`, `criticality_source_page_id`, `dr_page_id`, `decision_log_page_id` | список корней обхода |
| 2 | `confluence_get_page(page_id, convert_to_markdown=True)`, дети — `confluence_get_page_children`; BFS до глубины 2 | дерево страниц ИС |
| 3 | Приоритет чтения: DR → Support/SLA → трафик → архитектура → E2E → ИБ → Decision Log | значения раньше, шум позже |
| 4 | Поиск по ключевым словам: `SLA, RTO, RPO, доступность, 99., простой, нагрузка, RPS, QPS, клиент, влияние, критичн, E2E, зависим, ПДн, конфиденциальн, целостн` | найденные разделы |
| 5 | Фиксация: `page_id`, заголовок страницы, название раздела, дословная цитата, URL | `source.ref` и `evidence` |

Ограничения и ловушки:

| Ловушка | Симптом | Обход |
|---------|---------|-------|
| Новый редактор (ADF) | `confluence_get_page` вернул пустой `content.value` у непустой страницы | `confluence_get_page_history(page_id, version)` — история отдаёт полный текст версии |
| Rate limit | `Rate limit exceeded … Current limit: 30, Remaining: 0` | батчи не больше 10 страниц с паузами; пауза и повтор; лимит общий на ключ и на несколько агентов |
| Глубина обхода | дерево разрастается на десятки страниц | потолок: глубина 2, не больше 40 страниц на ИС |
| Пересказ вместо цитаты | «вроде бы написано, что SLA 4 часа» | значение ставится только по дословной формулировке раздела |

## 2a. Клоны сервисов: `docs/` и `openspec/`

| Шаг | Действие | Результат |
|-----|----------|-----------|
| 1 | `make services IS=...` (план) → `make services-apply IS=...` | клоны `apps/IS/COMPONENT/` обновлены (`git clone` / `fetch --prune` + `pull --ff-only`); `NO_CLONE=1` — git не вызывается, отсутствующие клоны идут в §2 |
| 2 | Открыть `is/IS/SERVICE-FINDINGS.md` §1 | какие сервисы есть, где `docs/`, `openspec/`, SLO-конфиг (`slo-kit.yaml`, `slo.yaml`, `alerts.yaml`, `sloth.yaml`); `Chart.yaml`, `values*.yaml`, `deploy/` и `.gitlab-ci.yml` — инфраструктура, а не SLO (видны в §7) |
| 3 | §3 «Назначение и потребители» | цитаты «файл:строка» → основание для `consumers_type` (значение подтверждает PdM) |
| 4 | §4 «Нормативы» + колонка «пригодно для `object_sla`» | цитаты про SLA/SLO/RTO/простой; минуты простоя ≠ процент доступности |
| 5 | §5 «Потоки данных» и §6 «Что даёт основание для входов» | Kafka/шедулеры/кроны; какие входы получили основание, какие нет |
| 6 | §7 «Не найдено» | чего в клоне нет: `docs/`, `openspec/`, SLO-конфиг, основание для входа |

Что ищется: назначение и потребители, нормативы доступности и простоя, потоки
данных и автоматизация, упоминания ПДн. Цитата всегда дословная и с
`файл:строка` — пересказ не годится.

Ограничения и ловушки:

| Ловушка | Симптом | Обход |
|---------|---------|-------|
| Аббревиатура внутри слова | `translator` даёт «SLA», `hasLabels` — «SLA», `slow` — «SLO» | поиск по границам слова (`SLA`, `SLO`, `RTO`, `RPO` как отдельные токены); ложные находки в отчёт не попадают |
| `недоступность` вместо `доступность` | строка про grace-режим попадает в «Нормативы» | `недоступност` — это влияние простоя (основание для `outage_impact`), а не норматив |
| Манифесты и lock-файлы | `go.sum`/`package-lock.json` дают десятки «нормативов» | `go.mod`, `go.sum`, lock-файлы, минифицированный код, `.env*` и тесты не сканируются |
| Аббревиатура без величины | `SLA` в заголовке задачи JIRA, `SLA = 'SLA'` в GraphQL-enum, `"slaTotal": "SLA общий"` в i18n | `SLA`/`SLO`/`RTO`/`RPO` считаются нормативом только вместе с числом и единицей в той же строке |
| Аббревиатура внутри литерала | `{ name: "Нарушен SLA доставки менее 20 минут" }` — причина компенсации, а не норматив | аббревиатура ищется вне строковых литералов: подпись или ключ нормативом не является |
| `gracefulShutdownTimeout` | `downtime` внутри слова (`shut` + `downtime` + `out`) даёт «влияние простоя» | `downtime`/`outage` ищутся по границам слова (`\bdowntime\b`), таймаут завершения процесса нормативом не считается |
| Кодогенерация и подписи | `src/__generated__/schema.graphql`, `i18n/locales/ru.json` дают десятки «нормативов» | каталоги `__generated__`, `locales`, `i18n` не сканируются |
| Объём отчёта | 43 сервиса дают тысячи совпадений | таблицы нормативов и потоков ограничены (200 строк); при усечении в отчёте напечатано, сколько всего совпадений |
| Процент вместо минут | `objective: 99.8` выглядит как SLA | в `object_sla` идут только минуты простоя: основанием становится цитата, где рядом со словом «простой» есть минуты (та же проверка, что в колонке «пригодно для `object_sla`»); процент пересчитывает SRE, а не скилл |
| Нет `docs/`/`openspec/` | «документации нет» | это факт, а не ошибка: §7 отчёта, дальше Confluence |
| Сборка «для проверки» | хочется запустить `go build` или тесты, чтобы «убедиться» | запрещено (R12): клон только читается, единственный процесс — `git` из allowlist (`clone`, `pull`, `fetch`, `rev-parse`, `log`, `status`, `show`, `diff`, `ls-remote`); `checkout`/`reset`/`clean` отклоняются |

### Пропуск закрытых сервисов

| Поле | Значение |
|------|----------|
| Что считается закрытым | компонент ИС, у которого `lifecycle` (в `INFORMATION.yaml` — `status`, значение то же) входит в `criteria.service_lifecycle.skip` — сейчас это `closed` |
| Что с ним делает скилл | не клонирует (`git clone`/`pull` не выполняется), не читает файлы, не строит находки и основания; в отчёте — §2 «Пропущенные сервисы (lifecycle)» с причиной из `service_lifecycle.skip_reason`. При `--no-clone` отсутствующий клон тоже попадает в §2, но с причиной «не склонировано» |
| Почему нельзя использовать как основание | сервис выведен из эксплуатации и не участвует в функционировании ИС: его `docs/`, нормативы и код описывают прошлое состояние, а не текущее (`service_lifecycle.evidence_rule`) |
| Что писать в отчёт | таблицу `сервис / репозиторий / lifecycle / причина` и строку `lifecycle не указан` для компонентов без значения (они анализируются как активные) |
| Как проверить | `make services IS=...` печатает `skip (lifecycle: closed)` и `пропущено (lifecycle): N`; в frontmatter отчёта `services_skipped: N` совпадает с числом компонентов `closed` |

## 3. Процедура Grafana

| Шаг | Действие | Результат |
|-----|----------|-----------|
| 1 | Папка продукта: uid `feuw533xc1hq8c` (E001), внутри — подпапки по ИС | область поиска |
| 2 | `grafana_search_dashboards` по коду ИС и именам компонентов-шлюзов (`*-gateway`, `krakend`, `nginx`, `vts`) | список дашбордов |
| 3 | `grafana_get_dashboard(uid)` → панели; искать `rate(`, `requests`, `rps`, `http_requests_total`, `nginx`, `vts` | целевая панель |
| 4 | Выполнение: `grafana_query_from_dashboard_panel` или `grafana_query_prometheus` (параметр `expr`, не `query`); окна 7d и 30d; брать пик | `peak_rps` |
| 5 | Фиксация: `uid` дашборда, номер/название панели, точный PromQL, datasource, окно, результат | `source.ref` и `evidence` |

Формула и границы применимости:

```text
peak_hour_load = peak_rps × 3600
```

- Пик берётся как `max_over_time(<expr>[7d:5m])` и сверяется с окном 30d.
- Контроль объёма за самый нагруженный час: `max_over_time(sum(increase(<counter>[1h]))[7d:10m])`.
- **Запрещено** использовать как нагрузку latency, errors, `up`/probe-метрики и число
  соединений (`nginx_vts_main_connections`): это не клиенты и не запросы.
- Метрика шлюза считает HTTP-запросы, а не уникальных клиентов. Если нужны
  именно клиенты, а бизнес-метрик в namespace нет — фиксируется это в `note`,
  а значение помечается `derived`.

Ловушки:

| Ловушка | Симптом | Обход |
|---------|---------|-------|
| Фильтр папки игнорируется | `folderUids` / `folderUIDs` в `grafana_search_dashboards` вернул все папки org | фильтровать результат на клиенте по uid папки |
| Тяжёлый запрос | `Request timed out` на `max_over_time(...[30d:5m])` | уменьшить разрешение подзапроса (`[30d:15m]`) или сузить окно |
| Неверный параметр | `grafana_query_prometheus` не принимает `query` | параметр называется `expr` |
| Datasource 404 | панель ссылается на удалённый datasource | брать datasource из ответа панели; при 404 — другая панель/дашборд, а не «примерное» значение |

### `peak_hour_load` из RPS шлюза

| Правило | Значение |
|---------|----------|
| Формула | `peak_hour_load = peak_rps × 3600` |
| Единица | `запросов/час` — шлюз считает HTTP-запросы, а не уникальных клиентов |
| Окно | фиксировать в `source.ref`/`evidence`; `7d` и `30d` дают разброс до 18% (в прогоне: 51324 против 60720) |
| Кросс-проверка | `max_over_time(sum(increase(<counter>[1h]))[<окно>:1h])` — фактический объём за пиковый час; расхождение с `peak_rps × 3600` объясняется тем, что пик держится не весь час |

Если панель фильтрует по `env=~"$env"`, а у серии лейбла `env` нет — панель
отдаёт пусто. Запрос воспроизводится без фильтра `env` (`sum(rate(...))`), факт
фиксируется в `evidence`; подменять «пусто» значением нельзя.


## 4. Статусы значения

| `status` | Когда ставится | Что проверяет гейт |
|----------|----------------|--------------------|
| `confirmed` | значение дословно есть в источнике и подтверждено владельцем роли | засчитывается без предупреждений |
| `derived` | значение вычислено по формуле (формула обязательна) или выведено из enum-правила | засчитывается, печатается «нужно подтверждение» |
| `missing` | данных нет или значение не подтверждено | blocking-вход считается отсутствующим → `BLOCKED` |

Правила:

1. `derived` без формулы — не значение: формула и исходные числа пишутся рядом.
2. `confirmed` без `source: {type, ref}` — не значение: `enrich` отклоняет лист.
3. `missing` при заполненном `value` — значение есть, но не подтверждено; гейт
   всё равно блокирует.
4. Решение владельца (`provenance.manual_decision`) оформляется как `manual` с
   ref вида «решение PdM, `<YYYY-MM-DD>`; `INFORMATION.yaml#notes`». Формат ref
   проверяется **человеком, а не механикой**: ref — свободный текст, `enrich` и
   `criteria check` его не разбирают, поэтому «похоже на решение» ≠ решение.

## 5. Запреты

| Запрет | Почему |
|--------|--------|
| Подставлять RTO «часы» в `object_sla` (минуты) без подтверждения SRE | RTO и допустимый простой — разные нормативы; перевод меняет корзину времени и уровень |
| Переносить норматив доступности с ИС другого уровня критичности | норматив привязан к уровню, а не к продукту |
| Считать метрику событий Kafka числом клиентов | одно событие ≠ один клиент; несколько событий на диалог |
| Выводить `axes_scores` и `cia` из документов | это экспертное решение; в источниках есть только итоговый уровень, разбивки нет |
| Подставлять значение «по аналогии с другой ИС» | провенанс указывает на чужой источник; проверка невозможна |
| Брать latency/errors/probe как нагрузку | это не запросы и не клиенты |
| Считать цитату из клона подтверждённым значением | комментарий в коде не подтверждён владельцем: значение проводит `enrich` (R14) |
| Собирать, тестировать или запускать код из клона | чужой репозиторий в неизвестном состоянии; этап `services` только читает (R12) |
| Заполнять лист в обход `enrich` | источник не проверен, гейт обойдён |
| Писать в SSoT что-то кроме блока `severity` | остальные поля карточки приходят из SSoT в паспорт, а не наоборот; лишние поля ломают схему |

| Оставлять в `confirmation` прежнюю ссылку | подтверждать нужно актуальный тред; источник — `catalog.yaml → approve_link` |

## 6. Проверка результата

```text
make collect IS=<код>          # план: страницы, дашборды, запросы, адресаты
make collect-apply IS=<код>    # записать RESEARCH-PLAN.md
make services IS=<код>         # план: клоны сервисов, docs/, openspec/, нормативы
make services-apply IS=<код>   # записать SERVICE-FINDINGS.md
   (сбор по плану; значения вписываются в DATA-REQUIREMENTS.yaml)
make enrich IS=<код>           # проверка листа без записи
make enrich-apply IS=<код>     # принять значения в INFORMATION.yaml
make check IS=<код>            # повторный гейт
```

- Заполнение принимается только через `enrich`: `source: {type, ref}` +
  `status: confirmed` (или `derived` с формулой).
- Если blocking-пропуски остались, они снова попадают в
  `DATA-REQUIREMENTS.*` и в новый `RESEARCH-PLAN.md`.
- Если данных нет и взять их негде — ИС исключается
  (`excluded: true` + `reason`), а не заполняется догадкой.
