# Протокол поиска: tier 1, tier 2 и доказательство «не найдено»

Сбор значений идёт в два прохода. **Tier 1** — точные идентификаторы: код ИС,
её название, namespace сервиса, группа GitLab. **Tier 2** — комбинации: код ИС
плюс термин предметной области, название плюс термин, страница плюс термин,
логин владельца плюс код, дерево от архитектуры, CQL по функциональным областям.

Правило одно: **если tier 1 не дал значения, tier 2 обязателен.** «Не найдено» —
это результат, а не отсутствие результата: он доказывается списком выполненных
запросов. Молчание вместо списка `validate` и `ask` считают незакрытым этапом
сбора.

## 1. Что считается результатом

| Результат | Что это | Куда попадает |
|-----------|---------|---------------|
| **Значение** | дословная формулировка входа: число минут простоя, член enum, пик RPS | `CANDIDATES.yaml` → кандидат с `value` и `source`, затем `ask-answers` / `enrich-apply` |
| **Основание** | цитата, из которой значение не следует дословно («RTO — часы», «SLA 99.9 %», «высокая нагрузка») | кандидат с `value: null` (`confidence: weak`) — человек вписывает значение вручную |
| **Не найдено** | ни значения, ни основания, но запросы выполнены и записаны | `search.<вход>.result: «не найдено — …»` + `done: true` |
| **Не искали** | запросов нет | `done` не ставится: это не результат, а пропуск этапа |

Основание не становится значением само: `confidence: strong` требует
`source: {type, ref}`, иначе `ask` понижает кандидата до `weak` с `WARN`
(R1 — факт-или-null).

## 2. Tier 1 — поверхностный

Поверхностный проход идёт по одному маршруту и **не расширяется**: бюджет —
не больше 8 запросов. Каждый шаг либо даёт значение/основание, либо уходит в
список `search.shallow` как пустой.

Маршрут: **Product scope → страница ИС → DR-страница → Support-страница**.

1. **Product scope продукта** (`catalog.yaml → product_scope_page_id`):
   `label = "functional-area" AND space = currentSpace() AND ancestor = <page_id Product scope>`
   — найти строку ИС в таблице-глоссарии. Пустая ячейка здесь ничего не
   опровергает (см. §4).
2. **Код ИС** дословно, в кавычках: `"<код ИС>"` — страницы, где ИС названа
   кодом (`opercrm.smkt`).
3. **Название ИС** из `identity.name`: `"<название ИС>"` — страницы, где код не
   пишут, а пишут название.
4. **Дерево страницы ИС**: `confluence_get_page_children`, глубина 2, ≤ 40
   страниц — разделы «Пользователи», «SLA», «Сценарии отказа».
5. **DR-страница ИС** (`catalog.yaml → dr_page_id`): разделы влияния, сценариев
   отказа, RTO/RPO, допустимого времени простоя.
6. **Support-страница ИС**: «целевое время решения» / «SLA решения»,
   «Классификация инцидентов».
7. **Grafana**: `namespace=<namespace>` по каждому компоненту-шлюзу из
   `components.yaml`; namespace неизвестен — поиск дашборда по коду ИС (папка
   продукта → подпапка ИС).
8. **SSoT**: `ssot_get(group="information-systems", entity="<код ИС>")`
   (`ssot_list` — если код неизвестен) — карточка ИС, компоненты, связи,
   команда, `links` / `resources`.

**Результат tier 1** — одно из трёх: значение (tier 2 не нужен), основание
(кандидат `value: null` + tier 2 для значения) или пусто по всем 8 запросам
(tier 2 обязателен, `shallow` заполнен). GitLab-группа (`catalog.yaml →
gitlab_group`) в бюджет tier 1 не входит: её разбор — комбинация tier 2.

## 3. Tier 2 — глубокий: маршруты по входам

> **Копия для чтения; канон запросов — `criteria.inputs[].queries`**
> (`criteria/criticality-criteria.yaml`). Для входов, у которых поля `queries`
> нет, канон — `criteria.inputs[].where` плюс `DEEP_SEARCH_TERMS` в
> `scripts/criticality.py` (печатаются в `RESEARCH-PLAN.md` §«Глубокий поиск»).
> Расхождение трактуется в пользу файла критериев.

| Вход | Запросы | Страницы-реестры | Как оценивать доказательство |
|------|---------|------------------|------------------------------|
| `peak_hour_load` | `<код ИС>` + `"нагрузка"`, `"RPS"`, `"QPS"`, `"пик"`; `grafana: namespace=<namespace>` + панель трафика | дерево страницы ИС (страницы трафика/RPS); реестр ММ `mm_registry` — шлюз | значение — панель с `expr`, datasource и окном 7d/30d; цитата «высокая нагрузка» — только основание |
| `consumers_type` | `<код ИС>` + `"пользователи"`, `"клиенты"`, `"аудитория"`, `"операторы"` | Product scope, страница ИС («Пользователи продукта»), SSoT `base.yaml` | значение — дословная формулировка из `enum_selection.consumers_type.values`; описание потребителей прозой — основание |
| `outage_impact` | `<код ИС>` + `"влияние"`, `"простой"`, `"последствия"`, `"недоступность"` | DR-страница, DRP-план (`is_registry` → «Ссылка на DRP план», шаблон `drp_template`) | значение — дословная формулировка из `enum_selection.outage_impact.values` в разделе влияния; «операторы не работают» — не значение |
| `object_sla` | `<код ИС>` + `"SLA"`, `"RTO"`, `"RPO"`, `"доступность"`, `"99."` | Support-страница, DR-страница, фреймворк НФТ `tier_framework`, `is_registry` (TIER DR) | значение — минуты простоя с цитатой; «RTO 4 часа» → `derived` 240 мин только с подтверждением SRE; «99.9 %» ≠ минуты |
| `time_to_impact` | `<код ИС>` + `"RTO"`, `"время восстановления"`, `"окно"`, `"мгновенн"` | DR-сценарии (кеш, репликация, очередь), DRP-план, разбор инцидентов | значение — одна корзина `time_buckets.order` с цитатой сценария; «последствия мгновенные» без окна — не значение |
| `axes_scores` | `<код ИС>` + `"ущерб"`, `"штраф"`, `"репутация"`, `"выручка"`, `"GMV"` | финансовая модель продукта, юридические заключения, ИБ/PR, клиентские метрики | только основание (кто оценивал, какие цифры ущерба упоминаются); сами оценки — экспертное решение TL/ИБ/финансов |
| `cia` | `<код ИС>` + `"ПДн"`, `"конфиденциальн"`, `"целостн"`, `"доступност"`, `"ИБ"` | классификация данных и модель угроз, `sec_methodology`, `protection_classes` | только основание; 5 классов методики ИБ ≠ `low/medium/high`, напрямую не подставляются |
| `financial_loss` (advisory) | `criteria.inputs.optional[financial_loss].queries` — 5 запросов: `"потери GMV"`, `"недополученного GMV"`, финансовая модель продукта, `<код ИС>` + `"ущерб"`/`"потери"`, `"постмортем"` + название | DR-страница (сценарии простоя), финансовая модель продукта, постмортемы, методология недополученного GMV (`financial_loss.methodology_refs`) | значение — сумма с периодом и ссылкой; пустой блок «Оценка ущерба» — не данные; внутренняя ИС (проверка `applicability_check`) → `0 руб/час` с прецедентом |
| `e2e` (маршрут, не вход) | `criteria.inputs.routes.e2e.queries` — 4 запроса: `label = "checkliste2e" AND text ~ "<код ИС>"`; `label = "e2e-process-card" AND space = SMKT AND text ~ "<название ИС>"`; `<код ИС>` + `title ~ "BP"`; `<название ИС>` + `"сквозной процесс"` | `e2e_catalog` (каталог процессов 2.0), `e2e_registry` (реестр процессов), `is_process_registry` (реестр ИС: «Наименование ИС / Код ИС / Название процесса») — перечислены в `routes.e2e.external_refs` | `direct` — код ИС в строке (`<tr>`) структурной таблицы: таблица шагов процесса (заголовок называет «Шаг процесса» / «Информационная система») или реестр («Код ИС» / «Наименование ИС»); `indirect` — упоминание в прозе или в служебной ячейке (лог изменений, шапка); `none` — совпадений нет. Строка считается один раз. Обязательно фиксировать «шагов N из M» (`record_steps`), M — число строк данных таблицы шагов |

**Общие комбинации** (применяются к любому входу; строки подставляются из
реальных данных ИС — кода, названия, продукта, команды, page_id, логинов):

1. `"<код ИС>" and "<термин>"` — по каждому из первых трёх терминов входа.
2. `"<название ИС>" and "<первый термин>"` — когда код в тексте не пишут.
3. CQL по функциональным областям продукта (Product scope, §2 шаг 1).
4. Дерево от **архитектуры ИС** (`architecture_page_id`): предки, дети, соседи,
   метки — архитектурные решения живут рядом, а не в тексте страницы ИС.
5. Страница ИС и её дети — с термином входа.
6. DR-страница (`dr_page_id`) + термин: влияние простоя, RTO/RPO.
7. Журнал решений (`decision_log_page_id`): принятые ограничения и нормативы.
8. `"<команда>" and "<первый термин>"` — нормативы могли осесть у подразделения.
9. `"<логин>" and "<код ИС>"` — по владельцам из `contacts` (TA, TL, SA, s-arch, po).
10. `grafana: namespace=<namespace> + панель «<термин>»`; без namespace —
    `заголовок дашборда "<код ИС>" + "<термин>"`.
11. `gitlab: группа <gitlab_group> + "<термин>"` — нормативы в `docs/`, `openspec/`.
12. `ssot: ssot_get(<код ИС>)` и `ssot_get` продукта — связи `links` и
    цепочка ссылок продукта.

Глубокий поиск не «перебирает всё»: он идёт по маршруту входа из таблицы плюс
общие комбинации и **записывает каждый выполненный запрос**, включая пустые.

## 4. Правила доказательности

1. **Прямое подтверждение** — код ИС в строке (`<tr>`) структурной таблицы
   источника: таблица шагов процесса (её заголовок называет «Шаг процесса» /
   «Информационная система») или реестр («Код ИС» / «Наименование ИС»), таблица
   SLA. Код в произвольной ячейке — шапка таблицы, «Лог изменений», служебная
   таблица — это `indirect`, а не доказательство участия ИС. Упоминание в прозе
   — тоже основание (`value: null`), даже если звучит утвердительно.
2. **Фиксируйте количественную силу** подтверждения: «шагов 20 из 91»,
   «3 из 4 сценариев DR», «колонка TIER DR заполнена у 12 из 20 строк» — а не
   только «да/нет». Шаги считаются строками таблицы шагов (одна строка — один
   шаг, даже если код в нескольких её ячейках); M — все строки данных этой
   таблицы, шапка не в счёт. Сила подтверждения — часть основания и
   переносится в `result`.
3. **Пустая колонка или шаблон без значений — не доказательство отсутствия**, а
   сигнал идти глубже. Пример: пустая колонка «Сквозной бизнес-процесс (e2e)» в
   Product scope с пометкой «В рамках пилота не заполняем» — повод идти в каталог
   процессов (`criteria.inputs.routes.e2e`), а не основание для `not_filled`.
4. **Шаблонные блоки не считать данными**: пустой блок «Оценка ущерба» в
   постмортемах, пустые разделы шаблона DRP, заголовок без содержания.
5. **Заголовки страниц — только из проверенного кеша** (R19): рендер берёт
   название из `catalog.yaml → page_titles` (`title_verified_at` заполнен
   `make verify-titles FIX=1`), а `ref` обязан указывать на реально прочитанную
   страницу с её настоящим `page_id`. Заголовок, сочинённый или
   «восстановленный по контексту», — дефект уровня публикации, а не опечатка:
   нет кеша — пишется `[page <id>] <url>` без названия (R1 «Факт-или-null»,
   R4 «Провенанс», R19 «Заголовки страниц»).

## 5. Как фиксировать: `CANDIDATES.yaml → search`

```yaml
search:
  object_sla:
    shallow:
      - 'confluence: "opercrm.smkt"'
      - 'confluence: "Операционный CRM"'
      - 'grafana: namespace=opercrm-gateway'
      - 'ssot: ssot_get(information-systems/opercrm.smkt)'
    deep:
      - 'confluence: "opercrm.smkt" and "SLA"'
      - 'confluence: "opercrm.smkt" and "RTO"'
      - 'confluence CQL: label = "functional-area" and space = currentSpace() and ancestor = <page_id>'
      - 'confluence: page_id=<DR> + "SLA" (DR: влияние, RTO/RPO)'
      - 'confluence: "dkozlov" and "opercrm.smkt" (владелец из contacts)'
    done: true
    result: "не найдено — SLA решения нет ни на DR-странице, ни в дереве ИС; RTO указан в часах, минут простоя нет"
```

| Поле | Смысл |
|------|-------|
| `shallow` | фактические запросы tier 1 |
| `deep` | фактические запросы tier 2 (маршрут входа + общие комбинации) |
| `done` | `true` — tier 2 выполнен и зафиксирован. Только тогда «не найдено» доказано |
| `result` | что дал поиск, с количественной силой подтверждения. «Не найдено — …» — тоже результат, и он обязателен |

`done: false` или отсутствие записи — это не «данных нет», а «этап не закрыт»:
`ask` печатает `WARN глубокий поиск не зафиксирован для <вход>`, в `--json`
ставит `deep_search_missing: true`, `validate` предупреждает по blocking-входу
без значения, без кандидатов и без записи `search`.

Секция `search` привязана к ИС так же, как `candidates`: в `CANDIDATES.yaml`
обязательны `is: <код>` и `schema_version: 1`. Если `is` не совпадает с
запрошенной ИС (или `schema_version` не 1), записи `search` отбрасываются с
`WARN` — скопированный из другой ИС `search.done: true` не глушит
предупреждение о незафиксированном tier 2. `validate` считает tier 2 закрытым
**только** при `done: true`; `done: false` и запись без `done` WARN не снимают.

## 6. Что делать после двух проходов

| Ситуация | Действие |
|----------|----------|
| tier 1 дал значение | записать кандидата с `source`, tier 2 не нужен |
| tier 1 пусто, tier 2 дал значение | записать кандидата, `search.done: true`, `result` — что нашлось |
| tier 1 и tier 2 пусто, **blocking** | `done: true`, `result: «не найдено — …»`, затем `make ask IS=...` — вопрос человеку. Догадку не вписывать |
| tier 1 и tier 2 пусто, **advisory** | то же, но вход не блокирует: паспорт будет неполным (`WARN`) |
| tier 2 дал основание без значения | кандидат `value: null`, `confidence: weak`, `done: true` |
| запрос упал (rate limit, ADF, таймаут) | это не «не найдено»: повторить по [failure-modes.md](failure-modes.md), `done` не ставить |

Значения `axes_scores` и `cia` из документов не выводятся: поиск по ним даёт
**основание** (кто оценивал, какие цифры ущерба упоминаются), а сами оценки —
экспертное решение TL/ИБ/финансов. Пустой tier 2 по этим входам — норма, но
запись `search` всё равно обязательна.

## 7. Что делать, если ничего не найдено

Поиск закрыт (`done: true`, `result: «не найдено — …»`), значения нет. Дальше —
вопрос человеку. Формулировки, нумерация и машинная форма вариантов живут в
[interactive.md](interactive.md) §«Как задавать вопросы» (`ask` / `ask-answers`);
здесь только **порядок применения**, без дубля:

| Вариант | Когда уместен | Что происходит с входом |
|---------|---------------|--------------------------|
| **Пропустить (waive)** | данных нет и человек осознанно отказывается их давать | `status: waived` + `waive {reason, decided_by, date, fallback}`; значение остаётся `null`, оценка становится предварительной с диапазоном (R17) |
| **Выбрать из кандидатов** | поиск дал одного или несколько кандидатов с `source` | выбранный кандидат становится значением, `status: confirmed`, провенанс кандидата сохраняется |
| **Дать ссылку** | человек знает страницу или дерево, но не помнит цифру | агент читает страницу, извлекает дословную цитату, значение пишется с `ref` на неё (R4) |
| **Свободный текст** | данные есть в переписке, презентации, на встрече | агент разбирает текст, фиксирует цитату как `source`, при отсутствии дословной формулировки — `manual` с ref на решение (`provenance.manual_decision`) |

Отдельный путь, если данных нет и взять их негде совсем: исключить ИС из расчёта
(`make exclude IS=<код> REASON="<причина>"`) — это не вариант ответа на вопрос
входа, а решение по ИС; см. [interactive.md](interactive.md).

## 8. Симптом → следующий запрос

| Симптом | Следующий запрос |
|---------|------------------|
| Код ИС в Confluence не находится вовсе | `"<название ИС>"`, затем CQL по функциональным областям продукта |
| Страница ИС есть, нужного раздела нет | дерево от **архитектуры ИС**: предки, дети, соседи, метки |
| В тексте «RTO 4 часа», а нужны минуты простоя | DR-страница + `"простой"`/`"недоступность"`; часы ≠ минуты, значение не подставлять |
| «SLA 99.9 %» без минут | DR/Support + `"допустимое время простоя"`; процент ≠ минуты |
| В Grafana панель трафика не находится | `grafana: namespace=<namespace>` по каждому шлюзу, затем заголовок дашборда по коду ИС |
| Панель есть, но окно 30d падает по таймауту | уменьшить разрешение подзапроса (`[30d:15m]`), а не отказываться от сбора |
| `confluence_get_page` вернул пустой `content.value` | `confluence_get_page_history(page_id, version)` — история отдаёт полный текст (ADF) |
| «Rate limit exceeded» | пауза, батч ≤ 10 страниц, повтор; `done` не ставить до результата |
| Норматив упомянут только в переписке | `"<логин>" and "<код ИС>"` по владельцам из `contacts` |
| Колонка «Сквозной бизнес-процесс (e2e)» в Product scope пуста | `label = "checkliste2e" AND text ~ "<код ИС>"`, затем `e2e-process-card` и реестр ИС `is_process_registry`; пустая колонка ≠ отсутствие процессов |
| В посте «потери GMV», но ИС не обслуживает заказы | проверить `financial_loss.applicability_check`; для внутренней ИС — `0 руб/час` с прецедентом, общесетевой GMV не подставлять |
| Ничего не найдено, вход blocking | `make ask IS=...` — вопрос с дословным enum и маршрутом «где взять» |

## 9. Запреты

- **Не выдавать основание за значение.** Цитата «RTO — часы» не заполняет
  `object_sla` в минутах: это кандидат-основание (`value: null`).
- **Не переносить значение с другой ИС.** «По аналогии с соседней ИС» — не
  источник (R1); такого запроса нет ни в tier 1, ни в tier 2.
- **Не ставить `done: true` без `deep`.** Пустой tier 2 при пустом tier 1 —
  это пропуск этапа, а не доказанное отсутствие данных.
- **Не сокращать список запросов до одного.** «Искал по коду — нет» не
  доказывает отсутствие: нужны маршрут входа из §3 и общие комбинации.
- **Не считать пустую колонку или шаблонный блок доказательством отсутствия** —
  это сигнал идти глубже (§4).
- **Не подставлять общесетевой GMV** (дашборд «GMV, AOV, Conversion») как
  потери ИС: он не атрибутируется ИС (`financial_loss.traps`).
- **Не сочинять заголовки страниц** — только из REST-ответа (§4).
- **Не искать в обход маршрутов.** Только Confluence, Grafana, GitLab и SSoT по
  карте [data-sources.md](data-sources.md); чужие системы и личные чаты — не
  источник.
