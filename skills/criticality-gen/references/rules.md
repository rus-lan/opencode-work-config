# Правила: criticality-gen

Правила жёсткие: каждое либо выполняется, либо останавливает работу. Проверка
у каждого правила — команда или наблюдаемый факт, а не «на глаз».

## R1. Факт-или-null

| Поле | Значение |
|------|----------|
| Правило | Любое значение без источника `{type, ref}` записывается как `null` со `status: missing`. Формулировки «примерно», «обычно», «скорее всего», «около» запрещены. |
| Зачем | Паспорт критичности — вход в процесс D6.1.1. Оценка «на глаз» превращает защитный документ в фикцию и обнуляет смысл гейта. |
| Как проверить | `grep -nE "примерно\|обычно\|скорее всего\|около\|порядка" is/*/INFORMATION.yaml` — пусто; у каждого непустого `criteria_inputs.*.value` есть `source: {type, ref}`. |
| Что делать при нарушении | Удалить значение, поставить `value: null` и `status: missing`, добавить поле в отчёт «чего не хватает» и назвать адресата (TL / PdM / SRE / ИБ). |

**Решение владельца — тоже источник, но не цитата.** Если дословной цитаты в
источнике нет, а владелец (PdM) решение принял, значение записывается как:

```yaml
outage_impact:
  value: "<значение из enum>"
  status: confirmed
  source:
    type: manual
    ref: "решение PdM, 2026-11-17; INFORMATION.yaml#notes"
```

Само решение (кто, когда, что решил, почему) — в `INFORMATION.yaml#notes`.
Новый тип провенанса для этого не изобретается: используется существующий
`manual`, правило зафиксировано в
`criteria/criticality-criteria.yaml → provenance.manual_decision`. Пересказ
источника, «по аналогии с другой ИС» и «обычно так» решением владельца не
являются — это R1-нарушение. Проверка: у каждого `type: manual` в `ref` есть
дата и ссылка на `notes`, а в `notes` — соответствующая запись.

## R2. Только шаблон

| Поле | Значение |
|------|----------|
| Правило | Артефакт создаётся исключительно рендером файла из `templates/`. Ручная правка сгенерированного файла запрещена: изменения вносятся в `INFORMATION.yaml` (факт) или `criteria/criticality-criteria.yaml` (правило), затем повторный `start`. |
| Зачем | Иначе следующий прогон затрёт ручную правку, а провенанс значения потеряется. |
| Как проверить | Шапка каждого сгенерированного файла содержит пометку «сгенерировано, руками не править»; `make start IS=erm.mm DIFF=1` после ручной правки показывает непустой diff. |
| Что делать при нарушении | Откатить ручную правку (`git checkout -- criticality-passport.yaml`), перенести изменение в источник, перегенерировать: `make start-apply IS=erm.mm FORCE=1`. |

## R3. Гейт

| Поле | Значение |
|------|----------|
| Правило | `check` (strict по умолчанию) обязателен перед `start`. Сценарий выбирается по данным: непустой любой вход только сложного набора → сложный сценарий, иначе простой. При нехватке blocking-входа выбранного сценария или значении вне допустимого множества — стоп с перечнем «чего нет / где взять»; неполный сложный набор — `BLOCKED` без фолбэка на простой сценарий; входы вне blocking-набора сценария не блокируют. |
| Зачем | Расчёт по неполному набору даёт число, которое нельзя защитить; лучше явный `BLOCKED`, чем красивый паспорт с дырой. |
| Как проверить | `make check` → код 0 и `готовы к расчёту: N` (strict по умолчанию); `make check-diag` — только для отладки. Для каждой ИС в `start` статус `OK`, а не `BLOCKED`. |
| Что делать при нарушении | Остановиться. Вернуть таблицу гейта, список отсутствующих `id`, `source_hint` из `criteria/criticality-criteria.yaml` и адресата. `start` не запускать. |

## R4. Провенанс

| Поле | Значение |
|------|----------|
| Правило | У каждого входа `criteria_inputs.*.source` = `{type, ref}`; `type ∈ ssot \| is_yaml_override \| catalog \| confluence \| gitlab \| jira \| grafana \| attachment \| ssot_links \| manual`. |
| Зачем | Без типа и ссылки значение нельзя ни проверить, ни переоценить, ни защитить на ревью. |
| Как проверить | `make start IS=erm.mm DIFF=1` → раздел «Входы с провенансом» в `GENERATION.md` не содержит пустых `source`; `type` входит в перечисление. |
| Что делать при нарушении | Дополнить `source`, указав точный `ref` (путь в `ssot/`, `page_id`, URL MR, `is.yaml#is.erm.mm`). Нет источника — вернуться к R1. |

## R5. Конвенции помечаются

| Поле | Значение |
|------|----------|
| Правило | Правило, не подтверждённое документом, получает `kind: convention` + `status: needs_validation`; в артефакте оно перечисляется в §7 `CRITICALITY.md` и в `GENERATION.md`. Выдавать конвенцию за документированное правило запрещено. |
| Зачем | Часть методики (например, экспресс-оценка) восстановлена по косвенным данным. Скрытая конвенция выглядит как канон и тиражируется. |
| Как проверить | `make criteria` → у каждого правила есть `kind`; `make start ... DIFF=1` → раздел «Conventions» в `GENERATION.md` непуст, если в критериях есть `kind: convention`. |
| Что делать при нарушении | Проставить `kind: convention` и `status: needs_validation` в файле критериев, добавить правило в §7 и в `GENERATION.md`, вынести вопрос владельцу методики. |

## R6. Расхождения не разрешаются молча

| Поле | Значение |
|------|----------|
| Правило | При конфликте SSoT ↔ расчёт ↔ dochub — запись в `conflicts`; оба значения остаются в артефакте, статус «требует подтверждения». Автоматический выбор одного значения запрещён. |
| Зачем | Молчаливое «поправил под расчёт» уничтожает след: на переоценке никто не поймёт, откуда взялось расхождение. |
| Как проверить | `make start IS=erm.mm DIFF=1` → раздел «Расхождения с реестром» в `GENERATION.md`; `make validate` → WARN `CONFLICT` (не ERROR); `conflicts` в `INFORMATION.yaml` непуст при расхождении. |
| Что делать при нарушении | Добавить запись `{field, values, chosen, rule, status: needs_confirmation}`, оставить оба значения, назначить подтверждающего (TL или SRE). |

## R7. Детерминизм

| Поле | Значение |
|------|----------|
| Правило | Одинаковые входы + одинаковая `--date` → побайтово одинаковые артефакты. Случайные значения и даты вне `meta` запрещены. |
| Зачем | Паспорт должен воспроизводиться на ревью и в CI; иначе diff перестаёт быть сигналом. |
| Как проверить | `make start IS=erm.mm DATE=2026-11-11 FORCE=1` дважды → `sha1sum` совпадает, `git diff` пуст; в шаблонах нет `now()` и текущей даты. |
| Что делать при нарушении | Найти источник недетерминизма (дата, порядок словаря, случайный id), вынести дату в `--date`, отсортировать коллекции, повторить проверку. |

## R8. Безопасная запись

| Поле | Значение |
|------|----------|
| Правило | Без `--force` существующие `criticality-passport.yaml` и `CRITICALITY.md` не перезаписываются. Сначала `--dry-run` (или `--diff`), затем запись. |
| Зачем | Паспорт — документ с подтверждением SRE. Тихая перезапись стирает подпись и историю. |
| Как проверить | `make start IS=erm.mm DIFF=1` → «DRY-RUN: файлы не записаны»; `make start-apply IS=erm.mm` без `FORCE=1` → файлы пропущены с сообщением. |
| Что делать при нарушении | Откатить из git, проверить `git log` по файлу, восстановить подтверждение; впредь использовать `DIFF=1` перед `start-apply`. |

## R9. Внешние действия — только по флагу и подтверждению

| Поле | Значение |
|------|----------|
| Правило | Jira / Confluence / сообщения создаются только при `--create-task` / `--create-confluence` / `--create-message` и явном подтверждении человека. Без флага создаётся action-пакет с инструкцией. |
| Зачем | Внешняя запись необратима и видна другим командам; скилл не должен создавать задачи и страницы «за компанию». |
| Как проверить | `make start-apply IS=erm.mm` без флагов → в `actions/` лежат инструкции, внешних объектов нет; с флагом — есть ссылка/ключ в `GENERATION.md`. |
| Что делать при нарушении | Остановиться, показать, что будет создано (проект, заголовок, получатели), запросить подтверждение; при сомнении — action-пакет. |

## R10. Остановка вместо догадки

| Поле | Значение |
|------|----------|
| Правило | Если данных нет и источник неизвестен — скилл останавливается и перечисляет точный список полей и адресатов (TL / PdM / SRE / ИБ). Продолжение с частичным набором запрещено. |
| Зачем | Единственный способ получить данные — запрос конкретному человеку. «Продолжу и потом уточню» гарантирует, что не уточнят. |
| Как проверить | Отчёт после `BLOCKED` содержит: `id` поля, `description`, `source_hint`, роль-адресата. Нет общих формулировок «нужно больше данных». |
| Что делать при нарушении | Переписать отчёт по форме «поле → что это → где взять → у кого», остановить конвейер, зафиксировать блокировку в `GENERATION.md` (если он создан) или в ответе пользователю. |

## R11. Остановка с файлом требований

| Поле | Значение |
|------|----------|
| Правило | При `BLOCKED` создаётся `DATA-REQUIREMENTS.md` и `DATA-REQUIREMENTS.yaml`: каждый незакрытый вход с полями «что это → зачем → где взять → у кого → как подтвердить» и готовым фрагментом для `INFORMATION.yaml`. Заполненный лист принимается только с `value`, `source: {type, ref}` и `status: confirmed`; иначе `enrich` завершается ошибкой и `INFORMATION.yaml` не меняется. Данных нет совсем — ИС исключается (`excluded: true` + `reason` в `catalog.yaml` для общего решения или в `is.yaml` локально, вердикт `SKIPPED` с источником), а не заполняется догадкой. |
| Зачем | Отчёт «чего не хватает» в консоли теряется; файл уходит адресату и возвращается заполненным. Гейт на входе `enrich` не даёт протащить значение без источника. |
| Как проверить | `make check` → для каждой `BLOCKED` ИС есть `is/CODE/DATA-REQUIREMENTS.md` и `.yaml`; `make requirements IS=...` без `APPLY=1` ничего не пишет; `make enrich IS=...` на пустом листе → «принято 0» и `sha1sum INFORMATION.yaml` не меняется; лист без `source` → ошибка. |
| Что делать при нарушении | Перегенерировать лист (`make requirements IS=... APPLY=1`), передать адресатам из колонки «у кого», заполненный лист прогнать через `make enrich-apply IS=...`; если источник данных отсутствует — `make exclude IS=... REASON="..."`. |

## R12. Клоны сервисов — только чтение

| Поле | Значение |
|------|----------|
| Правило | Внутри `apps/` разрешён только `git` (`clone`, `checkout`, `pull`, `rev-parse`). Сборка, тесты, установка зависимостей, миграции и запуск любых скриптов из клонированного репозитория запрещены. `services` читает файлы и не исполняет код сервиса. |
| Зачем | Клон — чужой репозиторий в неизвестном состоянии: сборка тянет зависимости и сеть, тесты пишут в файловую систему и внешние сервисы, скрипты деплоя могут что-то изменить. Этап нужен для документации, а не для проверки работоспособности. |
| Как проверить | `make services IS=...` не запускает ни одного процесса, кроме `git` (проверка `_git_only` падает до запуска при любой другой команде); в `SERVICE-FINDINGS.md` §8 напечатано ограничение; `git -C apps/IS/COMPONENT status --porcelain` пуст (рабочее дерево клона не менялось). |
| Что делать при нарушении | Остановиться, откатить изменения в клоне (`git -C ... checkout -- .`), убрать сборку из сценария; при необходимости пересоздать клон `make prepare-apply`. |

## R13. Сценарий выбирается по данным

| Поле | Значение |
|------|----------|
| Правило | Сценариев два: простой (экспресс-оценка по четырём входам) и сложный (детальная оценка по всем `inputs.required`). Сценарий определяется данными: непустой любой вход только сложного набора → сложный; неполный сложный набор — `BLOCKED` с перечнем недостающих; фолбэк на простой сценарий запрещён. Флагом сценарий не переключается. |
| Зачем | Иначе частичная детальная оценка выдаётся за полную или наоборот: простой сценарий по данным с детальными входами даёт число, которое нельзя защитить. |
| Как проверить | `make check` → колонка `сценарий`; шапка таблицы печатает blocking-наборы обоих сценариев; `make selftest` → проверки `scenario_of`, `blocking_inputs`, «неполный сложный → BLOCKED». |
| Что делать при нарушении | Не переключать сценарий вручную: добрать входы сложного сценария (`DATA-REQUIREMENTS.*`) или осознанно очистить сложный набор целиком — только тогда простой сценарий законен. |

## R14. Код — основание, а не значение

| Поле | Значение |
|------|----------|
| Правило | Порядок источников документации: клон (`docs/`, `openspec/`) → Confluence → SSoT. Из кода берётся основание с цитатой «файл:строка»; значение входа подтверждает человек через `enrich`. `SERVICE-FINDINGS.md` не пишет в `INFORMATION.yaml`. Отсутствие `docs/`, `openspec/` или норматива фиксируется в §7 отчёта, а не замалчивается. |
| Зачем | Комментарий в коде — не подтверждённый норматив: он может быть устаревшим, относиться к другому контуру или к тестовой заглушке. Значение без подтверждения — это `null` (R1). |
| Как проверить | В `SERVICE-FINDINGS.md` у каждой строки §3–§6 есть `файл:строка` и дословная цитата; §7 перечисляет отсутствующее; `sha1sum is/IS/INFORMATION.yaml` после `make services-apply` не меняется. |
| Что делать при нарушении | Убрать значение из `INFORMATION.yaml`, оставить цитату как основание в отчёте, запросить подтверждение у владельца (SRE / TL / PdM) и провести его через `enrich`. |

## R15. Закрытые сервисы не клонируются

| Поле | Значение |
|------|----------|
| Правило | Сервисы с `lifecycle: closed` (`criteria.service_lifecycle.skip`) не клонируются, не анализируются и не служат источником оснований (`service_lifecycle.evidence_rule`). Фильтр применяется в `prepare` (клонирование) и `services` (анализ); пропущенные попадают в раздел «Пропущенные сервисы» отчёта. Компонент без `lifecycle` — не пропуск: он анализируется, а в отчёт идёт строка `lifecycle не указан`. |
| Зачем | Закрытый сервис выведен из эксплуатации и не участвует в функционировании ИС: его документация и нормативы описывают прошлое состояние. Основание из закрытого сервиса ведёт к неверному входу критичности. |
| Как проверить | `make services IS=...` печатает `skip (lifecycle: closed)` и `пропущено (lifecycle): N`; в frontmatter `SERVICE-FINDINGS.md` `services_skipped` совпадает с числом компонентов `closed`; `make criteria-check` печатает строку `service_lifecycle`; `make selftest` — проверки `_component_skipped`. |
| Что делать при нарушении | Убрать закрытый сервис из анализа и из таблицы «вход → основание»; основание искать в активном сервисе, Confluence или Grafana; перегенерировать отчёт `make services-apply IS=...`. |

## R16. Язык: только русский

| Поле | Значение |
|------|----------|
| Правило | Скилл работает на русском языке: артефакты, вопросы, сообщения CLI и тексты ошибок — русские. Ответы пользователя принимаются только на русском. Значения enum берутся дословно из `criteria/criticality-criteria.yaml` (они русские); свободный текст (`source.ref`, `notes`, `reason`, `conflicts`) — тоже на русском. |
| Исключения (латиница допустима) | Идентификаторы и машинные значения: логины, URL, `page_id`, uid дашбордов/датасорсов, PromQL-выражения, ключи Jira/MR, имена файлов/сервисов/компонентов, значения enum, приходящие из внешних систем (например `business-critical` из SSoT), кодовые имена полей. |
| Зачем | Скилл — русскоязычный процесс D6.1.1: артефакт с прозой на другом языке нельзя защитить на ревью, а смешанный язык ломает единый словарь предметной области. Проверка мягкая, потому что язык — это качество текста, а не отсутствие факта. |
| Как проверить | `make validate` и `make enrich IS=...` предупреждают (`WARN`, не блокируют), если свободный текст в русскоязычном поле не содержит ни одной кириллической буквы, но содержит латинские слова — то есть поле заполнено прозой на другом языке. Идентификаторы и машинные ссылки не проверяются (`_prose_language_problem`). `make selftest` — проверки `R16`. |
| Что делать при нарушении | `WARN` в выводе с указанием поля и значения; значение **не отбрасывается** (это предупреждение о языке, а не о факте). Если ответ пользователя пришёл не на русском — агент переспрашивает на русском, а не переводит молча. |

## R17. Отказ от данных — записанный и предварительный

| Поле | Значение |
|------|----------|
| Правило | Если данных нет и человек осознанно отказывается их давать, это не `deferred`-пропуск и не `null`-дыра: вход закрывается `status: waived` с блоком `waive {reason, decided_by, date, fallback}`. `reason` — проверяемая причина (>= 10 символов), `fallback.mode` — `assume_worst` \| `assume_best` \| `assume_value` (у `assume_value` обязателен `fallback.value`). У waived-входа **не может быть значения**: `value: null` обязателен. Гейт считает такой вход закрытым и возвращает `provisional: true`; расчёт перебирает домен допустимых значений входа и печатает **диапазон** уровней, а в паспорт идёт уровень по режиму допущения (`assume_worst` → максимум, иначе минимум). Домен перечисляется полностью: у чисел — пороги, границы интервалов и оба предела (0 и +∞), у составных (`axes_scores`, `cia`) — все наборы (5⁴ и 3³). `CRITICALITY.md` получает блок «⚠ Оценка предварительная» (причина, допущение, диапазон; при `min == max` — «вход не влияет на уровень выбранного метода»), `GENERATION.md` — строку «Предварительная оценка», `INDEX.md` — пометку `(предв.)`, публикация — строку о предварительности. **Диапазон пересчитывается при каждом прогоне**: после подтверждения/удаления отказа пометка `(предв.)` и уровень паспорта обязаны исчезнуть/совпасть с новой оценкой. Домен не перечислим (свободный текст, ссылка, неизвестный enum) — `ERROR`, а не догадка. |
| Зачем | Отказ — законное решение человека, но он не превращает оценку в подтверждённую. Без записи причина и допущение теряются, а «Mission critical» из отказа читается как факт. Без диапазона оценка снова выглядит одним числом. Устаревшая пометка `(предв.)` или уровень паспорта от прошлого отказа так же вредны, как её отсутствие: артефакт перестаёт соответствовать данным. |
| Как проверить | `make validate` — `status: waived` без `reason`/`fallback.mode` = `ERROR`; `value` при `status: waived` = `ERROR`; waived-вход без пометки «⚠ Оценка предварительная» в `CRITICALITY.md` = `ERROR`; **пометка есть, а waived-входов нет** = `ERROR` («остался блок предварительной оценки»); **уровень паспорта ≠ текущей предварительной оценке** = `ERROR` с обоими значениями; исключённые из расчёта ИС пропускаются. `make score` печатает «Оценка предварительная», диапазон и «в паспорт записан»; `make start` — `WARN` и `(предв.)` в `INDEX.md`. `make selftest` — проверки `R17`. |
| Что делать при нарушении | Дописать `waive.reason`/`waive.fallback` (или подтвердить значение с `source` + `status: confirmed`), перегенерировать артефакты: `make start-apply IS=<код> FORCE=1`, затем `make index`. Выдавать отказ за подтверждённое значение запрещено. |

## R18. Внешние изменения — только после зелёной валидации

| Поле | Значение |
|------|----------|
| Правило | Порядок цикла жёсткий: исследование → заполнение критериев → расчёт → валидация ВСЕХ результатов → внешние изменения (MR в dochub и SSoT) → тред согласования. `publish` / `publish-apply` / `ssot` / `ssot-apply` отказывают (код ≠ 0), если `validate` по ИС даёт ERROR, `criteria_fingerprint` артефактов не совпадает с текущими критериями или в паспорте/`INFORMATION.yaml` остались незакрытые blocking-входы. Текст сообщения с `⛔ не заполнено` не переводится в статус `requested`: action-пакет остаётся `pending_manual` и печатает список незаполненных полей. Обход гейта — только `--force` (`FORCE=1`): печатает `WARN`, называет причину и пишет строку в `is/<код>/.gate-overrides.log`. |
| Зачем | Внешняя ветка и MR живут дольше локального прогона и видны другим командам: паспорт, посчитанный по старым критериям или с незакрытыми входами, читается как действующий. Тред с `⛔` в тексте выглядит как готовый к согласованию, хотя данных в нём нет. |
| Как проверить | `make publish IS=<код> TASK=<key>` при ERROR в `validate` → код 1 и `ERROR: publish … заблокирован`; при расхождении фингерпринта → причина `criteria_fingerprint не совпадает` и шаг `make start-apply IS=<код> FORCE=1`; `make publish … FORCE=1` → `WARN` + строка в `is/<код>/.gate-overrides.log`; `make start-apply IS=<код> FORCE=1 MESSAGE=1` при `⛔` в тексте → статус в `actions/rocketchat-message.md` остаётся `pending_manual` и напечатано «отправка заблокирована: N незаполненных полей». `make selftest` — проверки `G1–G6`. |
| Что делать при нарушении | Остановиться и закрыть причину, названную гейтом: исправить ERROR (`make validate`), перегенерировать артефакты (`make start-apply IS=<код> FORCE=1`), добрать blocking-входы (`make check IS=<код>` → `make enrich-apply IS=<код>`), заполнить поля сообщения. `--force` — только осознанно и с записью причины в лог; выдавать обход за зелёный прогон запрещено. |

## R19. Заголовки страниц — только из проверенного кеша

| Поле | Значение |
|------|----------|
| Правило | Заголовок страницы Confluence печатается **только** из проверенного кеша: `catalog.yaml → page_titles.<page_id>` (`title` + `title_version` + `title_verified_at`). Кеш наполняет `make verify-titles FIX=1` — он же приводит к фактическим заголовкам объявления в `criteria.external_refs.refs[]` и `criteria.meta.sources[]`. Выдуманное или «восстановленное по контексту» название — дефект уровня публикации, а не опечатка: ссылка в паспорте и в треде ведёт на документ, которого нет. Нет записи в кеше — рендерится `[page <id>] <url>` без названия (так честнее, чем красивый неверный заголовок). |
| Зачем | Заголовок — часть провенанса (R4): по нему человек находит источник. Переименованная или угаданная страница делает провенанс ложным, а гейт публикации (`validate` → `verify-titles`) — бессмысленным: проверить нечего, если название не сверялось с REST. |
| Как проверить | `make verify-titles` — `расхождений 0, без зафиксированного title 0, устаревших в источнике 0`; `make verify-titles FIX=1` — запись кеша и объявлений; `make validate` — гейт `_check_page_titles`: ERROR при отсутствии записи кеша, отсутствии `title_verified_at`, версии страницы новее проверенной или расхождении заголовка. `make verify` включает `verify-titles` в общий прогон. |
| Что делать при нарушении | `make verify-titles FIX=1` (нужен `CONFLUENCE_TOKEN`) и повторить `make start-apply IS=<код> FORCE=1` → `make validate`. Вписывать заголовок руками в шаблон, критерии или `INFORMATION.yaml` запрещено: рендер читает только кеш. |

## Запреты

- Подставлять значения по умолчанию вместо отсутствующих входов.
- Писать в `ssot/` и в `apps/` (это клоны, только чтение и `git pull`).
- Собирать, тестировать и запускать что-либо из клонов `apps/` (R12).
- Мержить MR, пушить в dochub, менять SSoT-карточку из скилла.
- Отправлять сообщения в чат без MCP и без подтверждения.
- Выдавать `kind: convention` за `kind: documented`.
- Запускать `start` при `BLOCKED` гейте.
- Вписывать в `INFORMATION.yaml` значение без `source: {type, ref}` и `status: confirmed` (обходить `enrich`).
- Выдавать цитату из клона за подтверждённое значение входа (R14).
- Выдавать `status: waived` за подтверждённое значение или скрывать
  предварительность оценки: диапазон и пометка обязательны (R17).
- Клонировать, анализировать или брать основание из сервиса с `lifecycle: closed` (R15).
- Формировать MR в dochub/SSoT до зелёной валидации всех артефактов (R18).
- Печатать заголовок страницы не из проверенного кеша — из памяти, шаблона или
  «по контексту» (R19).
- Переводить action-пакет сообщения в `requested`, пока в тексте есть `⛔ не заполнено` (R18).
- Править `DATA-REQUIREMENTS.md`/`.yaml` вручную: лист перегенерируется.
- Править `criteria/criticality-criteria.yaml` под конкретную ИС.
- Округлять, пересчитывать или «улучшать» числа, пришедшие из источника.

## Провенанс

- Каждое значение — с источником `{type, ref}`; `type` из перечисления R4.
- `ref` — конкретный адрес: путь в `ssot/`, `page_id` Confluence, URL MR,
  `is.yaml#is.erm.mm`, логин автора для `manual`.
- Производные значения (`derived`) допустимы, но требуют подтверждения
  владельцем и явной пометки в артефакте.
- Значение без источника не существует: оно не попадает в артефакт.

## Детерминизм

- Единственная дата в артефактах — `--date` (по умолчанию дата прогона);
  других источников времени нет.
- Коллекции выводятся в стабильном порядке (порядок файла-источника либо
  сортировка), случайные идентификаторы не генерируются.
- Проверка: два прогона с одной `--date` → одинаковый `sha1sum`, пустой `git diff`.

## Обработка нехватки данных

| Чего нет | Поведение |
|----------|-----------|
| `INFORMATION.yaml` | `BLOCKED`: «соберите `make prepare-apply`» |
| blocking-вход выбранного сценария (`scenarios.<сценарий>.inputs`) | `BLOCKED` + `DATA-REQUIREMENTS.*` со списком `id`, `source_hint` и адресатов (R11) |
| неполный сложный набор | `BLOCKED`: фолбэк на простой сценарий не применяется; простой сценарий возможен лишь при полностью пустом сложном наборе и со `status: preliminary` (R13) |
| вход вне blocking-набора сценария | `WARN` «не заполнено, требуется для полноты паспорта»; вердикт не меняется |
| в клоне сервиса нет `docs/`, `openspec/` или норматива | запись в `SERVICE-FINDINGS.md` §7 «Не найдено»; значение берётся из Confluence/Grafana или остаётся `missing` (R14) |
| сервис ИС не клонируется | `clone_error` в `SERVICE-FINDINGS.md`, остальные сервисы анализируются; доступ запрашивается у владельца репозитория |
| у сервиса `lifecycle: closed` | не клонируется и не анализируется, попадает в §2 «Пропущенные сервисы»; основание ищется в активном сервисе, Confluence или Grafana (R15) |
| источник значения неизвестен | `null` + `status: missing`, вопрос адресату (R10); вход попадает в `DATA-REQUIREMENTS.*` (R11) |
| данных нет и взять негде | `excluded: true` + `reason` в `catalog.yaml` (общее) или `is.yaml` (локально), вердикт `SKIPPED` — не выдуманное значение |
| расхождение SSoT ↔ расчёт | `conflicts` + «требует подтверждения» (R6) |

При нехватке данных скилл останавливается и возвращает: список отсутствующих
полей, требуемый источник и адресата — TL (архитектура и зависимости), PdM
(влияние на клиента и продукт), SRE (SLA, инфраструктура, дежурства), ИБ
(классификация данных, CIA).
