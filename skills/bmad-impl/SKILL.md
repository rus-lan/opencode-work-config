# BMAD Impl — планирование реализации для opencode

Invocation: `/bmad-impl <task> [--phase <name>]`

- `<task>` — описание задачи, PRD или ссылка на spec-файл
- `--phase` — имя фазы (если не указано, генерируется из заголовка)

## Когда использовать

- Задача на 3+ файла в разных слоях (frontend + backend + БД)
- Задача требующая миграций данных
- Задача с архитектурными решениями
- Когда пользователь говорит "это слишком большая задача для одной сессии"

## Конвейер подготовки

### Шаг 1: Kickoff
Создать `<project>/.bmad/KICKOFF-<фаза>.md`:

```markdown
# KICKOFF: <фаза>

## Скоуп-контракт
<что делаем, границы, что НЕ делаем>

## Зависимости
<на каком коде строится, что должно быть готово>

## Применимые правила
<ссылки на .claude/rules/* по стеку>

## План декомпозиции
- Эпик 1: <название>
- Эпик 2: <название>
- ...
```

### Шаг 2: Эпики → Истории
Создать `<project>/.bmad/epics-<фаза>.md` с таблицей:

```markdown
# Эпики: <фаза>

## Эпик 1: <название>
- [ ] История 1.1: <описание> [класс: обычная]
- [ ] История 1.2: <описание> [класс: CR-обязателен]
- ...

## Эпик 2: <название>
- ...
```

### Шаг 3: Ревью по классу истории

| Класс | Ревью | Когда |
|-------|-------|-------|
| **Обычная** | Self-review — dev-сессия перечитывает дифф | Большинство историй |
| **CR-обязателен** | Полный code review через reviewer-* сабагентов | Деньги/секреты/БД/security/публичные контракты |

**CR-обязателен**, если история трогает хотя бы одно из:
- Деньги: балансы, цены, списания
- Секреты/ключи/шифрование/custody
- Схему БД / миграции
- Публичные контракты: proto, REST API, enum ошибок
- Security-инварианты (fail-closed, allowlist)
- Расчётные числа, которые фронт не должен пересчитывать

### Шаг 4: Readiness
Перед стартом первого спринта проверить:
- [ ] Скоуп-контракт покрыт эпиками (coverage map)
- [ ] Каждая история имеет acceptance criteria
- [ ] Нет скрытых зависимостей между эпиками
- [ ] Определён порядок (какой эпик первый)

### Шаг 5: Спринт
1. Открыть первый эпик
2. Для каждой истории: `bmad-dev-story` → ревью по классу → отметка
3. После завершения эпика: проверить, что acceptance criteria выполнены
4. Перейти к следующему эпику

## Принципы

- **Канарейка**: первая история эпика — узкий срез (1 экран / 1 endpoint)
- **Батчинг**: 2-3 мелкие связанные истории — одной dev-сессией
- **Fail-closed**: безопасность зашивать при первой реализации, не "потом"
- **Одна история = один файл** (макс 2, если тесно связаны)
- **Коммит** — только по явному разрешению пользователя

## Антипаттерны

- Не распараллеливать эпики на общей кодовой базе
- Не начинать эпик 2 до завершения эпика 1, если эпик 2 строит на коде эпика 1
- Не закрывать историю на красных тестах
- Не пропускать CR для опасных историй

## Ограничения

- BMAD — для задач на 2+ сессии. Для задач на одну сессию используй `/build`
- Не генерировать фазы "на вырост" — только то, что нужно сейчас
- BMAD-файлы живут в `.bmad/` в корне проекта
