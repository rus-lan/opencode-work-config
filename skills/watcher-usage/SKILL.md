# watcher-usage

## 1. Назначение

Этот скилл описывает, как агент работает с **watcher** — общей базой фактов:
сохранять проверенные знания и находить их между сессиями. Скилл покрывает
**и ведение** базы (когда сохранять, как оформлять, чувствительность,
защиты), **и использование** (поиск по CLI и MCP, получение полного текста,
экспорт).

watcher **не привязан к информационным системам**. Факты могут быть о чём
угодно: сервисы и инфраструктура — лишь один из доменов; также это
договорённости, решения, люди, процессы, команды, инструменты. Любой
проверенный тезис, который пригодится в будущих сессиях, — кандидат на
сохранение.

Пользователь может называть watcher по-разному: «база фактов», «наша
память/база знаний», иногда с опечатками («память Watson» вместо watcher).
Распознавайте такие обращения по смыслу и работайте с watcher, не
переспрашивая.

## 2. Что такое watcher

- **База**: локальный SQLite (`~/memory/watcher.db`), конфиг
  `~/.config/watcher/config.toml` (встроенный в бинарь как дефолт).
- **Поиск**: гибридный скоринг — BM25 + три-граммы + векторный слой
  (`multilingual-e5-base`, 768 dims, опционален) + recency + backlinks (граф
  `[[wikilinks]]`), объединение RRF.
- **Поверхности**: CLI `watcher` (все команды) и MCP-сервер `watcher-mcp`
  (stdio, три тула: `watcher_save`, `watcher_search`, `watcher_get`; у
  search/get — `format: text|json`, у search — `explain`).
- **Экспорт**: `watcher export` — OKF-бандл в git (shareable-факты, сканер
  секретов gitleaks, карантин); `watcher compile` — Markdown-вики для
  Obsidian; `watcher backup` — снапшоты БД с ротацией.

## 3. Правила ведения базы фактов

Факт = **один проверяемый тезис** об объекте/предмете. Сохраняйте только
выжившие результаты: то, что уже подтвердилось в работе и важно для будущих
сессий.

### Когда сохранять

- итоги рабочей сессии: найденные факты, решения, договорённости, сломанное
  и починенное;
- стабильные знания: адреса/эндпоинты, архитектура, роли людей, процессы,
  правила;
- runbook-знания: «как разбирать X», типовые причины, ссылки на инструкции.

### Когда НЕ сохранять

- **секреты**: токены, пароли, ключи — в любом виде (см. также deny ниже);
- **одноразовый контекст**: текущий вопрос, промежуточные выкладки, всё, что
  не нужно через неделю;
- **конфиденциальное** (персональные данные, коммерческая тайна) — или только
  с `sensitivity: private`, если без этого никак;
- мелочи и очевидности.

### Формат факта

- `title` — короткий однозначный заголовок-идентификатор; при наличии
  связанных сущностей — `[[wikilinks]]` на их title (ссылки создают граф и
  участвуют в ранжировании).
- `body` — один тезис, самодостаточный текст (не «см. выше»), без
  дублирования title.
- `kind` — тип факта: `service | metric | log | infra | runbook | fact`
  (для всего, что не является сервисом/метрикой/логом/инфраструктурой/
  runbook'ом, — `fact`).

### Чувствительность (sensitivity)

- `private` — личное/узкое, не для шаринга (по умолчанию, если не указано),
- `internal` — внутреннее для команды/организации,
- `shareable` — можно экспортировать (`watcher export` берёт только такие).

Выбирайте самый строгий из уместных уровней. По умолчанию — `private`.

### Параметризация идентификаторов

**Не сохраняйте как есть** подстановочные пользовательские идентификаторы:
pod-хеши, trace-id, user-id, конкретные инстансы. Для `kind: metric|log`
пишите параметризованно: `{pod="$pod"}`, `{trace_id="<id>"}` вместо реальных
значений. Реальные имена сервисов/топиков/кластеров — можно; реальные
конкретные id пода/трейса — нельзя.

Если в факте одноразовых идентификаторов нет (имена метрик уже
параметризованы/обобщены) — «параметризовать нечего», и это нормальный
ответ: проверьте тело и честно скажите об этом, не выдумывайте
плейсхолдеры.

### Deny-паттерны

`watcher_save` **отклоняет** `shareable`-факты с секретными паттернами —
английские и русские термины секретности (`password|пароль|secret|секрет|
token|токен|логин|api[_-]?key|bearer`), приватные сети (10.x/172.16–172.31/
192.168), `customer_*` и т.п. (актуальный список — `[export.deny].patterns`
в `tools/watcher/config.toml`). Это защита, **не** приглашение к обходу: не
пытайтесь «переформулировать так, чтобы прошло» — либо понизьте sensitivity
до `internal`/`private` (это честно отражает природу факта), либо не
сохраняйте.

### Не дублировать

Перед сохранением сделайте быстрый `watcher search` по теме: если факт уже
есть — обновите его (пересохраните с тем же title) либо не сохраняйте.
Дубли заголовков — известное ограничение поиска, избегайте их.

## 4. Поиск и использование

### CLI

```sh
watcher search "лаг kafka ticket-system"        # гибридный поиск
watcher search "kafka" --explain                # why-строка: вклад слоёв
watcher search "kafka" --json                   # машинный контракт
watcher get <id>                                # полный текст факта
watcher entity <имя>                            # факты по сущности + co-occurring
```

Лайфхак: ищите и терминами (bm25+триграммы), и перефразировкой (векторный
слой). Если ничего не нашлось — попробуйте синонимы/словоформы
(«тикеты»→«ticket», «бэкап»→«backup»), не уступает встроенный словарь.
«Нет хитов» — не равно «в базе этого нет»: прогоните несколько формулировок
(термин / синоним / перефразировка / `watcher entity <имя>`), и только
потом делайте вывод и честно говорите его пользователю.

### MCP (watcher-mcp)

Дозированная выдача: сначала `watcher_search` → получите id/превью, затем
`watcher_get` по одному id, **не читая тела заранее** (для `kind=metric|log`
— параметризованные лейблы, см. §3). `watcher_save` — сохранение с
`kind`/`sensitivity`.

### Ответ пользователю

Отвечая по найденным фактам, цитируйте источник (title + id) и не
домысливайте: чего в базе нет — так и говорите. Если факты противоречат
друг другу — покажите оба и отметьте конфликт (можно завести новый факт с
пометкой).

## 5. Чек-листы сценариев

**Конец сессии (подведение итогов):**
1. Соберите выжившие факты (что узнали/решили/сломали/починили).
2. Для каждого: title + body + kind + sensitivity (`internal` — разумный
   дефолт для рабочих итогов; `shareable` — только если это можно
   экспортировать).
3. Быстрый search на дубли → сохранение (CLI или `watcher_save`).

**«Что мы знаем о X?»:**
1. `watcher search "X"` (+ варианты формулировок).
2. `watcher get` топ-хитов.
3. Ответ с цитатами (title + id, ключевые факты), честно про пробелы.

**Разбор инцидента:**
1. Ищите похожие runbook/факты (`runbook` kind, «инцидент», имя сервиса).
2. Следуйте найденному runbook'у; по завершении сохраните выводы новым
   фактом (что случилось, причина, фикс) — это пополняет базу.
3. Честно отметьте, чего в базе не хватает для полного разбора (нет
   runbook'а по сценарию, нет фактов про метрики и т.п.) — и скажите это
   пользователю, не додумывайте недостающее.

**Экспорт (если пользователь просит):** shareable-факты уходят в git через
`watcher export` (OKF-бандл, gitleaks-сканер, карантин); `watcher compile` —
Obsidian-вики; `watcher backup` — снапшот БД. Подробности — в README watcher.

## 6. CLI-справочник

| Команда | Что делает | Exit |
|---|---|---|
| `watcher doctor` | проверка установки: версии, checksums, конфиг, целостность индексов | 0/1/2/3 |
| `watcher save` | сохранить факт (интерактив или `--file`/`--stdin`) | 0/1/2/3 |
| `watcher search "…"` | гибридный поиск; `--json`, `--explain` | 0/1/2/3 |
| `watcher get <id>` | полный факт по id | 0/1/2/3 |
| `watcher entity <name>` | факты по сущности + co-occurring | 0/1/2/3 |
| `watcher model fetch` | скачать модель эмбеддингов (единственная сетевая команда) | 0/1/2/3 |
| `watcher reindex` | полный пересбор индексов (recovery-only) | 0/1/2/3 |
| `watcher compile` | Obsidian-слой из БД: facts/, entities/, index.md | 0/1/2/3 |
| `watcher lint` | контент-проверки: повисшие wikilinks, сироты | 0/1/2/3 |
| `watcher export` | shareable-факты в git как OKF-бандл (scanner→deny→render→conformance→git+quarantine) | 0/1/2/3 |
| `watcher quarantine` | карантин упавших на экспорте фактов (promote — только человек) | 0/1/2/3 |
| `watcher backup` | снапшот БД + экспортный git + ротация | 0/1/2/3 |
| `watcher query <SQL>` | диагностический read-only SQL (SELECT-only, `--limit`) | 0/1/2/3 |
| `watcher schema` | дамп схемы БД + версия миграций | 0/1/2/3 |

**Exit codes**: `0` ok, `1` usage, `2` data, `3` конфиг. `--json` —
стабильный машинный контракт (данные и единый конверт ошибки в stdout).

## 7. Устранение неполадок

- **Типовой вход** — `watcher doctor`: покажет отсутствующие файлы, битые
  checksums, проблемы конфига.
- **Модель не скачана** («модель эмбеддингов не найдена») — выполните
  `watcher model fetch`. Модель **опциональна**: без неё векторный слой
  отключается, поиск работает на bm25 + триграммы.
- **Индексы повреждены/странные результаты** — `watcher reindex` (полный
  пересбор).
- **Не сохраняется shareable-факт** — сработал deny-паттерн (секрет); см.
  §3 «Deny-паттерны»: понизьте sensitivity, не обходите.
- **Поиск пустой** — попробуйте синонимы/словоформы, затем перефразировку
  (векторный слой); факта может не быть в базе вовсе — так и ответьте.
- За подробностями — `tools/watcher/README.md` в репозитории e001-ai-hub.
