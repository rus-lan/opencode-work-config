# Модель оценки: математика, шкала, ограничения

Как из эталона Story Points и статистики закрытых спринтов получается число в отчёте. Документ
воспроизводимый: по нему можно пересчитать любую оценку вручную и получить те же числа, что в
`estimate.json`.

Нормативные источники: `CONTRACT.md` §5.6, §5.9, §8; `estimation-model.schema.json`;
`reference-estimates.schema.json`; `sprint-stats.schema.json`; `estimate.schema.json`.
Эталон шкалы — Confluence «T100 Story Points», page_id `4278391451`.

Термины, которые дальше используются без пояснений:

| Термин | Значение |
|---|---|
| бакет | пара «роль + вид работ» (+ тип задачи), по которой считается статистика и строится база |
| `base` | база бакета в Story Points — из эталона, а при его отсутствии из статистики спринтов |
| `observed` | наблюдаемая медиана Story Points по бакету спринтов |
| `factor` | коэффициент калибровки: во сколько раз реальность отличается от эталона |
| `expected` | итоговое ожидаемое значение в шкале |
| `range` | `[нижняя, верхняя]` границы в шкале |
| `gap_penalty` | штраф в шагах шкалы за блокирующие пробелы в описании задачи |
| `provenance` | запись «откуда взялось это число»; без неё число в отчёт не попадает |

## 1. Шкала Story Points

Шкала нормативна и не настраивается: `[1, 2, 3, 5, 8, 13, 21]`. Любое другое значение в
`estimation.scale` — ошибка конфига (код 3), а не «настройка под проект».

### 1.1 Значения и их смысл

Формулировки колонок — из эталона (page_id 4278391451, версия 7). Это не пересказ: `train` вычитывает
именно эти строки и фиксирует их в `norm/reference-estimates.json`.

| SP | Описание (сложность, скорость, объём кода) | Неопределённость | Рефакторинг | Исследование | Декомпозиция | Примерное время |
|---|---|---|---|---|---|---|
| 1 | Очень просто и очень быстро | Нет | Нет | Нет | Нет | до 2 часов |
| 2 | Просто и быстро | Нет | Нет | Нет | Нет | до 4 часов |
| 3 | Просто, но достаточно объёмно **или** попутный рефакторинг текущего кода | Низкая | Опционально | Неглубоко | Нет | до 1,5 дня |
| 5 | Объёмно **или** нетривиально **или** нужен research, но путь к цели понятен **или** мощный рефакторинг | Низкая | Заранее понятный и необъёмный | Да | Нет | до 3 дней |
| 8 | Объёмно/сложно **или** нужен объёмный research с неопределённостью **или** ещё более мощный рефакторинг | Высокая | Да | Да | Опционально | до 5 дней |
| 13 | Максимальный объём (логики **или** рефакторинга **или** рисёрча) для одной задачи | Высокая | Да | Да | Опционально | до 8 дней |
| 21 | Задачи, требующие исследования/декомпозиции | Высокая | Да | Да | Да | более 8 дней |

Как читать таблицу:

- Колонки «неопределённость / рефакторинг / исследование / декомпозиция» — не украшение: они объясняют,
  **почему** задача стоит столько. Если у задачи высокая неопределённость, значение ниже 5 почти наверняка
  занижено.
- «Декомпозиция = Да» (21) означает, что задачу вообще нельзя брать в спринт как есть: её надо разбить.
  Оценка 21 — это сигнал «сначала декомпозиция», а не «большая задача».
- «Примерное время» — календарное усилие одного человека, а не срок с учётом ожиданий и ревью.

## 2. Роли и виды работ

### 2.1 Роли

Роль приходит из Jira (`customfield_12750`) и нормализуется через `validation.role_map`. Неизвестное
значение — не ошибка: роль становится `OTHER`.

| Роль | Что оценивается |
|---|---|
| `BA` | требования, критерии приёмки, сценарии, согласование с заказчиком |
| `SA` | контракты, схемы, архитектурные решения, техническая постановка |
| `BE` | серверная часть: API, миграции, обработка данных, интеграции |
| `FE` | клиентская часть: компоненты, страницы, состояния, вёрстка |
| `QA` | проверка: тест-дизайн, прогон, регресс, e2e |
| `DEVOPS` | инфраструктура, пайплайны, конфигурация окружений |
| `OTHER` | роль не определена; оценивается по общей базе с `confidence=low` |

Одна задача может требовать работы нескольких ролей. Тогда в `estimate.json` появляется несколько
записей `roles[]` (по одной на роль, отсортированы по `role`), а `total` — их сумма.

### 2.2 Виды работ (`work_kind`)

`work_kind` определяет агент по смыслу задачи и типу; это единственное смысловое решение ИИ в оценке,
и оно фиксируется в `context.json` до расчёта.

| `work_kind` | Как определяется | Пример типа задачи |
|---|---|---|
| `implementation` | новый функционал или доработка | `Feature`, `Задача` |
| `research` | цель ясна, путь нет; результат — знание, а не код | `Задача` с исследованием |
| `bugfix` | исправление поведения | `Ошибка` |
| `tech_debt` | рефакторинг, миграции, обновление зависимостей | `Tech Debt` |
| `analysis` | решение/документ: ADR, разбор, проектирование | `ADR` |
| `testing` | отдельная задача на тестирование | `Задача` с меткой QA |
| `unknown` | тип и смысл не позволяют выбрать уверенно | любой |

**Как `work_kind` попадает в статистику.** В строке `sprint-sample.json` поля `work_kind` нет: схема строки —
ровно 10 полей (`sprint`, `key`, `issue_type`, `role`, `sp`, `qa_estimation`, `has_testing`, `status`,
`labels`, `summary_sha256`). Поэтому `stats.py` выводит `work_kind` из `issue_type` по таблице выше. Это
единственное место, где вид работ задаётся данными, а не решением агента при `check`.

**Правило для `unknown`.** Если `work_kind = unknown` (тип и смысл не позволяют выбрать уверенно), база
берётся из бакета `implementation` той же роли, `confidence = low`, а причина печатается в
`variability_reason[]` (`"work_kind=unknown → база implementation, confidence=low"`). Молча «дотянуть» до
`implementation` без пометки нельзя.

**Сопоставление с эталоном.** Эталон размечает `work_kind` не так дробно, как модель: в нём есть строки
`implementation`, а также отдельные бакеты `BE/bugfix`, `BE/tech_debt` и `FE/bugfix` (фикстура
`tests/fixtures/reference-estimates-t100.json`). Бакеты, которых в эталоне нет (`research`, `analysis`,
`testing` у BE/FE, любые `work_kind` у BA/SA), получают `reference: "none"` и базу из статистики спринтов
(§8), а не «натянутую» строку эталона.

## 3. Два поля Jira и что из них берётся

Оценка в Jira живёт в двух независимых полях. Их нельзя смешивать: это разные величины с разными
владельцами.

| Поле Jira | id по умолчанию | Что содержит | Как используется в модели |
|---|---|---|---|
| Story Points | `customfield_10004` | оценка роли, указанной в поле «Роль» | выборка `sp` для всех ролей, кроме `QA`; медиана бакета |
| QA Estimation | `customfield_13819` | оценка тестирования | выборка для роли `QA`; применяется **только** при `has_testing = true` |
| Роль | `customfield_12750` | `FE` / `BE` / … | определяет, в какой бакет попадёт строка; нормализуется `role_map` |

Правила:

- **Story Points принадлежит роли из поля «Роль».** Если в задаче стоит `Роль = BE`, то `sp` — это
  оценка BE, а не «общая оценка задачи». Складывать `sp` по всем задачам спринта и называть это
  «средней оценкой задачи» нельзя.
- **QA Estimation — отдельная шкала.** Она не равна Story Points и не обязана совпадать с ней. Для
  бакета `QA/*` выборкой служит `qa_estimation`, а строки с `has_testing = false` в QA-бакет не попадают
  вообще (иначе медиана QA съедет вниз за счёт задач, которые никто не тестировал). QA-бакет всегда имеет
  `work_kind: "testing"` — независимо от типа задачи, потому что работа там одна и та же.
- **Сравнение QA-поля с эталоном опирается на предположение о шкале.** Модель считает, что
  `qa_estimation` — число в той же шкале `1…21`, что и Story Points: тогда база из эталонных QA-примеров
  и медиана фактических QA Estimation сопоставимы. Если в вашей Jira `QA Estimation` заполняется в другой
  шкале (часы, проценты, «1–5»), сравнение ломается — в этом случае QA-бакет помечается
  `reference: "none"` и строится только из статистики. Проверять это нужно на `train`, а не догадываться
  по названию поля.
- **Пустое значение — это `null`, а не `0`.** В `sprint-sample.json` `sp` и `qa_estimation` — число или
  `null`. `0` вместо «нет данных» запрещён: он бы тянул медиану вниз и врал.
- **`DEV Estimation` (`customfield_13818`)** существует в Jira, но в модели не используется: контракт
  его не задействует. Если он понадобится — это изменение схемы, а не «тихое» чтение поля.

## 4. Формула по шагам

Все шаги выполняются по одному бакету `(role, issue_type, work_kind)`. Порядок фиксирован, промежуточные
значения округляются только там, где это указано.

### Шаг 0. Выбор бакета

Статистику по строкам считает `stats.py`: бакет — тройка `(role, issue_type, work_kind)`. Из
`norm/sprint-sample.json` берутся строки с непустым значением оценки:

- для ролей кроме `QA` — `sp`;
- для `QA` — `qa_estimation`, только строки с `has_testing = true`; такой бакет всегда имеет
  `work_kind: "testing"`.

`n` — число строк с непустым значением (`sp = null` в метрики не попадает). `n = 0` означает «данных
нет»: бакет не строится, и это не «ноль баллов», а отсутствие основания для оценки.

Какой бакет берётся для оценки роли — четыре уровня, от точного к грубому (порядок нормативный,
реализация: `estimate.select_bucket`):

1. **`exact`** — точное совпадение `(role, issue_type, work_kind)`. Тип задачи берётся из
   `context.issue_type` (запасной путь — `context.fields.issue_type`).
2. **`work_kind`** — `(role, work_kind)` при любом `issue_type`: если у роли нет бакета именно этого
   типа, но есть бакет того же вида работ. Из нескольких кандидатов берётся **наибольший `n`**
   (при равенстве — по возрастанию `work_kind`, затем `issue_type`).
3. **`role`** — `(role, *)`: у роли нет бакета этого вида работ. Тот же детерминированный выбор по `n`.
   Это деградация: `confidence = low`, причина — в `variability_reason[]`.
4. **`other_role`** — бакет роли `OTHER` по уровням 1–3 (роль без бакетов вообще: `DEVOPS` и подобные).
   Если у `OTHER` подходящего нет — любой бакет модели (`any`). Роль в `roles[]` остаётся исходной,
   числа — из чужого бакета, `confidence = low`.

Уровень, сработавший для роли, всегда записан в её `provenance`:

```
{"field": "bucket", "kind": "rule", "source": "estimate:bucket-select",
 "detail": "уровень выбора: exact — (role, issue_type, work_kind); бакет BE/Задача/implementation"}
```

Когда `work_kind` не задан (`explicit = false`), выбор сразу начинается с уровня 3: угадывать вид работ
нельзя, поэтому берётся бакет роли с наибольшим `n`. `work_kind = "unknown"` до уровня 3 не поднимается:
по правилу для `unknown` (§2.2) база берётся из `implementation`, `confidence = low`.

Роль вне словаря скилла (`TL`, `DevOps`, `Аналитик` — не входят в `ROLES`) оценивается по `OTHER`
одной ролью, а не суммой всех ролей модели: иначе пустой снимок давал бы 28–45 SP. Причина —
`variability_reason[]`: «роль 'TL' вне словаря скилла → оценка по OTHER, confidence=low».

**Роль не указана вовсе** (`role: null` или ключа нет) — оценивается **одна доминирующая роль вида
работ**: бакет с максимальным `n` среди бакетов этого `work_kind` (детерминированно: `n` desc → `role`
asc → `work_kind` asc → `issue_type` asc). `total = roles[0]`, `confidence = low`, в `estimate.json`
появляется `role_assumed: true`, в `variability_reason[]` — строка
«роль не указана → принята доминирующая роль <ROLE> (n=<n>) для work_kind=<wk>», в `provenance` роли —
запись `field=role, source=estimate:role-assumed`, в `warnings` CLI — `[WARN]`. Суммы по всем ролям
модели больше нет: 29/76 SP не значат ничего для одной задачи. Если для `work_kind` бакетов нет вовсе,
роль выбирается по всем бакетам модели, а дальше работает обычная деградация `select_bucket` (уровни
1–4, вплоть до `OTHER`). Пример: снимок без роли и без `work_kind` → `work_kind=implementation` →
доминирующая роль `BE` (`n=80`) → `expected=3` (до штрафов), `confidence=low`, `total=3`.

**Достижимость бакетов.** Любой бакет модели достижим на своей собственной тройке — это проверяет
`synth-run` (`buckets.probe`): на каждый бакет строится минимальный снимок `(role, issue_type, work_kind)`
и `estimate` обязан вернуть тот же бакет. `buckets.hit` в `summary.json` — другое: сколько бакетов
реально встретилось в датасете. На датасете, собранном с покрытием троек
(`trr synth --coverage-all-buckets`, по умолчанию), `hit = reachable = 20/20`: генератор гарантирует
`--coverage-quota` (по умолчанию 20) снимков на каждую тройку модели. `hit < reachable` — признак того,
что датасет собран старым генератором или с `--no-coverage-all-buckets` (осей выборки не хватает на все
комбинации).

Молча подставить чужую роль или чужой бакет нельзя: каждое понижение уровня — строка в
`variability_reason[]` (и `[WARN]`-строка в `warnings` CLI), каждое число — с провенансом.

### Шаг 1. База

```
base = значение эталона для (role, work_kind)        → reference = "yes"
base = nearest_scale(median бакета спринтов)         → reference = "none"
```

`base` обязан быть элементом шкалы. Если точного бакета в эталоне нет (BA, SA, `bugfix`, `tech_debt`),
база берётся из статистики — и это всегда видно в `provenance` и в `confidence`.

### Шаг 2. Наблюдаемое значение

```
observed = median(sp)   при n >= min_sample_n
```

`min_sample_n` — из конфига, по умолчанию `5`. Статистика **не участвует** в калибровке, если
`n < min_sample_n` (`coverage: "insufficient"`) **или** медианы нет вообще: тогда `observed` не
считается, `factor = 1.0`, `confidence = "low"`. Малая выборка остаётся в `sprint-stats.json` как
справка.

Медиана берётся из `sprint-stats.json`, то есть уже округлённая до 2 знаков — так расчёт воспроизводим
по файлам, без «второй математики» внутри модели.

### Шаг 3. Коэффициент калибровки

```
raw    = observed / base
factor = clamp(raw, factor_clamp[0], factor_clamp[1])     # по умолчанию [0.5, 2.0]
factor = round(factor, 4)
```

`clamp(x, lo, hi) = min(max(x, lo), hi)`. Ограничение не даёт одному выбросу в спринте перевернуть
всю модель: даже если медиана спринтов вдвое выше эталона, `factor` не превысит `2.0`.

### Шаг 3b. Множитель параметров

```
params_multiplier = clamp(1 + a·(w − w₀) + b·(h − h₀) + c·(k − k₀), clamp[0], clamp[1])
```

`w/h/k` — профиль параметров бакета (`buckets[].params_profile`, §13.7), `w₀/h₀/k₀` — `defaults`,
`a/b/c` — `coefficients` (§13.4). Когда профиль бакета не построен (строк спринта мало или сигналов
нет), в роли профиля выступают `defaults` — тогда множитель **ровно** `1.0` и шаги 4–5 совпадают с
прежней формулой. Смысл: бакет сравнивается сам с собой, поэтому «типовая» задача уровня не сдвигает
оценку, а задача с параметрами выше/ниже профиля — сдвигает.

### Шаг 4. Ожидаемое значение

```
expected = nearest_scale(base × factor × params_multiplier)
```

Округление к ближайшему значению шкалы (правила — §5). При равенстве расстояний выбирается **большее**
значение: лучше переоценить, чем обещать невыполнимое.

### Шаг 5. Диапазон

```
lower = nearest_scale_down(p25 × factor × params_multiplier)
upper = nearest_scale_up(p75 × factor × params_multiplier)
range = [lower, upper]
```

`nearest_scale_down` — наибольшее значение шкалы, не превышающее аргумент; `nearest_scale_up` —
наименьшее значение шкалы, не меньшее аргумента. Оба зажимаются в границы шкалы: ниже `1` и выше `21`
диапазон не выходит никогда.

После расчёта действует гарантия **`range[0] ≤ expected ≤ range[1]`**: если арифметика вывела границу
за `expected`, граница подтягивается к нему. Без этого возможен бакет, где `p25 × factor` больше
`base × factor` (например, при сильном расхождении эталона и статистики), и диапазон «не содержал бы»
собственную оценку.

Смысл: `p25`-ветка — «если повезёт и всё пойдёт по нижней квартили», `p75` — «если всплывут типичные
для этого бакета сложности».

### Шаг 6. Штраф за пробелы (`gap_penalty`)

```
steps    = Σ penalty_steps по сработавшим правилам, урезанная до MAX_PENALTY_STEPS = 2
expected = сдвиг expected вверх по шкале (последовательно, правило за правилом)
upper    = сдвиг upper на steps шагов вверх по шкале
lower    = без изменений
```

Сработавшие правила берутся из `validation.gaps[]` (только `severity = "REQUIRED"`) по таблице
`gap_rules`; подробности и порядок применения — §10.

Штраф применяется **только** к `expected` и верхней границе. Нижняя граница не опускается: пробелы в
описании не делают работу меньше, они делают её менее предсказуемой. Сработавшие правила попадают в
`blocked_by_gaps` в `estimate.json`.

### Шаг 7. Итог по задаче

```
total.expected = Σ roles[].expected
total.range    = [Σ roles[].range[0], Σ roles[].range[1]]
```

Сумма — по ролям, для которых есть работа. Роль без бакета в `roles[]` не попадает: причина пишется в
`variability_reason[]` («нет данных по роли X»), а не превращается в ноль. Если в модели нет ни одного
бакета, оценка невозможна — код 5 с сообщением «оценивать нечем» (лечится `train`/`enrich`, а не правкой
отчёта).

## 5. `nearest_scale`, `nearest_scale_down`, `nearest_scale_up`

```
nearest_scale(x)      = argmin |x - s| по s ∈ scale; при равенстве — больший s
nearest_scale_down(x) = max { s ∈ scale : s <= x }, иначе min(scale) = 1
nearest_scale_up(x)   = min { s ∈ scale : s >= x }, иначе max(scale) = 21
```

Примеры (шкала `1, 2, 3, 5, 8, 13, 21`):

| `x` | `nearest_scale(x)` | `down(x)` | `up(x)` | Комментарий |
|---|---|---|---|---|
| 0.4 | 1 | 1 | 1 | ниже шкалы — зажимается в 1 |
| 1.0 | 1 | 1 | 1 | точное попадание |
| 1.2 | 1 | 1 | 2 | ближе к 1 |
| 1.5 | 2 | 1 | 2 | равенство расстояний → большее |
| 2.5 | 3 | 2 | 3 | равенство → большее |
| 3.0 | 3 | 3 | 3 | точное попадание |
| 4.0 | 5 | 3 | 5 | равенство (1 и 1) → большее |
| 6.5 | 8 | 5 | 8 | равенство (1.5 и 1.5) → большее |
| 10.5 | 13 | 8 | 13 | равенство (2.5 и 2.5) → большее |
| 25.0 | 21 | 21 | 21 | выше шкалы — зажимается в 21 |

Правило «при равенстве — большее» — не косметика: оно делает функцию детерминированной (нет зависимости
от порядка элементов) и консервативной (не занижаем).

## 6. Процентили

Квартили и медиана считаются по одному алгоритму — линейная интерполяция (тип 7, он же
`PERCENTILE.INC` в таблицах). Не «ближайший ранг», не «среднее двух соседей» — именно интерполяция,
иначе `p25`/`p75` разойдутся с тем, что показывает таблица, и модель перестанет быть проверяемой.

Для отсортированного по возрастанию массива `a` из `n` значений и доли `p` (`0 ≤ p ≤ 1`):

```
idx  = (n - 1) × p
lo   = floor(idx)
hi   = ceil(idx)
v    = a[lo] + (idx - lo) × (a[hi] - a[lo])
```

Следствия:

- `n = 1` → все квантили равны единственному значению.
- Если `idx` целое, `lo = hi = idx` и `v = a[idx]` — интерполяция вырождается в точное значение.
- `median = p = 0.5`, `p25 = p = 0.25`, `p75 = p = 0.75`.
- В `sprint-stats.json` все четыре величины округлены до 2 знаков (`round(x, 2)`).

**Пример на 12 значениях.** Отсортированный бакет:
`[1, 1, 2, 2, 2, 3, 3, 3, 5, 5, 8, 8]`.

| Величина | `idx = (12-1) × p` | `lo` / `hi` | Расчёт | Результат |
|---|---|---|---|---|
| `p25` | `11 × 0.25 = 2.75` | 2 / 3 | `a[2] + 0.75 × (a[3] - a[2]) = 2 + 0.75 × 0` | `2.0` |
| `median` | `11 × 0.5 = 5.5` | 5 / 6 | `a[5] + 0.5 × (a[6] - a[5]) = 3 + 0.5 × 0` | `3.0` |
| `p75` | `11 × 0.75 = 8.25` | 8 / 9 | `a[8] + 0.25 × (a[9] - a[8]) = 5 + 0.25 × 0` | `5.0` |

Дополнительно: `min = 1`, `max = 8`, `mean = 43 / 12 = 3.5833… → 3.58`, `n = 12`.

## 7. Уровни уверенности

`confidence` — это не «насколько мы уверены в задаче», а «насколько надёжна база под числом».

| Условие | `confidence` |
|---|---|
| `reference = "yes"` и `n >= 2 × min_sample_n` | `high` |
| `reference = "yes"` и `n >= min_sample_n` | `medium` |
| `reference = "none"` (любое `n`) | `low` |
| данных нет: `coverage = "insufficient"` или нет медианы | `low` |

Из таблицы следуют три жёстких факта:

- **BA и SA не могут получить выше `low`.** У них `reference = "none"` по построению (в эталоне их нет),
  а `high`/`medium` требуют эталона. Это осознанная честность, а не баг.
- **`high` требует запаса по выборке.** Порог — `2 × min_sample_n` (при `min_sample_n = 5` это `n ≥ 10`):
  база из эталона плюс статистика, на которой это можно проверить.
- **Недостаточная выборка не повышает уверенность.** `n < min_sample_n` даёт `low`, даже если эталон есть:
  база хорошая, но проверить её на трёх задачах бессмысленно.

### Единственное правило выбора

Канон — таблица выше; она совпадает с `calibrate.py` и с `CONTRACT.md` §5.6:

```
high   : reference = "yes" и n >= 2 × min_sample_n
medium : reference = "yes" и n >= min_sample_n
low    : всё остальное — reference = "none", n < min_sample_n, нет медианы/данных
```

`estimation-model.schema.json` проверяет только перечисление значений (`enum: high|medium|low`), поэтому
никакая формулировка в описании поля не может «разрешить» другой уровень. Описание поля в схеме обязано
совпадать с этой таблицей: если правило меняется, меняются одновременно `calibrate.py`, `CONTRACT.md` §5.6,
схема и этот раздел — с повышением версии схемы.

## 8. Честность данных: BA/SA и недостаточная выборка

### 8.1 Роли, отсутствующие в эталоне

`absent_roles` в `estimation-model.json` и `reference-estimates.json` — сейчас всегда `["BA", "SA"]`.
Для них:

- `reference = "none"`;
- `base` выводится **только** из статистики спринтов: `nearest_scale(median)`;
- `provenance` для `base` указывает на `sprint-stats:<role>/<issue_type>/<work_kind>`, а не на Confluence;
- `confidence = "low"` — всегда, при любой выборке (§7);
- в `report.md` и в `estimation-model.md` печатается предупреждение:

```
[WARN] BA/SA отсутствуют в эталоне «T100 Story Points» — база выведена из статистики спринтов
       (reference: none), точность ниже, чем у BE/FE/QA
```

Это предупреждение нельзя отключить конфигом. Смысл: человек, читающий отчёт, должен видеть ограничение
до того, как начнёт спорить с числом.

### 8.2 Бакеты с недостаточной выборкой

Если `n < min_sample_n`:

- бакет попадает в `sprint-stats.json` с `coverage: "insufficient"` и в список `insufficient[]`
  (`"<role>/<work_kind>"`);
- `factor = 1.0` — калибровка по такой выборке не выполняется;
- `expected = nearest_scale(base)` — то есть фактически «как в эталоне»;
- `confidence = "low"` — калибровки не было, значит и уверенности в числе нет;
- в отчёте рядом с числом печатается пометка «выборка n=… < min_sample_n=…».

Ключевое: **недостаточная выборка не используется как основа.** Она остаётся справкой («вот что было
в этих двух задачах»), но не двигает `factor`. Иначе две случайные задачи переопределяли бы эталон.

### 8.3 Чего модель не делает

- Не заполняет пропуски средним по всем ролям: `BE`-статистика не подставляется в `BA`.
- Не экстраполирует за пределы шкалы: максимум — `21`.
- Не «сглаживает» выбросы вручную: единственный ограничитель — `factor_clamp`.
- Не подменяет отсутствующую роль ролью `OTHER` молча: `OTHER` — это отдельный бакет со своим `low`.

## 9. Пример расчёта целиком

### 9.1 Базовый случай: BE / implementation

Дано:

- эталон: строка «5» содержит примеры BE → `base = 5`, `reference = "yes"`;
- статистика бакета `BE / Задача / implementation`: `n = 12`, `min = 1`, `max = 8`, `mean = 3.58`,
  `median = 3.0`, `p25 = 2.0`, `p75 = 5.0`, `coverage = "sufficient"`;
- `min_sample_n = 5`, `factor_clamp = [0.5, 2.0]`;
- REQUIRED-пробелов нет.

| Шаг | Действие | Числа |
|---|---|---|
| 0 | выборка | `n = 12 ≥ 5` → статистика участвует |
| 1 | база из эталона | `base = 5`, `reference = "yes"` |
| 2 | наблюдаемое | `observed = median = 3.0` |
| 3 | коэффициент | `raw = 3.0 / 5 = 0.6`; `clamp(0.6, 0.5, 2.0) = 0.6`; `factor = 0.6` |
| 3b | множитель параметров | профиль бакета = `defaults` → `params_multiplier = 1.0` |
| 4 | ожидаемое | `5 × 0.6 × 1.0 = 3.0` → `nearest_scale(3.0) = 3` → `expected = 3` |
| 5 | нижняя граница | `2.0 × 0.6 × 1.0 = 1.2` → `down(1.2) = 1` |
| 5 | верхняя граница | `5.0 × 0.6 × 1.0 = 3.0` → `up(3.0) = 3` |
| 5 | диапазон | `range = [1, 3]` |
| 6 | штраф | пробелов нет → `steps = 0`, ничего не сдвигается |
| 7 | уверенность | `reference = "yes"`, `n = 12 ≥ 2 × 5 = 10` → `confidence = "high"` |

Сценарии в `estimate.json`:

| Сценарий | Значение | Почему |
|---|---|---|
| `base` | `3` | `base 5 × factor 0.6 = 3` |
| `optimistic` | `1` | `p25 2 × 0.6 = 1.2` → вниз по шкале |
| `pessimistic` | `3` | `p75 5 × 0.6 = 3.0` → вверх по шкале, штрафа нет |

Обратите внимание: при `median = 3` нижняя граница не может быть выше `1`. Это не ошибка расчёта, а
следствие того, что `p25 ≤ median`: `p25 × factor ≤ 3 × 0.6 = 1.8`, а `down(1.8) = 1`. Узкий диапазон
получается на бакетах с медианой, близкой к базе, а не правкой формулы: например `base = 5`,
`median = 5`, `p25 = 2`, `p75 = 5` дают `factor = 1.0`, `expected = 5` и `range = [2, 5]`.

### 9.2 Тот же бакет, но с REQUIRED-пробелом

Проверка задачи дала один REQUIRED-пробел: `SA-08 = FAIL` (нет измеримых критериев приёмки). Правило
`GR-01` даёт `+2` шага и попадает в `applies_to` для BE. Контракт (`SA-04 = FAIL`) в этом же снимке
штрафа не даёт: `SA-04` — `RECOMMENDED`, а `_penalties` берёт только `REQUIRED`-пробелы (см. §10).

| Шаг | Действие | Числа |
|---|---|---|
| 1–5 | без изменений | `expected = 3`, `range = [1, 3]` |
| 6 | порядок обхода | единственный REQUIRED-пробел `SA-08` → `GR-01` |
| 6 | потолок | `GR-01` требует `+2`, лимит `2` шага — штраф проходит целиком |
| 6 | сдвиг `expected` | `3 → 8` (`GR-01`, `+2` шага) → `expected = 8` |
| 6 | сдвиг верхней границы | `shift(3, 2) = 8` → `upper = 8` |
| 6 | нижняя граница | не меняется → `1` |
| итог | | `expected = 8`, `range = [1, 8]`, `blocked_by_gaps = ["SA-08"]` |

Сценарий `pessimistic` = `8`, `base` = `8`, `optimistic` = `1`. Отчёт обязан объяснить, что половина
разброса — не неопределённость оценки, а незакрытый пробел в описании.

Механику потолка (`MAX_PENALTY_STEPS = 2`) на текущем каталоге показать нечем: из четырёх `gap_rules`
срабатывает только `GR-01`, и он один занимает ровно весь лимит. `GR-02`/`GR-03`/`GR-04` не
срабатывают (см. §10), поэтому пример «`GR-01` урезается после `GR-02`» остался бы описанием мёртвого
пути.

### 9.3 Роль без эталона: BA / implementation

Дано: `reference-estimates.json` содержит `absent_roles = ["BA", "SA"]`; статистика
`BA / Задача / implementation`: `n = 7`, `median = 2.0`, `p25 = 1.0`, `p75 = 3.0`.

| Шаг | Действие | Числа |
|---|---|---|
| 1 | база из статистики | `nearest_scale(2.0) = 2` → `base = 2`, `reference = "none"` |
| 2 | наблюдаемое | `observed = 2.0` (`n = 7 ≥ 5`) |
| 3 | коэффициент | `2.0 / 2 = 1.0` → `factor = 1.0` |
| 4 | ожидаемое | `2 × 1.0 = 2` → `expected = 2` |
| 5 | диапазон | `down(1.0) = 1`, `up(3.0) = 3` → `range = [1, 3]` |
| 7 | уверенность | `reference = "none"` → `confidence = "low"` при любом `n` |

В отчёте рядом с `2` будет стоять не «эталон, строка 2», а «sprint-stats:BA/Задача/implementation,
median 2.0, n=7» плюс предупреждение из §8.1. Если выборка упадёт до `n = 2`, числа не изменятся
(`factor` и так `1.0`), но выборка станет `insufficient` — и в отчёте появится пометка о размере
выборки. Уровень `confidence` при этом останется `low`: он и так минимальный.

### 9.4 Несколько ролей в задаче

Задача требует BE (`expected = 8`, `range = [1, 8]`) и QA (`expected = 2`, `range = [2, 3]`):

```
total.expected = 8 + 2 = 10
total.range    = [1 + 2, 8 + 3] = [3, 11]
```

Итог не обязан быть элементом шкалы: сумма двух шкальных значений — арифметическая величина, и
округлять её к шкале нельзя (иначе итог перестанет быть суммой частей). В шкалу укладываются только
`roles[].expected`, `roles[].range` и `scenarios[].points`.

### 9.5 QA-составляющая

QA — такая же запись `roles[]`, как BE и FE: слагаемое `total.expected` и `total.range`, строка в
секции 5 отчёта и строка `Dev: N SP · QA: M SP · Итого: N+M SP`. Порядок ветвей (`estimate._qa_entry`):

| Условие | Что получается |
|---|---|
| `context.role = QA` | второй записи нет: QA уже посчитана основным циклом (`source=model`), двойного счёта нет |
| `qa_estimation` заполнена | значение из Jira как есть, `source=jira`, `range = [N, N]`, без `params` и без `gap_rules` |
| тип задачи ∈ `validation.qa_required_issue_types` (`check.detect_has_testing`) | расчёт моделью по QA-бакету, `source=derived`, `qa_bucket = QA/<issue_type>/testing` |
| тип задачи ∉ `qa_required_issue_types` | QA-работы нет, записи нет; в `estimate.json` появляется `qa_scope` |

По умолчанию `qa_required_issue_types` = `Feature`, `New Feature`, `Фича`,
`Ошибка`, `Bug`, `Дефект`. **У остальных типов (Задача, Tech Debt, ADR, Релиз,
Дизайн) QA-оценки нет:** исполнитель (роль из поля «Роль») выполняет полный
объём задачи, включая проверку результата. Сигналы тестирования в тексте,
метках или разделе описания QA-запись не включают — они лишь поясняют причину
(`has_testing_reason`). В отчёте вместо QA-строки печатается
`QA: не требуется (тип «…») — проверка результата входит в объём роли …`;
то же значение лежит в `estimate.json → qa_scope` (ключ необязательный).

Правила расчёта `derived`:

- бакет выбирается тем же `select_bucket`, но вид работ — `testing` (`stats.QA_WORK_KIND`): QA-бакеты
  статистики строятся только по `qa_estimation` строк с `has_testing = true`. Нет бакета `testing` —
  берётся `implementation`, затем любой QA-бакет;
- множитель параметров — **тот же**, что у основной роли (параметры задачи общие), но baseline —
  `params_profile` QA-бакета;
- `expected = nearest_scale(base × factor × params)`, но не меньше `1`; диапазон — `down`/`up` границ
  бакета с тем же множителем, с зажимами `lower ≤ expected ≤ upper`;
- `confidence`: `high` — бакет найден на уровне `exact`/`work_kind` при `reference = yes` и `n ≥
  min_sample_n`; `medium` — любой fallback по бакету; `low` — в модели нет ни одного QA-бакета и взята
  доля `QA_SHARE_FALLBACK = 0.25` от dev-оценки;
- `gap_rules` к QA не применяются: REQUIRED-пробел уже сдвинул оценку роли-исполнителя, повторять сдвиг
  в QA — двойной счёт;
- пустое поле пишет `[INFO] QA: поле пустое → рассчитано моделью: N SP (бакет …, n=…, reference=…)` в
  `warnings` и строку `QA: …` в `variability_reason[]`; в `total.qa` попадает `{expected, source, bucket}`.

### 9.6 Дополнительные ресурсы

Задача может требовать не только работы роли, но и **отдельного ресурса**. Два типовых случая:
написание тест-кейсов дополнительно затрагивает **allure**, написание автотестов — **e2e-сервис
автотестирования**. Это самостоятельный кусок работы (подготовка данных, разметка, прогон,
поддержка), которого нет в базе бакета, поэтому правило **`RS-01`** добавляет надбавку.

**Правило.** За каждый распознанный ресурс — `estimation.resources.sp_per_resource` SP (по умолчанию
`1`) к оценке основного исполнителя, либо оценка идёт **по верхней границе** уже посчитанного
диапазона (`mode: upper_bound`). Второй режим — для задач, которые фактически на написание тестов:
объём там известен плохо, и нижняя оценка заведомо оптимистична.

**Формула** (после `params` и `gap_rules`, до сборки `total`):

```text
# mode: add
expected = nearest_scale(expected + N × sp_per_resource)
range    = [min(low, expected), max(high, nearest_scale(high + N × sp_per_resource))]

# mode: upper_bound
expected = range_high
range    = [low, high]                     # диапазон не меняется
```

где `N` — число распознанных ресурсов, `low`/`high` — границы диапазона роли после множителя
параметров и штрафов. `mode: add` **не сужает** границы: `expected` всегда остаётся внутри
`range`; `mode: upper_bound` не добавляет шаг, а сдвигает `expected` к уже посчитанному `high`.

**Почему надбавка не применяется к QA-записи `source=derived`.** Производная QA-оценка считается
моделью по QA-бакету **от того же объёма работы** (§9.5). Надбавка к ней была бы двойным счётом:
ресурс уже двигает оценку исполнителя, а QA — слагаемое `total`, посчитанное от этого объёма. Поэтому
`_apply_resources` вызывается **после** добавления QA-записи и правит только запись основного
исполнителя: роль из `context.role` (та, что в `roles[]` идёт как основная), а при её отсутствии —
первую не-QA запись. QA из Jira (`source=jira`) — факт из задачи, надбавка к нему тем более не
применяется.

**Что попадает в артефакты.**

| Где | Что |
|---|---|
| `estimate.json → resources` | `{items: [{name, evidence, source}], count, sp_per_resource, bonus_sp, mode, applied_to, effect}`; ключ **не появляется**, если ресурсов нет (как `qa_scope`). При `mode: upper_bound` шаг не прибавляется, поэтому `bonus_sp: 0`, а `effect` = `expected = upper bound (N SP)` |
| `estimation-model.json → resources` | настройки правила как данные модели: `rule_id`, `enabled`, `sp_per_resource`, `mode`, `items` (каталог алиасов), `provenance[]`; изменение настроек даёт новую версию модели |
| `estimation-model.md` §9.6 | таблица настроек `RS-01` и каталог ресурсов с алиасами |
| `estimate.json → roles[].provenance[]` | запись `{"kind":"rule","ref":"RS-01","value":"+N SP за ресурсы: allure, e2e"}` у роли-исполнителя |
| `estimate.json → variability_reason[]` | строка `RS-01: ресурсы allure, e2e → +N SP (mode add)` |
| `report.md` §5 | `Ресурсы: allure, e2e → +2 SP (mode add)`; нет ресурсов — строки нет |
| комментарий оценки | пункт `дополнительные ресурсы: allure, e2e → +2 SP (mode add)` в блоке «На чём базируется оценка» |

**Расхождение модели и конфига.** `calibrate` снапшотит настройки `RS-01` в модель (страница модели
обязана объяснять числа), а `estimate` применяет надбавку по **живому** конфигу. Если конфиг
поправили без `train`/`enrich`, `estimate` печатает
`[WARN] resources: настройки RS-01 в модели расходятся с конфигом …` — числа считаются по конфигу,
модель объясняет прежние числа; лечение — переобучить модель (`train`/`enrich`).

**Дефолты** (`estimation.resources`, блок необязателен):

| Ключ | Дефолт | Смысл |
|---|---|---|
| `enabled` | `true` | распознавать ресурсы; `false` — правило выключено целиком |
| `sp_per_resource` | `1` | надбавка за один ресурс; `0` — ресурсы распознаются, но оценку не меняют |
| `mode` | `add` | `add` — прибавить SP; `upper_bound` — взять верхнюю границу диапазона |
| `items` | `allure`, `e2e` (см. ниже) | каталог «имя ресурса → алиасы (подстроки, casefold)» |

**Детекция.** Источники текста в фиксированном порядке: заголовок (`fields.summary`), `description`,
значения `sections{}`, `labels`, `issue_type`. Поиск — подстрокой по `casefold()` тексту. Один ресурс =
один элемент, сколько бы раз он ни упоминался; `evidence` — короткая цитата (≤ 120 символов), `source`
— поле, где нашлось первое совпадение. Результат сортируется по `name` — одинаковый снимок всегда даёт
одинаковый список.

**Ловушка, которая уже проверена тестом:** алиас `автотест` **не** является подстрокой слова
«автоматизация», поэтому «Корректировка работы 14 автоматизации» ресурсом `e2e` **не** считается — это
исправление самой автоматизации, а не написание автотестов.

**Как добавить свой ресурс** (например, Grafana-дашборд как отдельный ресурс):

```yaml
estimation:
  resources:
    items:
      grafana: ["grafana", "дашборд"]
```

`items` сливается по именам: своё имя добавляет ресурс, пустой список выключает существующий
(`allure: []` — ресурс больше не распознаётся), остальные остаются с дефолтными алиасами.

## 10. Правила штрафа (`gap_rules`)

`gap_rules` — данные в `estimation-model.json` (`GAP_RULES` в `calibrate.py`), а не код. Менять их можно
только через `enrich` (новая версия модели), чтобы у каждой оценки оставался провенанс «по какой версии
правил считали».

**`gap_rules[].condition` — единственный источник связи «check-id → правило».** Отдельной таблицы
соответствия в коде и документации нет: `estimate.py` берёт `validation.gaps[].id` и ищет правило, у
которого `condition` совпадает с `<id>=<status>`. Добавили правило проверки — добавили строку в
`gap_rules` (и наоборот); никаких «смысловых» псевдонимов вида `desc.<поле>` или `handoff.<поле>` не
существует.

`condition` ссылается на `id` правила проверки из действующего каталога `check.py` (`TPL-01…`, `SA-01…`,
`FT-01` — см. `validation-rules.md`).

| `rule_id` | `condition` | `penalty_steps` | `applies_to` | Когда применяется |
|---|---|---|---|---|
| `GR-01` | `SA-08=FAIL` | **2** | `SA`, `BE`, `FE`, `QA` | нет критериев приёмки: объём работы нечем проверить, приёмка будет «на глаз» — самый дорогой пробел |
| `GR-02` | `SA-04=FAIL` | 1 | `SA`, `BE`, `FE` | не зафиксирован контракт API: реализация упрётся в переделку — **не срабатывает при текущем каталоге правил**: `SA-04` всегда `RECOMMENDED`, `_penalties` берёт только `REQUIRED` |
| `GR-03` | `TPL-07=FAIL` | 1 | все роли | не заполнена Роль: непонятно, чья это работа и по какой базе считать — **не срабатывает при текущем каталоге правил**: `TPL-07` — `RECOMMENDED` |
| `GR-04` | `QA-01=FAIL` | 1 | `QA` | нет оценки QA при требуемом тестировании — **не срабатывает при текущем каталоге правил**: `QA-01` всегда `PASS` (QA требуется только для Feature/Ошибка, и там её считает модель) |

Правила применения (`estimate.py`):

- Штраф считается по `validation.gaps[]`, а не по всему `checks[]`: берутся только пробелы с
  `severity = "REQUIRED"`. `RECOMMENDED`/`OPTIONAL` не штрафуют никогда.
- Пробелы обходятся в порядке возрастания `id`; для каждого ищется правило по `condition` в `gap_rules`.
  Нет совпадения — штрафа нет: это не ошибка, а «правило не про эту модель».
- Штраф применяется **один раз на правило**, только к ролям из `applies_to`.
- Суммарный штраф ограничен **`MAX_PENALTY_STEPS = 2`** шагами шкалы. Если правило требует больше, чем
  осталось до потолка, оно урезается до остатка (например, `GR-01` (+2) при уже набранном `+1` даст
  `+1`). Дальше цикл останавливается. При текущем каталоге потолок недостижим как ограничение: штрафует
  только `GR-01`, и он занимает лимит целиком.
- `expected` сдвигается последовательно, правило за правилом (в отчёте видно `3 → 5 → 8`); верхняя
  граница сдвигается на **суммарное** число шагов; нижняя не меняется.
- После сдвигов действуют зажимы: `upper ≥ expected`, `lower ≤ expected`, `lower ≤ upper`.

Замечание по `GR-04`: правило `QA-01` есть в `check.py` — `severity: RECOMMENDED`, `kind: qa_estimation`.
Правило **всегда `PASS`**: заполненное поле даёт факт из Jira; пустое при требуемом QA (тип задачи ∈
`validation.qa_required_issue_types`) — сообщение «QA Estimation не заполнена — будет рассчитана
моделью» и `evidence: "derived"`; пустое при не-QA типе — сообщение о том, что проверку выполняет
исполнитель, и `evidence: "n/a"`. Поэтому `GR-04` (`QA-01=FAIL`) не срабатывает никогда, и штрафа за
QA в `_penalties` больше нет: QA не штрафуется, а **оценивается** — отдельной записью `role=QA` в
`roles[]` и слагаемым `total` (см. §9.5).

## 11. Почему это не заменяет оценку команды

Модель — вход в планирование, а не приговор.

- **Число из модели — это «сколько стоило похожее в прошлом»**, а не «сколько будет стоить это».
  Модель не знает про отпуска, чужой релиз, заблокированный доступ к стенду и человека, который уходит
  через неделю.
- **Финальное слово за командой.** Оценка обсуждается и принимается людьми; скилл даёт отправную точку,
  диапазон и список пробелов, из-за которых диапазон широкий.
- **Расхождение больше 2 шагов шкалы — сигнал перечитать задачу.** Если модель говорит `3`, а команда
  `13`, то дело не в том, «кто прав»: либо в задаче есть скрытый объём (не описан), либо модель не видит
  контекста (опишите его в задаче и запустите `refresh`), либо задача требует декомпозиции.
- **Расхождение фиксируется, а не заминается.** `enrich` меняет модель по подтверждённым данным
  (добавили спринт, поправили эталон), но не «подгоняет» её под желаемое число в конкретной задаче.
- **Уверенность честная.** `low` у BA/SA и у малых выборок — это не баг, а информация: на такое число
  нельзя опираться в обещаниях сроков без разговора с людьми.

## 12. Воспроизводимость и округление

Модель обязана быть проверяемой: одинаковый вход → байт-в-байт одинаковый JSON.

- **Канонический JSON**: `json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))`.
- **Запись файла**: `sort_keys=True`, `indent=2`, UTF-8, перевод строки `\n`, ровно один `\n` в конце.
- **`checksum` модели** = `sha256(canonical_json(модель без поля checksum))`. Поэтому «та же модель» —
  это совпадение `checksum`, а не совпадение версии.
- **Округление**: `mean`/`median`/`p25`/`p75` — `round(x, 2)`; `factor` — `round(x, 4)`;
  `expected`/`points`/`base` — целые из шкалы (никакого округления, только `nearest_scale`).
- **Порядок**: `buckets` — по `(role, issue_type, work_kind)`; `gap_rules` — по `rule_id`;
  `roles` в оценке — по `role`; `scenarios` — строго `base`, `optimistic`, `pessimistic`.
- **Время внутри вычисляемых полей** — только `computed_at` / `generated_at` / `estimated_at`.
  Всё остальное от времени не зависит, поэтому два прогона на одних данных сравнимы побайтово.
- **Версия модели только растёт**: `enrich` → `+1`, если входы изменились; при неизменных входах модель
  не переписывается (`[OK] входы не изменились, версия N не переписана`). `train` без изменений входа —
  версия не меняется.

## 13. Параметры задачи `weight` / `heat` / `connectivity` (эвристика)

Три числа `0.0…1.0`, которые описывают задачу по осям «сложность» / «необходимость проработки» /
«внешние интеграции». Полей в Jira под них нет: значения выводит `params.derive(context, cfg)`
(`trr params`), а ручной override — число в `context.json` или флаги `--weight/--heat/--connectivity`.
Значение параметра — **взвешенная сумма сигналов**, зажатая в `[0, 1]`; сумма весов сигналов
каждого параметра равна `1.0`, поэтому «все сигналы максимальны» → `1.0`, «сигналов нет» → `defaults`
(по умолчанию `0.5`).

Каждый сигнал нормирован в `[0, 1]`; в `evidence[]` попадает нормированное значение, в
`components{}` — взвешенный вклад. Ни полный текст задачи, ни значения полей Jira в evidence не
копируются: только числа и метки.

### 13.1 `weight` — вес задачи (сложность)

| Сигнал | Что считается | Нормировка | Вес |
|---|---|---|---|
| `issue_type` | тип задачи: Feature `0.60`, Tech Debt `0.55`, Исследование `0.65`, Задача `0.45`, Ошибка `0.40`, ADR `0.30`, иначе `0.50` | значение как есть | `0.25` |
| `description_len` | длина описания в символах | `log1p(len) / log1p(4000)`, зажим `1.0` | `0.15` |
| `acceptance_items` | критерии приёмки из секции + пункты списка в описании (`-`, `*`, `1.`, `- [ ]`) | `count / 8`, зажим `1.0` | `0.12` |
| `refactor_markers` | вхождения «декомпозиц», «рефактор», «переписать», «миграц», «схема БД» | `count / 3`, зажим `1.0` | `0.10` |
| `components` | число компонентов/сервисов (`context.components` / `fields.components`) | `count / 5`, зажим `1.0` | `0.13` |
| `analysis_numbers` | числа в тексте задачи (`analysis.signals.numbers`) — конкретика объёма | `count / 8`, зажим `1.0` | `0.10` |
| `analysis_scenarios` | число сценариев (`analysis.scenarios.count`) | `count / 3`, зажим `1.0` | `0.10` |
| `analysis_components` | компоненты/экраны/сервисы, упомянутые в тексте (`analysis.scope.components`) | `count / 5`, зажим `1.0` | `0.05` |

### 13.2 `heat` — необходимость проработки

| Сигнал | Что считается | Нормировка | Вес |
|---|---|---|---|
| `uncertainty` | вхождения «неизвестно», «уточнить», `TBD`, «подводные камни», «риск», `?` | `count / 3`, зажим `1.0` | `0.28` |
| `research_labels` | метки `research` / `spike` / `исследование` / `discovery` | `1.0`, если есть хоть одна | `0.20` |
| `missing_sections` | нет обязательной секции из `context.sections`: acceptance / scope / dod (с алиасами) | `missing / 3` | `0.16` |
| `open_questions` | `context.questions` (список/число) либо `?` в тексте | `count / 5`, зажим `1.0` | `0.16` |
| `analysis_ambiguity` | доля маркеров неопределённости (`analysis.ambiguity.ratio`) — выше неопределённость, больше проработки | `ratio / 0.15`, зажим `1.0` | `0.12` |
| `analysis_clarity_inverse` | `1 − analysis.clarity.score`: чем понятнее задача, тем меньше heat | `1 − score` | `0.08` |

Секции `sections` учитываются только если объект вообще передан: пустой/отсутствующий `sections` —
это «сигнала нет», а не «всё пропущено».

Сигналы `analysis_*` приходят из `analysis.analyze(context)` (содержательный
анализ: числа, сценарии, неопределённость, типы связей, упоминания интеграций) и
добавляются только когда сигнал наблюдён: нулевой счётчик не занимает вес, иначе
«сигналов нет» перестало бы давать `defaults`. Анализ считается один раз на
`derive()` и передаётся во все три эвристики.

Сумма весов каждого параметра остаётся `1.0` (проверяется тестом): добавление
`analysis_*` перераспределило веса старых сигналов, поэтому задача без новых
сигналов получает значение чуть ниже прежнего. Это осознанное следствие
версии правил 2, модель при этом не переобучается: `params_profile` бакетов
остаётся прежним, меняется только относительный сдвиг от профиля.

### 13.3 `connectivity` — внешние интеграции

| Сигнал | Что считается | Нормировка | Вес |
|---|---|---|---|---|
| `issuelinks` | `fields.issuelinks` / `context.issuelinks` (список или уже посчитанное число) | `count / 5`, зажим `1.0` | `0.24` |
| `integration_labels` | метки из `check.INTEGRATION_LABELS` (`api`, `contract`, `integration`, …) | `1.0`, если есть хоть одна | `0.20` |
| `external_systems` | упоминания: URL, `api`, `контракт`, `интеграц`, `grpc`, `kafka`, `очеред`, `webhook`, имена через дефис | `count / 5`, зажим `1.0` | `0.20` |
| `linked_components` | число компонентов/сервисов | `count / 5`, зажим `1.0` | `0.16` |
| `analysis_link_types` | число разных типов связей (`analysis.dependencies.link_types`: `blocks`, `is blocked by`, `relates`, `depends`) | `count / 3`, зажим `1.0` | `0.12` |
| `analysis_integrations` | упоминания интеграций/внешних систем (`analysis.dependencies.integrations`) | `count / 2`, зажим `1.0` | `0.08` |

### 13.4 Множитель и границы

```
multiplier = clamp(1 + a·(weight − w₀) + b·(heat − h₀) + c·(connectivity − k₀), clamp[0], clamp[1])
```

`a, b, c` — `estimation.params.coefficients` (по умолчанию `0.5 / 0.4 / 0.3`), `w₀, h₀, k₀` —
`estimation.params.defaults` (по умолчанию `0.5`), `clamp` — `[0.5, 2.0]`. При значениях по
умолчанию множитель равен `1.0`; на краях зажимается.

Множитель **входит в формулу §4 третьим сомножителем**: `expected = nearest_scale(base × factor ×
params_multiplier)`, обе границы диапазона масштабируются им же. База сравнения — профиль параметров
бакета (`buckets[].params_profile`, §13.7); если профиля нет, берутся `defaults` и множитель равен
`1.0`. `estimate` печатает строку `[INFO] params: …` с применённым множителем и его базой.

### 13.5 Приоритет источников

1. `enabled: false` → все три = `defaults`, `source: disabled`.
2. Ручной override (`context.<имя>`, `context.params.<имя>`, флаги CLI) → `source: override`,
   значение зажимается в `[0, 1]`.
3. Эвристика → `source: heuristic`; если ни один сигнал не наблюдался — `defaults` с пояснением
   «сигналов нет → default …».

### 13.6 Приоры из эталонной таблицы

Кроме эвристики по тексту задачи, у каждого уровня шкалы есть **приор** — что обычно означает
этот SP по колонкам-маркерам эталонной таблицы (`reference-estimates.json → levels[].params_hint`).
Приор считается один раз при чтении эталона и не зависит от конкретной задачи; бакет наследует приор
своего уровня (`buckets[].params_hint`).

Формула — фиксированная, без подгонки:

```
weight = clamp(0.5 + refactoring_вклад + decomposition_вклад, 0, 0.9)
heat   = clamp(0.5 + uncertainty_вклад + research_вклад,     0, 0.9)
```

| Колонка эталона | Значение ячейки | Вклад |
|---|---|---|
| `Присутствуют неопределённость` | `Нет` / пусто | `heat += 0.00` |
| | `Низкая` | `heat += 0.10` |
| | `Высокая` | `heat += 0.25` |
| `Требуется исследование` | `Нет` / пусто | `heat += 0.00` |
| | `Неглубоко` | `heat += 0.30` |
| | `Да` | `heat += 0.40` |
| `Возможен рефакторинг` | `Нет` / пусто | `weight += 0.00` |
| | `Опционально` | `weight += 0.15` |
| | `Заранее понятный и необъёмный` | `weight += 0.20` |
| | `Да` | `weight += 0.30` |
| `Требует декомпозицию` | `Нет` / пусто | `weight += 0.00` |
| | `Опционально` | `weight += 0.15` |
| | `Да` | `weight += 0.30` |

Следствия формулы (проверены на таблице 4278391451):

- строка с `research = Да` всегда упирается в потолок `heat = 0.9` — «нужно исследование» и есть
  максимальная необходимость проработки, независимо от того, насколько строка «объёмна»;
- `weight` различает объём: `0.5` у строк 1–2, `0.65` у строки 3 (попутный рефакторинг), `0.70` у
  строки 5 (мощный рефакторинг), `0.9` у строк 8/13/21 (рефакторинг + декомпозиция);
- `connectivity` в приор **не входит**: в таблице нет колонки про внешние интеграции, а выводить её
  из числа примеров значило бы выдумать сигнал. Поле остаётся `null`/отсутствует — эвристика §13.3
  работает как раньше.

Приор — **характеристика уровня, а не множитель**: в `base × factor × params_multiplier` он не
входит, `estimate` его не читает. В формулу входит `params_profile` бакета (§13.7) — медиана
эвристики по строкам спринта, а не приор из таблицы. Приор нужен, чтобы у уровня была машинная
характеристика «сколько в нём неопределённости и объёма», сверяемая с `params.derive` по конкретной
задаче: расхождение приора и эвристики — сигнал, что задача не похожа на свой уровень.

#### Как выбирается `value` бакета

`buckets[]` отвечает на вопрос «сколько стоит вид работ», `levels[]` — «что написано в таблице на
этой строке». Бакет выбирается по правилу, одинаковому для всех ролей:

| `work_kind` | Какая строка становится бакетом |
|---|---|
| `implementation` | строка, где примеры роли описывают её основной поток работ, а не край шкалы (не «очень просто», не «максимальный объём»); для BE/FE это SP=5, для QA — SP=3 (типовой объём проверки) |
| `bugfix` | строка, где у роли есть пример про исправление/баг и объём соответствует «быстрому исправлению»: SP=2 для всех трёх ролей |
| `tech_debt` | строка, где описание строки или пример роли говорит про рефакторинг **и** объём «попутный», а не «максимальный»: SP=3 для BE/FE (строка 3: «…или попутный рефакторинг текущего кода»), SP=5 для QA (строка 5: «Регресс тестирование модуля на странице» — типовой объём проверки затронутого рефакторингом модуля) |

Крайние строки (SP=13 «максимальный объём», SP=21 «неизвестный объём») бакетами не становятся:
это не типовой уровень, а верх диапазона. Если роль в строке отсутствует, цитируется описание строки
(единственный такой случай — FE/`tech_debt`); факт фиксируется в `evidence` вместе с цитатой крайней
строки, чтобы выбор был проверяем.

`value` обязан входить в `scale`; `example_count` — сколько примеров этой роли на выбранном уровне;
`level` — тот же SP. Дубликат пары `(role, work_kind)` — `SCHEMA_ERROR` (`calibrate._reference_index`),
усреднения нет.

### 13.7 Профиль параметров бакета и калибровка коэффициентов

В формулу §4 входят **две** вещи из этого раздела: `params_profile` бакета (точка, в которой множитель
равен `1.0`) и `coefficients` (насколько сильно отклонение параметра двигает оценку).

#### Профиль бакета (`buckets[].params_profile`)

`calibrate` считает `params.derive` по каждой строке выборки спринта, попавшей в бакет (та же
группировка, что в `stats.compute`), и берёт **медиану** по каждому параметру:

```
profile[name] = median(derive(row)[name] for row in bucket_rows)   # если покрытие сигналов достаточно
profile[name] = estimation.params.defaults[name]                    # иначе
```

Покрытие (`params.coverage`) — доля веса сигналов параметра, реально присутствовавших в снимке строки.
Строка выборки (`sprint-stats.rows[]`) содержит только `labels` и `issue_type`, поэтому покрытие там
мало; при покрытии ниже `_PARAM_COVERAGE_MIN = 0.5` параметр берётся из `defaults`, а не из шума.
Источник профиля фиксируется в `buckets[].params_profile_source`:

| `params_profile_source` | Когда | Множитель |
|---|---|---|
| `bucket` | все три параметра покрыты сигналами строк | из медианы, может отличаться от `1.0` |
| `sample_limited` | часть параметров покрыта, остальные из `defaults` | ≈ `1.0` (сдвиг только по покрытым) |
| `defaults` | строк меньше `min_sample_n` или сигналов нет вовсе | ровно `1.0` |

Профиль — **не приор уровня** (§13.6): приор описывает строку эталонной таблицы, профиль — то, как
выглядят реально закрытые задачи этого бакета. Поэтому «типовая» задача бакета не сдвигает оценку.

#### Коэффициенты (`params.coefficients`)

Коэффициенты `a/b/c` калибруются регрессией по строкам выборки, где есть и `sp`, и сигналы параметров:

```
log(sp / base) ~ 1 + a·(w − w₀) + b·(h − h₀) + c·(k − k₀)
```

Решаются нормальные уравнения (stdlib, без внешних зависимостей); результат зажимается в `[0, 2]`.
Регрессия **отказывается** подгонять, и тогда берётся приор конфига (`estimation.params.coefficients`),
если:

- строк с сигналами меньше `_REGRESSION_MIN_N = 30`; или
- дисперсия любого регрессора ниже `_REGRESSION_MIN_VARIANCE = 0.01` — коэффициент не идентифицируется
  (например, `heat` и `connectivity` в выборке постоянны); или
- нормальные уравнения вырождены.

Причина отказа, `n` и (для регрессии) `r2` попадают в провенанс модели: `params.coefficients_source`
(`prior` / `regression`) и `params.provenance[]`. Подгонять коэффициенты под синтетику или под выборку,
где регрессор не меняется, нельзя: множитель начал бы «объяснять» шум.
