# Симптомы и лечение

Практический разбор отказов скилла `task-readiness-review`: что видно на экране, почему так вышло и какой
командой это лечится. Теория — `pipeline.md`, коды выхода — `commands.md` §4, деградация источников —
`sources-fallback.md`.

Обозначения:

```sh
TRR="${TRR:-$HOME/.config/opencode/skills/task-readiness-review/scripts/trr}"
SKILL_DIR="$(cd "$(dirname "$TRR")/.." && pwd)"
```

Общее правило: сначала `"$TRR" doctor` и `"$TRR" config-check`. Они дают точную строку с путём до поля, а
не «что-то не так». Ниже — случаи, которые диагностика не покрывает или покрывает неочевидно.

---

## 1. Нет `task-readiness-review.yaml`

**Симптом**

```text
[MISSING] task-readiness-review.yaml — скопируйте пример из скилла и заполните sources.reference и sources.sprints
```

`trr config-check` / `trr doctor` / любой этап возвращают код `3`.

**Причина.** В проекте не проходил `init`, либо конфиг лежит не в корне проекта, либо запуск идёт не из
того каталога.

**Что делать**

```sh
ls -la task-readiness-review.yaml                     # есть ли файл вообще
"$TRR" doctor --root <корень-проекта>                 # проверить, что смотрим туда
/task-readiness-review init "<где эталон и какие спринты брать>"
```

Если конфиг есть, но в другом каталоге — передавай `--root <dir>` всем подкомандам либо запускай из корня
проекта. Не копируй конфиг из соседнего проекта: там другие `page_id`, `board_id` и `jira.project`.

---

## 2. Конфиг содержит секрет

**Симптом**

```text
[MISSING] config.jira.token — ключ похож на секрет: секреты в конфиге запрещены, используйте переменные окружения JIRA_TOKEN / CONFLUENCE_TOKEN / GITLAB_TOKEN
```

Код `3`. Значение в сообщение не попадает — проверяется только имя ключа.

**Причина.** В `task-readiness-review.yaml` появился ключ с именем, подходящим под
`(?i)(token|secret|password|passwd|api[_-]?key|private[_-]?key|\bpat\b)`.

**Что делать**

1. Удали ключ из файла (в том числе «закомментированный» — комментарии в YAML не спасают, если ключ
   раскомментирован).
2. Перенеси значение в переменную окружения и перезапусти проверку:

   ```sh
   export JIRA_TOKEN=…          # не печатать значение в чат и логи
   "$TRR" config-check
   ```

Токен в артефакты не попадает никогда; если он уже был записан в файл — считай его скомпрометированным и
перевыпусти.

---

## 3. Свободный текст в источниках не резолвится

**Симптом.** В конфиге написано «эталон в конфлюенсе, спринты 26.18–26.19», а `resolved-sources.json`
содержит источник с `page_id: null`, `confidence: low`, и гейт отвечает:

```text
[BLOCKED] reference: не найден ни один источник kind=reference — добавьте ссылку на эталон оценки в sources.reference …
```

**Причина.** Свободный текст — только вход для резолва. Агент не выполнил резолв (нет ссылки, нет доступа,
поиск не дал совпадений), поэтому в файле остался «кандидат», а не разрешённый источник.

**Что делать**

1. Дай агенту разрешимую формулировку: URL страницы или `page_id`.

   ```yaml
   sources:
     reference: |
       https://space.samokat.ru/display/ECOMCS/T100+Story+Points
   ```

2. Повтори резолв: `/task-readiness-review init` (на существующем конфиге — правка только `sources.*`, без
   `--force`).
3. Проверь результат: `"$TRR" validate resolved-sources .task-readiness/resolved-sources.json` — код `0`
   и непустой `evidence` у каждого источника.

Правило: имя страницы без ссылки — подсказка, а не источник. `page_id` не выдумывается.

---

## 4. Спринт не найден

**Симптом**

```text
[BLOCKED] sprint: не найден ни один источник kind=sprint — перечислите закрытые спринты в sources.sprints …
```

или `train` падает на конкретном имени.

**Причина.** Три разных случая, и лечатся они по-разному:

| Что видно | Причина | Лечение |
|---|---|---|
| имени нет в списке борда | опечатка или спринт другого борда | `jira_get_sprints_from_board(board_id=…, state="closed")` и сверить имя посимвольно; поправить `sources.sprints` |
| спринт есть, но `state=future/active` | статистика по незакрытым недостоверна | взять закрытый спринт; либо дождаться закрытия |
| `404` на agile-эндпоинт | нет прав на борд или agile API недоступен | запросить доступ к борду; `404` здесь не значит «спринтов нет» |

**Что делать**

```sh
"$TRR" state get runs                    # какие прогоны уже были
/task-readiness-review init                     # поправить sources.sprints и перерезолвить
"$TRR" validate resolved-sources .task-readiness/resolved-sources.json
```

Не подставляй «похожий» спринт: чужие задачи сдвинут фактор калибровки.

## 5. В проекте нет поля Story Points

**Симптом.** `train` не может заполнить `sp`; в `sprint-sample.json` все `sp: null`; `calibrate` ругается
на отсутствие данных или строит модель с `confidence=low` по всем бакетам.

**Причина.** Поле называется иначе (`story_points` ≠ `customfield_10004`) или не используется в проекте.

**Что делать**

1. Узнай фактический id поля в Jira (админ проекта или `/rest/api/2/field`).
2. Пропиши его в конфиг:

   ```yaml
   jira:
     fields:
       story_points: customfield_XXXXX
   ```

3. `"$TRR" config-check`, затем `/task-readiness-review train`.

Если поля в проекте нет вовсе — это `[BLOCKED]`: без Story Points статистику не построить. Записывать `0`
вместо «нет данных» запрещено — это исказит медиану и фактор.

---

## 6. Бакет меньше `min_sample_n`

**Симптом**

```text
[WARN] bucket BA/implementation: n=2 < min_sample_n=5 — confidence=low
```

Код `0` — это не ошибка.

**Причина.** В выборке слишком мало задач этой роли/вида работ; статистика insufficient.

**Что делать.** Ничего не «дотягивать». Два законных пути:

```sh
/task-readiness-review enrich "T100-T102 26.23"     # добавить спринты с задачами этой роли
```

либо снизить порог осознанно (только если пользователь понимает цену):

```yaml
validation:
  min_sample_n: 3
```

После правки — `"$TRR" config-check`, `"$TRR" stats`, `"$TRR" calibrate`, затем
`/task-readiness-review publish --model` (страница модели должна совпадать с новой версией).

Пока бакет insufficient, в отчёте у роли будет `confidence: low` — это надо показывать, а не скрывать.

## 7. Модель не опубликована

**Симптом**

```text
[BLOCKED] check: страница модели не опубликована — запустите /task-readiness-review publish --model (для проекта без Confluence: --target obsidian)
```

`state.model_page` = `null`, `check` блокируется.

**Причина.** `train` построил модель, но запись страницы не удалась (нет прав, `output.target: none`,
MCP недоступен) — либо `enrich` обновил модель, а страницу не переопубликовали.

**Что делать**

```sh
"$TRR" state get model_page            # null?
"$TRR" model-hash                      # версия и sha256 модели
/task-readiness-review publish --model
"$TRR" state get model_page            # должен стать объектом с system/id/url/hash/version
```

**Проект без Confluence (офлайн).** Гейт закрывается локальной публикацией — сеть и MCP не нужны:

```sh
"$TRR" publish --model --target obsidian --ref local \
  --url .task-readiness/model/estimation-model.md \
  --file .task-readiness/model/estimation-model.md --no-stage
"$TRR" state get model_page            # system=obsidian, id=local, hash == model-hash
"$TRR" check --task <KEY> --no-jira    # гейт пройден, код 0
```

`--target obsidian` пишет `state.model_page` в `state.json` с тем же `hash` (checksum модели), что и
`--target confluence`, поэтому `check` проходит. `--ref` — стабильный локальный идентификатор (`local`
или путь заметки), `--url` — путь к `estimation-model.md`. После `enrich`/`train` команду нужно
повторить: hash старой записи разойдётся с новой моделью.

Если страница нужна именно в Confluence (публичное доказательство версии), а прав на пространство
нет — попытка публикации даст `[WARN]`, а `check` останется `[BLOCKED]`: попроси доступ, не «объявляй»
страницу опубликованной вручную. Для проекта, где Confluence нет вовсе, штатный путь — офлайн-вариант
выше.

## 8. MCP Confluence недоступен

**Симптом.** `confluence_get_page` таймаутит/обрывается; `train` не может прочитать эталон; `publish`
не может записать страницу.

**Причина.** Транспортный сбой MCP-сервера, протухшая сессия, либо страница закрыта правами.

**Что делать**

1. Одна повторная попытка — **только** на транспортный сбой (таймаут/обрыв/пустой ответ при существующем
   объекте). На `401/403/404` повторять бессмысленно.
2. REST fallback:

   ```sh
   test -n "$CONFLUENCE_TOKEN" && echo "[OK] токен задан"
   curl -fsS -H "Authorization: Bearer $CONFLUENCE_TOKEN" \
     "$CONFLUENCE_URL/rest/api/content/4278391451?expand=body.storage,version"
   ```

3. Оба недоступны: для **чтения** — `[BLOCKED]` + `.task-readiness/DATA-REQUIREMENTS.md`; для **записи** —
   `[WARN]` + `actions/confluence-page.md` (работа не падает).

У Cloud база может быть `/wiki/rest/api/...` — определяй по фактическому ответу, а не по памяти.

---

## 9. MCP Jira недоступен

**Симптом.** Не читаются спринты (`train`) или задача (`check`); `jira_get_issue` возвращает ошибку.

**Причина.** Транспортный сбой MCP, протухший токен, либо нет прав на проект/борд.

**Что делать**

1. Повторить один раз на транспортный сбой.
2. REST fallback:

   ```sh
   curl -fsS -H "Authorization: Bearer $JIRA_TOKEN" \
     "$JIRA_URL/rest/api/2/issue/E001-1234?fields=summary,status,customfield_10004"
   curl -fsS -H "Authorization: Bearer $JIRA_TOKEN" \
     "$JIRA_URL/rest/agile/1.0/board/6662/sprint?state=closed&maxResults=50"
   ```

3. Оба недоступны: спринты и задача — `[BLOCKED]` + `DATA-REQUIREMENTS.md` (что нужно, где взять, кому);
   комментарии — `[WARN]` + action-пакеты (`actions/jira-validation.md` и `actions/jira-estimate.md` у
   `publish`, `actions/jira-questions.md` у `check`).

Jira Cloud использует `/rest/api/3/...` и токен-пагинацию: `400` на `startAt` — признак не той ветки API.

## 10. REST отвечает 401/403

**Симптом**

```text
401 Unauthorized
403 Forbidden
```

**Причина.** Это **не** флап и не «неверный формат». `401` — токен не передан/протух/не от той
инсталляции; `403` — токен валиден, но прав на объект нет.

**Что делать**

| Ответ | Проверка | Действие |
|---|---|---|
| `401` | `test -n "$JIRA_TOKEN"`, `test -n "$CONFLUENCE_TOKEN"` | задать/обновить переменную; MCP может работать без токена — тогда REST просто недоступен |
| `403` | тот же запрос к объекту, который точно доступен | запросить доступ и записать в `DATA-REQUIREMENTS.md` «нужен доступ к <объект>» |

Запрещено: подбирать креды, отключать проверку TLS, обходить SSO, использовать чужую сессию. Для **чтения**
`401/403` — это `[BLOCKED]` с просьбой выдать доступ; для **записи** (комментарии в задачу) — `[WARN]`,
код `0` и action-пакеты `actions/jira-validation.md` / `actions/jira-estimate.md`
(`actions/jira-questions.md` у `check`), см. сценарий 25.

Отдельно: `400/500` с текстом `Invalid format: … malformed at "…"` — это формат параметра (чаще дата), а
не права. Ищи проблему в значении, а не в токене.

## 11. В задаче не заполнена Роль

**Симптом**

```text
| TPL-07 | RECOMMENDED | FAIL | не заполнено поле «Роль» |
```

Вердикт `WARN` (в rules version 2 поле «Роль» — `RECOMMENDED`, а не блокирующее): в оценке роль может
отсутствовать, и `variability_reason` содержит причину деградации до доминирующей роли. Штраф `GR-03`
больше не применяется: `estimate._penalties` смотрит только `gaps[]` со `severity = REQUIRED`, а
`TPL-07` туда не попадает.

**Причина.** Поле `jira.fields.role` пустое или содержит значение, которого нет в `validation.role_map`
(тогда роль нормализуется в `OTHER`).

**Что делать**

1. Если значение в Jira есть, но незнакомое — добавь его в маппинг:

   ```yaml
   validation:
     role_map:
       Backend: BE
       Фронтенд: FE
   ```

2. Перепроверь задачу: `/task-readiness-review check E001-1234`, затем `/task-readiness-review estimate E001-1234`.

3. Если поле реально пустое — это вопрос к BA: `TPL-07` попадёт в `questions.json` с адресатом и местом
   поиска. Не подставляй роль «по смыслу задачи»: бакет оценки от неё зависит.

## 12. В задаче нет критериев приёмки

**Симптом**

```text
| SA-08 | REQUIRED | FAIL | нет критериев приёмки, ожидаемого результата, объёма работ и действия
в заголовке задачи — не понять, что делать и как проверять |
```

либо «раздел «Критерии приёмки» есть, но ни один критерий не измерим и не описывает результат работ…».

**Причина.** В задаче нет **ни одного** основания готовности: ни измеримого критерия, ни критерия-
результата работ, ни ожидаемого результата, ни объёма работ («Решение», «Задача», «Необходимо»,
«нужно + глагол действия»), ни цели, ни действия в заголовке. «Ожидаемый результат» — эквивалент
«Критериев приёмки», а описанный объём работ — самостоятельное основание: если в задаче сказано, что
надо сделать, `SA-08` ставит `PASS` и пишет источник (`объём работ описан (раздел «Решение»): …`).

**Что делать**

1. Сначала проверь, что снимок собран полно: раздел «Решение»/«Задача» мог остаться в `description`,
   но не попасть в `sections{}` — правило найдёт его и в описании, если заголовок распознан
   (`h3.`, `**Жирный:**`, `*Курсив:*`, `{*}…{*}`, `Заголовок: значение`).
2. Если оснований правда нет — это блокирующий пробел (`REQUIRED`): вердикт `BLOCKED`, но `estimate`
   всё равно считается: `gap_penalty` расширяет диапазон. Покажи пользователю цену неготовности.
3. Вопрос уже сформулирован в `questions.json` (`q.SA-08`) с `target_role: BA` и `where_to_find`.
4. После правки задачи: `/task-readiness-review refresh E001-1234` — получишь `delta.md` с закрытым `SA-08`.

Не «дописывай» критерии за BA и не правь `validation.json` руками: следующий прогон всё равно перезапишет
его из `context.json`.

## 13. `estimate` без `validation.json`

**Симптом**

```text
[MISSING] .task-readiness/runs/<KEY>/<RUN-ID>/validation.json — сначала запустите /task-readiness-review check <KEY>
```

Код `4`.

**Причина.** Прогон не создан, либо создан только каталог с `context.json`, либо `check` упал на схеме и
не записал результат.

**Что делать**

```sh
ls -la .task-readiness/runs/E001-1234/*/            # какие прогоны есть
"$TRR" validate validation .task-readiness/runs/E001-1234/<RUN-ID>/validation.json
/task-readiness-review check E001-1234                     # пересобрать прогон
/task-readiness-review estimate E001-1234
```

Если `check` отвечает кодом `5` — сначала лечи `context.json` (неполный снимок), иначе `estimate` снова
нечего будет читать.

## 14. `init` на существующем конфиге

**Симптом**

```text
[BLOCKED] task-readiness-review.yaml уже существует — используйте --force для перезаписи
```

Код `2`.

**Причина.** Это защита, а не сбой: `init` создаёт конфиг, а не правит чужой.

**Что делать**

| Намерение | Команда |
|---|---|
| обновить только источники | править `sources.*` в существующем файле, затем `/task-readiness-review init` (резолв без перезаписи) |
| пересоздать конфиг с нуля | `"$TRR" init --non-interactive --force` — **осознанный сброс**: `state.json` пересоздаётся, история прогонов теряется |
| принять готовый артефакт обучения | скопировать файлы и проверить `"$TRR" model-hash` + `"$TRR" state get model_page`, без `init --force` |

Перед `--force` всегда спроси пользователя и покажи, что именно будет потеряно (`"$TRR" state get runs`).

## 15. После `enrich` осталась старая страница модели

**Симптом.** `"$TRR" model-hash` показывает `version 4`, а `"$TRR" state get model_page` — `version 3`;
`check` отвечает `[BLOCKED] check: страница модели устарела (hash … ≠ модель …) — запустите
/task-readiness-review publish --model` и возвращает код 2. Ту же строку теперь печатает и `doctor`
(см. сценарий 21) — расхождения между диагностикой и проверкой больше нет.

**Причина.** `enrich`/`train` пересобрал модель, но страницу не переопубликовали. Гейт свежести требует,
чтобы `state.model_page.hash` совпадал с `checksum` актуальной модели.

**Что делать**

```sh
"$TRR" model-hash                 # version N, sha256 …
"$TRR" render-norm                # .md-зеркала из JSON
/task-readiness-review publish --model   # перепубликация + state.model_page
"$TRR" state get model_page       # hash и version должны совпасть с model-hash
```

Дополнительно: откат этапа в `trained` делает сам `"$TRR" calibrate --reason enrich` — вручную `stage`
не выставляй. Если `calibrate --reason enrich` напечатал `[WARN] state: этап не обновлён`, причина в
повреждённом `state.json` или в том, что флаг не дошёл до скрипта: исправь состояние и повтори команду.

## 16. `check` без модели

**Симптом.** `trr check` печатает `[BLOCKED] check: модель оценки не обучена — запустите
/task-readiness-review train` и возвращает код 2.

**Причина.** Гейт «нет модели / нет `state.model_page` → `BLOCKED`» выполняет CLI-обвязка `trr check`
(ядро правил модель не читает). Иначе получилась бы «проверка без возможности оценить».

**Что делать**

```sh
test -f .task-readiness/model/estimation-model.json || /task-readiness-review train
"$TRR" state get model_page
/task-readiness-review check E001-1234
```

Модель здесь обязательна: `trr check` не умеет работать «наполовину». Если нужна только проверка
полноты без оценки — сначала обучи модель (`/task-readiness-review train`), затем повтори `check`.

## 17. Контрольная сумма модели не совпадает с состоянием

**Симптом.** `"$TRR" model-hash` даёт `sha256:A`, `"$TRR" state get model_checksum` — `sha256:B`.

**Причина.** Модель пересобрана (или подменена) без обновления `state.json`; либо `state.json` откатили
из резервной копии.

**Что делать**


## 21. `doctor` зелёный, а `check` красный (свежесть страницы модели)

**Симптом.** `"$TRR" doctor` возвращает `0` и печатает `[OK] model_page: опубликована`, а
`/task-readiness-review check E001-1234` отвечает:

```text
[BLOCKED] check: страница модели устарела (hash 0a2162f0… ≠ модель 1b3c9d42…) — запустите /task-readiness-review publish --model
```

код `2`.

**Причина.** Гейт `check` требует не только `state.model_page ≠ null`, но и `state.model_page.hash ==
checksum` текущей модели. Раньше `doctor` смотрел только на факт публикации — после
`enrich`/`train` модель менялась, страница оставалась старой, и диагностика была зелёной при красной
проверке. Теперь `doctor` проверяет то же условие, что и гейт.

**Что делать.** Читай строку про страницу модели как вердикт гейта:

| Строка `doctor` | Код | Что значит |
|---|---|---|
| `[OK] state: страница модели соответствует модели (vN)` | `0` | hash совпал, `check` пойдёт |
| `[BLOCKED] страница модели устарела (hash … ≠ модель …)` | `2` | страница от предыдущей версии → `/task-readiness-review publish --model` |
| `[WARN] у state.model_page нет hash — свежесть не проверена` | `0` | запись до гейта: `check` тоже предупредит и пойдёт дальше; лучше перепубликовать |

```sh
"$TRR" doctor                        # строка про страницу модели — как у гейта
"$TRR" model-hash                    # version N, sha256 текущей модели
"$TRR" state get model_page          # что записано как опубликованное
/task-readiness-review publish --model      # перепубликация: обновляет hash и version
```

Обратное («`doctor` `[BLOCKED]`, а `check` зелёный») невозможно: условие одно и то же. Если видишь именно
так — команды смотрят в разные каталоги: сверь `--workdir`/`--root` у обоих запусков, а не ищи «мягкий»
`doctor`.

```sh

```

Дальше — по ответу:

```sh
"$TRR" calibrate                     # модель + .md-зеркала из norm/*, версия в model-history.jsonl
"$TRR" model-hash                    # checksum новой модели
```

## 24. Комментарий задублировался

наблюдений, поэтому сборка честно блокируется.

**Что делать**

1. Добавить спринты (`enrich`), пересобрать `norm/task-texts.json` и повторить `trr vectors build`.
2. Либо осознанно снизить порог: `--min-corpus N` или `min_corpus: N` в конфиге — но не ниже 30
   (пол в `config.validate_config`: `config.estimation.vector.min_corpus: N < 30` → `CONFIG_ERROR`, 3).
3. Не подкладывать тексты из чужого проекта: `idf` привязан к языку и предметной области.

## 35. Cosine высокий у одинаковых названий и низкий у похожих по смыслу

**Симптом.** Две разные задачи с одинаковым заголовком дают `cos ≈ 1.0`; две задачи про одно и то же,
но разными словами («терминология» vs «глоссарий»), — `cos` ниже порога.

**Причина.** Это лексическая близость, а не «понимание смысла»: документ = `summary` + `text`, word
TF-IDF + символьные 3–5-граммы, усечение терма до 6 символов. Одинаковый заголовок сам поднимает
косинус, а синонимы — разные термы.

**Что делать**

1. Проверить, что в `norm/task-texts.json` у задач есть `text` (описание), а не только `summary`:
   `python3 -c "import json;d=json.load(open('.task-readiness/norm/task-texts.json'));print([t['key'] for t in d['tasks'] if not t['text']])"`.
2. Пустые описания — не «норма»: задача без описания не различается вектором. Пересобрать тексты после
   того, как задачи дополнены.
3. Смотреть на `sp` соседей и на бакет (`same_bucket`), а не на `cos` как на вероятность.

## 36. Пороги выглядят странно

**Симптом.** `similar_threshold` очень низкий (`0.1`–`0.3`) или, наоборот, высокий; `vectors build`
печатает `[WARN] калибровка ненадёжна (пар < 50)`.

**Причина.** Пороги — процентили межбакетных косинусов **вашего** корпуса, а не универсальные константы:
`similar_threshold = p90`, `dissimilar_threshold = p50`. Мало задач или мало разных бакетов → мало пар →
`confidence: low`. Абсолютные `0.5`/`0.2` не используются намеренно.

**Что делать**

```sh
"$TRR" vectors calibrate        # пересчитать по текущим векторам
python3 -c "import json;print(json.load(open('.task-readiness/norm/task-vectors.json'))['calibration'])"
```

Пока `confidence: low`, `adjust_range: true` включать не стоит: порог — ориентир, а не измерение.
Лечение по существу — больше задач и больше разных `(role, work_kind)`.

## 37. `adjust_range: true` сдвинул оценку

**Симптом.** После включения `adjust_range: true` у роли вырос `range`, `confidence` стал `low`, в
`variability_reason` появилась строка `vector_nn: … диапазон расширен до [a, b]`, а итог `total.range`
изменился.

**Причина.** Это ожидаемое поведение этапа B: `range` расширяется до фактических SP соседей того же
бакета, у которых `cosine >= similar_threshold`; уверенность понижается, потому что интервал стал
шире. `base` и `expected` при этом **не меняются** — если они изменились, значит изменился не векторный
флаг, а входные данные (`validation.json`, `context.json`, модель).

**Что делать**

1. Посмотреть, кто именно расширил диапазон:

   ```sh
   python3 -c "import json;d=json.load(open('.task-readiness/runs/<KEY>/<RUN-ID>/estimate.json'));print(d['variability_reason']);print([ (r['role'],r['range'],r['confidence']) for r in d['roles']])"
   ```

2. Проверить `provenance` роли: `kind=vector_nn`, `source: task-vectors:<built_at>`, `detail: top-N: KEY@cos …`.
3. Если соседи чужие — выключить `adjust_range` (оставить справочную секцию 9) и разобраться с корпусом:
   `trr vectors similar --task <KEY>`.
4. Не «править» `range` в JSON: следующий `estimate` пересчитает его из модели и соседей.

## 38. Оценка тестовой задачи ниже ожидаемой (ресурсы не учтены)

**Симптом.** Задача фактически на написание тестов («покрыть тест-кейсами и автотестами»), а
`estimate` даёт 1–2 SP: `estimate.json → total.expected` не отличается от обычной задачи той же роли.
В `report.md` нет строки `Ресурсы: …`.

**Причина.** Надбавка за дополнительные ресурсы (правило `RS-01`) не применилась: либо ресурсы не
распознаны по тексту задачи, либо блок `estimation.resources` выключен, либо ресурс есть, но его
алиасов нет в каталоге. Правило добавляет `+1 SP` за каждый ресурс (allure для тест-кейсов, e2e для
автотестов) — или берёт верхнюю границу диапазона при `mode: upper_bound`.

**Что делать**

1. Посмотри `estimate.json → resources`:

   ```bash
   python3 -c "import json;e=json.load(open('.task-readiness/runs/<KEY>/<RUN-ID>/estimate.json'));print(json.dumps(e.get('resources','НЕТ КЛЮЧА'),ensure_ascii=False,indent=1))"
   ```

   - ключа нет → ресурсы не распознаны: проверь `estimation.resources.enabled` и алиасы;
   - ключ есть, но `count` меньше ожидаемого → часть ресурсов не нашлась.

2. Сверь `resources.items[].source` со снимком задачи (`context.json`): детекция смотрит только
   `fields.summary`, `description`, значения `sections{}`, `labels`, `issue_type`. Если нужный текст
   лежит в другом поле (например, во вложении или комментарии Jira), он не участвует — перенеси
   формулировку в описание/критерии приёмки или добавь алиас, который встречается в тексте.

3. Добавь алиас (или новый ресурс) в `estimation.resources.items` и перезапусти `estimate`:

   ```yaml
   estimation:
     resources:
       items:
         grafana: ["grafana", "дашборд"]
   ```

4. Помни про ловушку: алиас `автотест` **не** матчит слово «автоматизация». «Корректировка работы 14
   автоматизации» — это исправление самой автоматизации, а не написание автотестов; если по смыслу
   задача всё-таки про автотесты, формулируй это в описании явно.

**Чего не делать.** Не правь `estimate.json` руками и не «докручивай» `total` в отчёте: числа — зеркало
артефакта. Надбавка применяется только к основному исполнителю и **никогда** к производной QA-записи
(`source=derived`) — иначе двойной счёт; если кажется, что QA занижена, вопрос к QA-бакету модели, а не
к `resources`.

## 39. Синтетический полигон: как читать `summary.json`

**Симптом.** `trr synth-run` вернул `[OK]` или `[BLOCKED]`, в `summary.json` десятки чисел, и непонятно,
что из этого дефект, а что — ожидаемое поведение.

**Что считается дефектом (чинить).**

| Метрика | Порог | Что значит |
|---------|-------|-----------|
| `errors` / `unexpected_errors` | > 0 | исключение в `check`/`estimate` на валидном снимке. `error_examples[].traceback` — точка падения |
| `unestimable` | > 0 | `ValueError: ни одной роли с данными` — роль без бакетов уронила оценку. Оценка обязана деградировать, а не падать |
| `schema_failures.cases` | > 0 | артефакт не соответствует `schemas/*.json` — сломан контракт |
| `scale_violations.cases` | > 0 | `roles[].expected` вне шкалы `[1,2,3,5,8,13,21]` |
| `range_violations.cases` | > 0 | `expected` не внутри своего `range` |
| `param_violations.cases` | > 0 | `weight`/`heat`/`connectivity` вне `[0,1]` или NaN |
| `monotonicity.violations` | > 0 | рост параметра уменьшил `expected` (сломан множитель) |
| `determinism.equal` | `false` | один вход дал разные числа; `first_diff` — case_id |
| `buckets.reachable` | < `buckets.total` | селектор не умеет вернуть какой-то бакет модели — дефект `select_bucket` |
| `buckets.hit` | < `buckets.total` при датасете с покрытием | генератор не произвёл тройку `(role, issue_type, work_kind)` модели — дефект покрытия (`manifest.json` → `coverage.min_per_triple`) |
| `buckets.probe.hit` | < `buckets.probe.probes` | end-to-end проба бакета вернула чужой бакет |

**Что ожидаемо (не дефект).**

- **`blocked` — заметная доля.** Блокируют ровно два правила: `CL-01` (суть непонятна — снимок без
  описания и без секций) и `SA-08` (нет ни одного основания готовности — ни критериев, ни ожидаемого
  результата, ни объёма работ, ни цели, ни действия в заголовке). На `synth`-датасете с покрытием это
  ~5 % снимков (16 из 300 на прогоне `--count 300 --seed 42`), а не половина: версия 4 правил принимает
  описанный объём работ как основание. `SA-04` больше не блокирует даже на задачах с интеграциями: его
  провал влияет на точность оценки, но вердикт не меняет. Высокий `blocked` здесь измеряет строгость этих
  двух правил, а не ошибку вердикта. Проверка: `verdict` обязан быть `BLOCKED` ровно тогда, когда есть
  провал `REQUIRED`; `WARN` — когда провал только `RECOMMENDED`; `OK` — когда провалов нет (`OPTIONAL`
  вердикт не меняет).
- **`work_intent` и `fields.absent_in_project` на числа не влияют.** `work_intent[]` — справочная ось
  отчёта; её отсутствие или несколько сигналов не меняют ни `verdict`, ни `expected`. Поле
  `fields.absent_in_project` переводит `TPL-02/05/07/08/10/11` в `NA`: `NA` вердикт не меняет, поэтому
  `blocked`/`warn` от него не растут. Если `synth-run` показал иное — это дефект, а не ожидаемое
  поведение.
- **`total_off_scale`.** `total.expected` — сумма `roles[].expected`; по схеме `estimate` у неё нет
  `enum` (только `integer >= 0`). Когда у снимка несколько ролей, `13/21/29` — контракт, а не дефект.
  На шкале обязана быть каждая **роль**, и это проверяет `scale_violations`. На датасете с покрытием
  троек `total_off_scale = 0`: роль не указана → оценивается одна доминирующая роль
  (`role_assumed: true`), а не сумма всех ролей модели, поэтому `29/76 SP` больше не появляются.
- **`distribution.multi_role_cases`.** `> 0` законно только если снимок действительно описывает работу
  нескольких ролей (явный список ролей). Для `synth`-датасета это `0`: одна роль на снимок. Ненулевое
  значение на полигоне — признак того, что где-то снова суммируются роли молча.
- **`buckets.hit` < `buckets.reachable`.** `hit` — что реально встретилось в датасете, `reachable` —
  что селектор умеет вернуть. На датасете, собранном с покрытием троек (`trr synth --coverage-all-buckets`,
  по умолчанию), ожидаемо `hit = reachable = total = 20/20`: генератор гарантирует `--coverage-quota`
  снимков на каждую тройку. `hit < reachable` законен только для старого датасета или
  `--no-coverage-all-buckets`: осей выборки не хватает на все комбинации (у `QA` в выборке нет `Ошибка`
  и `Tech Debt`, а `QA/Feature`/`QA/Задача` исторически уходили в `testing`). Независимое
  доказательство достижимости — `buckets.probe`: на каждый бакет модели строится снимок
  `(role, issue_type, work_kind)` и `estimate` обязан вернуть тот же бакет; `probe.hit = probe.probes`
  = все бакеты достижимы.
- **`distribution.differs_from_sample`.** Оценка модели сравнивается с `sp` из выборки; расхождение на
  1–2 шага шкалы — норма (модель считает по бакету и множителю, а не воспроизводит исторический `sp`).
- **`timing.per_task_ms.p50`** — единицы миллисекунд; растёт при большом числе ролей в снимке.
- **`seed` в `summary.json`** берётся из `manifest.json` датасета; `null` — датасет собран без манифеста.

**Как разбирать.**

```bash
# сводка + подозрительные кейсы
python3 -c "import json;s=json.load(open('/tmp/trr-synth-out/summary.json'));print({k:s[k] for k in ('errors','unestimable','unexpected_errors','ok','warn','blocked')});print(s['error_examples']);print(s['buckets'])"

# конкретный кейс: входные оси и что посчиталось
grep '"SYN-000218"' /tmp/trr-synth/contexts.jsonl
grep '"SYN-000218"' /tmp/trr-synth-out/records.jsonl

# повтор на том же датасете (детерминизм): summary должен совпасть без timing
$TRR synth-run --dir /tmp/trr-synth --out /tmp/trr-synth-out2 --no-record
```

**Чего не делать.** Не «улучшать» `summary.json` подгонкой генератора или модели под ожидаемые числа:
`synth` детерминирован по `--seed`, и любое изменение датасета ломает сопоставимость «до/после».
Дефект — это нарушение инварианта (таблица выше), а не «некрасивое» распределение. Покрытие троек
(`--coverage-all-buckets`) — не подгонка чисел, а ось генератора: старый датасет не перегенерируется,
`buckets.hit` на нём остаётся прежним, а новый датасет собирается отдельно (`--seed 43`) и доказывает,
что каждая тройка модели производится.
