# Векторизация: похожие задачи по тексту

> **Статус: этап A реализован и включён по умолчанию на `train`** — `trr vectors build|similar|calibrate`,
> артефакты `norm/task-texts.json` и `norm/task-vectors.json`, справочная секция 9 в отчёте.
> `estimation.vector.enabled` по умолчанию `true`: `train` собирает векторы, `estimate` показывает
> аналоги без дополнительных флагов.
> Этап B (автокоррекция `range`/`confidence` по соседям) реализован за флагом
> `estimation.vector.adjust_range`, по умолчанию `false` — векторы справочные, числа не меняются.
>
> Исследование, числа эксперимента и обоснование калибровки:
> `docs/superpowers/specs/2026-11-17-task-readiness-review/VECTORIZATION.md`.
> Код: `scripts/trr_impl/vectors.py`, `scripts/trr_impl/estimate.py` (`_apply_vectors`),
> `scripts/trr_impl/report.py` (`similar_tasks_table`).

## 1. Что это даёт

Оценка в SP считается по бакету `(role, work_kind)`: медиана похожих задач в прошлом.
Бакет не различает **объём внутри одного вида работ** — «исследовать терминологию в UI»
(найти место и заменить тексты) и «исследовать внедрение поля из внешней ИС» (интеграция,
ADR, контракты, контакты, коммуникации, данные, бэкенд, UI) попадают в один бакет
`BE/research`, хотя объём различается в разы.

Векторы добавляют второй, более узкий взгляд: **какие конкретные закрытые задачи похожи
на эту по тексту** и сколько они стоили.

| Что делает (по умолчанию) | Чего не делает |
|---|---|
| пишет `similar_tasks[]` в `estimate.json` (top-N по косинусу) | не меняет `base`, `expected`, `range`, `confidence` |
| рендерит справочную секцию 9 в отчёте | не публикует тексты задач наружу |
| пишет `provenance kind=vector_nn` на каждую роль | не заменяет бакетную статистику |

При `adjust_range: true` (осознанное решение, см. §6) добавка такая:

| Что делает | Чего не делает |
|---|---|
| расширяет `range` до фактических SP соседей того же бакета | не сужает диапазон и не меняет `base`/`expected` |
| понижает `confidence` до `low` | не повышает уверенность |
| дописывает причину в `variability_reason` | не трогает `provenance` соседей |

## 2. Как это работает (включено по умолчанию на `train`)

Векторы строятся на этапе `train` — дополнительных действий не требуется:

1. **Собрать тексты задач** — `norm/task-texts.json`. Тексты вычитывает **агент** из Jira
   (Python в сеть не ходит): по каждой задаче выборки `key`, `summary`, `text`, `role`,
   `work_kind`, `issue_type`, `sp`, `qa_estimation`, `has_testing`, плюс `built_at` и
   `source{sprints[], retrieved_at}`. Формат — `schemas/task-texts.schema.json`.
   В `norm/sprint-sample.json` текста нет (там только `summary_sha256`), поэтому файл
   отдельный.
2. **Собрать векторы** — `trr vectors build`. Порог корпуса по умолчанию `min_corpus: 30`;
   явно: `trr vectors build --min-corpus 30`. Калибровка порогов считается тут же и
   записывается в артефакт.
3. **Пересчитать пороги (опционально)** — `trr vectors calibrate`. Нужен, если артефакт
   собран раньше или корпус изменился без пересборки: `build` уже пишет калибровку.
4. **Проверить глазами** — `trr vectors similar --task <KEY>` (или `--text "…"`). Если top-5
   выглядят чужими, включать `adjust_range` нельзя.
5. **Этап B (осознанно)** — `estimation.vector.adjust_range: true`, только после шага 4.
   Этап A работает без него.

```yaml
estimation:
  vector:
    enabled: true          # по умолчанию true: векторы строятся на train
    adjust_range: false    # по умолчанию false: векторы — только справка
    top_k: 5
    min_corpus: 30
    top_terms: 15
    weight_word: 0.5
```

Порядок в конвейере:

```
train  →  тексты задач (агент)  →  trr vectors build  →  trr vectors calibrate
       →  check  →  estimate (similar_tasks[])  →  report (секция 9)
```

Если `estimation.vector.enabled: true`, а `norm/task-vectors.json` нет — `train` считается
незавершённым (это не тихий пропуск: `estimate` печатает `[WARN]`, `doctor` показывает
проблему). Отключить векторы можно явным `enabled: false`.

`vectors build` **не требует** пересчёта модели: ему нужен только
`norm/task-texts.json` (роли/SP берутся из самих текстов).

## 3. Пороги: только калибровка

| Что | Как считается |
|---|---|
| `similar_threshold` | `p90` косинусов **ненулевых** пар задач из **разных** бакетов `(role, work_kind)` |
| `dissimilar_threshold` | `p50` тех же ненулевых межбакетных пар |
| `method` | `p90_inter` (в артефакте, не в конфиге); `p90_inter_all` — ненулевых пар мало |
| `dissimilar_method` | `p50_inter`; `p50_inter_all` — ненулевых пар мало |
| `pairs` | сколько межбакетных пар посчитано (включая нулевые) |
| `pairs_nonzero` | сколько из них дали косинус > 0 — по ним и считаются процентили |
| `confidence` | `high` при `pairs_nonzero >= 50`, иначе `low` + `[WARN] калибровка ненадёжна (ненулевых пар N < 50)` |

**Нули не участвуют в процентилях.** Нулевой косинус означает «общих термов нет», а не «не
похожи»: при `top_terms: 15` на демо-корпусе нулевых межбакетных пар ~92 % (`pairs_nonzero`
= 1629 из 20400), и процентиль по всем парам вырождается в `0.0` — порог перестаёт отсекать
что-либо. Если ненулевых пар меньше `MIN_CALIBRATION_PAIRS` (50), включается прежнее
поведение: процентили считаются по всем парам, `confidence: low`, `method`/`dissimilar_method`
получают суффикс `_all`.

**Абсолютные пороги `0.5` / `0.2` экспериментом опровергнуты — не использовать.** В конфиге
ключей `similar_threshold`/`dissimilar_threshold` нет вообще: пороги приезжают только из
`calibration` артефакта.

Факт контейнерного прогона на демо-корпусе (30 задач, `tests/container/mock`), у другой
команды будут свои числа:

| Пара | cosine |
|---|---|
| `A ↔ A'` (одна тема, разные формулировки) | `0.8967` |
| `B ↔ B'` (та же тема, почти тот же текст) | `1.0000` |
| `A ↔ B` (разные темы) | `0.0411` |
| `similar_threshold` (p90 inter, 403 пары) | `0.2496` |
| `dissimilar_threshold` (p50 inter, 403 пары) | `0.1722` |

## 4. Что видно в отчёте

Секция рендерится **только если `similar_tasks` непусто**:

```
## 9. Похожие задачи (справочно)

| Задача | cosine | SP | Роль | Вид работ | Тот же бакет |
|---|---|---|---|---|---|
| E001-90002 | 0.8967 | 5 | BE | research | да |
```

- `enabled: false` → секции нет, нумерация отчёта 1–8.
- `enabled: true`, но `similar_tasks` пусто (нет артефакта, малый корпус, пустой текст
  задачи) → секции тоже нет: отчёт остаётся 1–8.
- Секция справочная: она не объясняет числа, а показывает, на что смотреть человеку.

`trr vectors similar` печатает ту же таблицу в stdout:

```
cos     key          role  work_kind       sp
0.8967  E001-90002   BE    research        5
```

## 5. Что нужно, чтобы `similar_tasks` появились

| Условие | Что будет, если нет |
|---|---|
| `estimation.vector.enabled: true` | секции нет, `similar_tasks` не пишется |
| `norm/task-vectors.json` существует | `[WARN] estimate: векторы включены, но norm/task-vectors.json нет — запустите trr vectors build; оценка без похожих задач` |
| `calibration.corpus_rows >= min_corpus` | `[WARN] estimate: корпус векторов N < min_corpus 30 — похожие задачи не ищутся, добавьте спринты через enrich` |
| текст задачи не пуст (`summary`/`description`/`sections` снимка) | `similar_tasks` пусто |

Все четыре случая — `WARN`, а не ошибка: оценка считается как обычно, числа не меняются.

## 6. `adjust_range: true` — что именно меняется

Флаг включает единственную обратную связь векторов на числа. Для каждой роли:

1. берутся соседи с `same_bucket = true`, тем же `role`, непустым `sp` **и** `cosine >= similar_threshold`;
2. из их SP собираются точки шкалы; `range` расширяется до `[min(было, min(точки)), max(было, max(точки))]`;
3. если диапазон расширился — `confidence` становится `low`;
4. в `variability_reason` дописывается строка
   `vector_nn: N похожих задач в бакете BE/research (cosine >= 0.2496), диапазон расширен до [5, 8]`.

Инварианты:

- `base` и `expected` не меняются **никогда**;
- диапазон только расширяется, не сужается;
- уверенность только понижается, не повышается;
- нет соседей в том же бакете выше порога — изменений нет;
- нет `calibration.similar_threshold` в артефакте — правка пропускается целиком (fail-safe):
  `[WARN] vectors: в артефакте нет calibration.similar_threshold — adjust_range пропущен`, числа как
  при `adjust_range: false`. Порог `0.0` «по умолчанию» означал бы «любой сосед подходит» и подменял
  бы оценку молча.

## 7. Как читать `provenance kind="vector_nn"`

```json
{
  "field": "similar_tasks",
  "kind": "vector_nn",
  "source": "task-vectors:2026-11-17T09:41:07Z",
  "detail": "top-5: E001-90002@0.8967, E001-90005@0.4123, …"
}
```

| Часть | Что означает |
|---|---|
| `kind: "vector_nn"` | соседи найдены по тексту, а не по эталону и не по бакету |
| `source: "task-vectors:<built_at>"` | каким артефактом искали; после пересборки строка меняется |
| `detail: "top-N: KEY@cos, …"` | ключи соседей и косинусы — можно проверить руками |

Запись добавляется на **каждую** роль в `estimate.json`, даже когда `adjust_range: false`:
видно, что соседи были и на числа не повлияли.

`cos` — «похожесть по словам и n-граммам», не вероятность. Смотрите на `sp` соседей, а не на
`cos`: пять соседей со `sp = 13` при `cos = 0.15` — повод перечитать задачу, а не ставить 13.

## 8. Чего НЕ ждать

| Ожидание | Реальность |
|---|---|
| «Понимает смысл» | Это **лексическая близость**: word TF-IDF (`w:`) + символьные 3–5-граммы (`c:`) с усечением терма до 6 символов. Синонимы («поле» / «атрибут» / «реквизит») — разные термы, близость между ними не появится |
| «Эмбеддинги» | Внешних моделей и API нет, только stdlib. Вектор — разреженный словарь `top_terms` термов на задачу |
| «Различит одинаковые заголовки» | Документ склеивается как `summary + text`. Одинаковые названия сами по себе поднимают косинус: у пары с совпадающим заголовком и почти совпадающим описанием `cos = 1.0000` |
| «Заголовок поможет» | Заголовок — слабый различитель: одинаковые названия у разных задач дают высокий `cos`. Основной вес — на тексте описания (он длиннее и даёт больше термов); отдельного ключа «вес заголовка» в конфиге нет |
| «Работает на коротких описаниях» | Короткое описание — шум: пара «своих» может оказаться ниже порога, а пара «чужих» — выше. Порог лечит статистику, а не отсутствие текста |
| «Починит оценку» | По умолчанию меняет только справку. При `adjust_range: true` — только ширину диапазона и уверенность |
| «Работает на любом языке» | Нормализатор `ru-lower-e-strip-truncate-v1`: lowercase, `ё → е`, русский стоп-список, усечение до 6 символов. Артефакт с другим `normalizer.id` не используется — `[MISSING]` и просьба пересобрать |
| «Найдёт аналог всегда» | В корпусе 30 задач — 403 межбакетные пары; на такой выборке калибровка `high`, но сам поиск грубый. Комфортно от сотен задач |
| «Заменит разговор с командой» | Как и вся модель: число — вход в планирование, решение за людьми |

## 9. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `[BLOCKED] vectors: корпус N меньше min_corpus — добавьте спринты через enrich` (2) | задач в `task-texts.json` меньше `min_corpus` | добавить спринты (`enrich`), пересобрать тексты; `min_corpus` ниже 30 не поставить: схема допускает `minimum: 1`, но семантическая проверка (`config.validate_config`) требует ≥ 30 и отвечает `CONFIG_ERROR` (3) строкой `[MISSING] config.estimation.vector.min_corpus: N < 30 — ниже нижней границы корпус не даёт надёжной калибровки` |
| `[MISSING] norm/task-texts.json — сначала соберите тексты задач (train/enrich)` (4) | файла нет | агент вычитывает тексты из Jira и пишет файл по `task-texts.schema.json` |
| `[MISSING] norm/task-texts.json — …` (5) | файл есть, но не по схеме / не читается | `trr validate task-texts <path>` и перезаписать |
| `[WARN] калибровка ненадёжна (пар < 50)` (0) | межбакетных пар меньше 50 → `confidence: low` | больше задач и разных бакетов; пороги пока считать ориентиром |
| `[MISSING] norm/task-vectors.json — запустите trr vectors build` (4) | артефакта векторов нет | `trr vectors build` |
| `[MISSING] vectors similar: задачи KEY нет в корпусе` (4) | задача не входит в собранный корпус | `trr vectors build` после добавления текста, либо `--text`/`--text-file` |
| `[BLOCKED] vectors similar: укажите --task <KEY>, --text-file <path> или --text "<строка>"` (2) | не задан запрос | передать один из трёх |
| `[WARN] --same-bucket: у текста нет бакета — фильтр не применён` (0) | `--same-bucket` с `--text`: бакета у строки нет | использовать `--task` |
| `[MISSING] нормализатор артефакта … ≠ …` (5) | артефакт собран другой версией нормализатора | `trr vectors build` заново |
| Секция 9 не появилась | `enabled: false`, нет `task-vectors.json`, корпус < `min_corpus` или пустой текст задачи | смотреть `[WARN]` в выводе `estimate`; см. `troubleshooting.md` §33 |

## 10. Экспорт и перенос между командами

`norm/task-texts.json` и `norm/task-vectors.json` входят в `trr artifact pack` (порядок
`FILE_ORDER`: `… task-texts.json, sprint-stats.json, task-vectors.json …`). Поэтому бандл
переносит и векторы: на новом месте `similar` работает сразу, если
`calibration.corpus_rows >= min_corpus` — пересборка не нужна.

Важно: `task-texts.json` — **потенциально чувствительные данные** (описания задач). При
экспорте в общий GitLab/Confluence это осознанное решение команды. Отдельного ключа «не
класть тексты в бандл» в конфиге нет: `artifacts.include_sprint_sample` управляет только
`norm/sprint-sample.json`. Если тексты не должны уезжать — файл исключается из бандла вручную
(собрать архив без него), и тогда векторы в бандле остаются без источника для пересборки.

Переносить один `task-vectors.json` в другой проект бессмысленно: `idf` привязан к языку и
предметной области. Переносится **код**, а `trr vectors build` пересобирает артефакт на своих
данных за миллисекунды.
