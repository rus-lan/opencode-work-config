# Правила проверки готовности задачи

Человекочитаемое зеркало каталога `check.CHECKS` (id-в-id). Источник истины —
данные в коде: `skills/task-readiness-review/scripts/trr_impl/check.py`.
Изменение каталога требует **бампа `RULES_VERSION`** и golden-теста
(`tests/test_check.py`), иначе прогоны разных версий правил станут неотличимы.

Версия правил: `check.RULES_VERSION` = `4` (rules version 4).

Что изменилось в версии 4: `SA-08` принимает **объём работ** — раздел «Решение» /
«Задача» / «Необходимо» / «Тех.решение» (и английские `task`/`solution`) либо
строку «необходимо/нужно + глагол действия» в описании — как самостоятельное
основание готовности; заголовок с действием (инфинитив) стал последним фолбэком.
Разбор заголовков расширен (`*Заголовок:*`, `*Заголовок*:`, `{*}…{*}`, `h3.`,
`h2.`). Появились две новые оси, не влияющие на вердикт и числа: `work_intent`
(что делается: миграция структуры БД vs перенос данных и т.п.) и
`context.fields.absent_in_project` (поля, которых нет в проекте задачи, → `NA`).
Состав правил, severity и формула оценки не менялись.

Что изменилось в версии 3: `SA-08` расширен — критерий приёмки может быть
**результатом работ** («подготовлены тест-кейсы», «проведено ревью», «настроен
алерт»), а источниками содержания стали, помимо «Критериев приёмки» и
«Ожидаемого результата», раздел «Цель» и заголовок задачи (заголовок — только
последний фолбэк). Состав правил и severity не менялись.

Что изменилось в версии 2: каталог разделён на **содержательные** правила
(`CL-*`, читают `analysis.analyze`) и **гигиену шаблона** (`TPL-*`, `SA-*`).
Блокируют только `CL-01` (суть задачи непонятна) и `SA-08` (нет ни одного
критерия приёмки — ни измеримого, ни фиксирующего результат работ, — и нет
ожидаемого результата/цели задачи); остальные правила дают `WARN` и влияют на
точность оценки, а не на право задачи быть оценённой.

## Каталог проверок

Колонки: `id` → severity → раздел шаблона → что проверяется → кому адресован
вопрос (`target_role`) → как формируется вопрос → где искать ответ.

`Severity` — ровно значение поля `severity` правила. Условных повышений
severity в каталоге нет: `SA-04` больше не эскалируется до `REQUIRED` при
изменении интеграций (механизм `escalate` в `run_checks` сохранён для будущих
правил, но ни одно правило его не использует). В `validation.json` всегда
виден фактический `severity` конкретной проверки. `QA-01` условным не является:
правило всегда `PASS`, а `has_testing` решает только, появится ли QA-запись в
оценке. QA-оценка нужна только для типов из `validation.qa_required_issue_types`
(по умолчанию Feature/Ошибка); для остальных типов (Задача, Tech Debt, ADR,
Релиз, Дизайн) проверку результата выполняет исполнитель — QA-записи нет, а в
`estimate.json` появляется `qa_scope`.

## Каталог и CONTRACT.md §6.4

`CONTRACT.md` §6.4 содержит тот же каталог, что и `check.CHECKS` (rules version
1): `TPL-01…TPL-11`, `TPL-09a`, `SA-01…SA-09`, `QA-01`, `FT-01`,
`DEP-01…DEP-03`. Других идентификаторов правил нет: «смысловые» id ранних редакций
контракта (точечные псевдонимы вида `desc.<поле>`, `handoff.<поле>`, `dod.<поле>`,
`toggle.<поле>`) упразднены и в коде не существуют.

Сверка автоматическая: `tests/test_check.py` парсит таблицу выше и сравнивает
множество id, `severity`, `target_role`, `question` и `where_to_find` с
`check.CHECKS`. Расхождение — падение теста, а не «документация отстала».

## Условия применимости и эскалации

`condition` — мини-DSL: `поле=значение1|значение2` (через `&` для конъюнкции,
`!=` для отрицания), поля только из `context.json`: `issue_type`, `role`,
`work_kind`, `has_testing`, `labels`. Невыполненное условие → `status=NA`,
правило не влияет на `verdict`.

### `has_testing`

`has_testing` отвечает на вопрос «нужна ли в оценке отдельная QA-запись».
Решает **тип задачи**, а не текст: QA требуется только для типов из
`validation.qa_required_issue_types` (по умолчанию Feature/Ошибка).
`has_testing = true`, если выполнено любое (порядок проверки — как в
`detect_has_testing`):

1. `fields.qa_estimation` заполнено — явное решение человека уважается всегда;
2. тип задачи (`issue_type`, strip + casefold) входит в
   `validation.qa_required_issue_types` (по умолчанию `Feature`, `New Feature`,
   `Фича`, `Ошибка`, `Bug`, `Дефект`).

Иначе `has_testing = false`: у типов **Задача, Tech Debt, ADR, Релиз, Дизайн**
QA-оценки нет — исполнитель (роль из поля «Роль») выполняет полный объём,
включая проверку результата. Сигналы тестирования в тексте/метках/разделе
(`тест`, `автотест`, `test`, `qa`, `покрыть тестами`, `регресс`; метки `qa`,
`test`, `testing`, `autotest`, `автотест`; раздел «Тестирование») остаются
только **информационной пометкой** в причине и QA не включают:

```text
тип задачи «Tech Debt» не требует QA-оценки: объём исполнителя (роль FE)
включает проверку результата; в тексте есть сигнал «тест», но тип задачи
не требует QA-оценки
```

Причина фиксируется (`detect_has_testing` → `(bool, reason)`) и попадает в
сообщение проверки QA-01. **На severity QA-01 `has_testing` не влияет:** правило всегда
`PASS` (severity `RECOMMENDED`, kind `qa_estimation`) — заполненное поле даёт факт из Jira,
пустое при требуемом QA — `evidence: "derived"` и сообщение «QA Estimation не заполнена — будет рассчитана моделью».
От `has_testing` зависит только то, появится ли в оценке запись `role=QA` (`estimate._qa_entry`).

Раньше (rules version 2) текст и метки сами включали QA: задача «Покрыть эпик
тест-кейсами и автотестами» типа Tech Debt получала QA-запись (кейс
E001-31353). Правило изменено: объём такой задачи — работа исполнителя, а не
отдельная QA-оценка.

### `SA-08`: основание готовности — критерии, объём работ, цель, заголовок

Задача проверяема, если из неё понятно **что должно получиться** или **что надо
сделать**. `SA-08` ищет основание по приоритету и останавливается на первом
найденном:

1. раздел «Критерии приёмки» (`sections.acceptance_criteria`);
2. раздел «Ожидаемый результат» / «Expected result» / «Ожидаемое поведение» /
   «Как должно работать» — эквивалент критериев: терминология команд разная,
   требование одно;
3. **объём работ** — раздел «Решение» / «Тех.решение» / «Задача» / «Что нужно
   сделать» / «Необходимо» / «Перечень работ» / «Изменения» (канонические ключи
   `sections{}`: `task`, `solution`, `work scope`, `scope of work`, `what to do`)
   либо строка описания, где маркер долженствования («необходимо», «нужно»,
   «требуется», «следует», «надо») стоит рядом с глаголом действия
   («реализовать», «добавить», «настроить», «перенести», «выгрузить», …). Блок
   короче 20 символов основанием не считается: «Сделать» — не объём работ;
4. раздел «Цель» (`sections.goal`) — критерии в части задач фиксируются как
   **результат работ**, и тогда цель задачи вместе с заголовком описывает
   готовность полнее, чем отсутствующий раздел критериев;
5. заголовок задачи с действием — **последний фолбэк**: в заголовке есть
   инфинитив действия («Убрать лот доставки», «Создать тикет»). «Создание
   тикета» и «Поддержка продукта» — тема, а не действие, и основанием не
   считаются.

Заголовок не подменяет критерии: если раздел есть, оценивается раздел, а
заголовок добавляется лишь как контекст к цели.

Критерий **измерим**, если в строке (не короче 15 символов) есть число, порог,
процент, срок, «должен/должна/должно» **или** описание наблюдаемого поведения в
нормальном состоянии: «не срабатывает», «не перезаписывает», «отображается»,
«возвращает», «формирует», «создаёт», «сохраняет», «работает», «остаётся»,
«становится», «доступен», «успешно», «без ошибок», «корректно», «как ожидалось».

Критерий **как результат работ** (`analysis.deliverable_criteria`) фиксирует
созданный/изменённый артефакт, а не поведение системы: глагол
создано/подготовлено/проведено/настроено/написано/покрыто/задокументировано/
согласовано/внедрено/исправлено/удалено/переименовано/обновлено **плюс**
существительное тест-кейс/автотест/ревью/документация/алерт/дашборд/скрипт/
миграция/инструкция/чек-лист. Для задач на тест-аналитику, документацию и
инфраструктуру это нормальная и полная формулировка готовности: «По фиче
подготовлены тест-кейсы», «Проведено ревью тест-кейсов», «Настроен алерт на
ошибки».

Сообщение проверки называет фактически использованный источник:
`критериев: N (измеримых X, как результат работ Y; раздел «Критерии приёмки»)`;
`объём работ описан (раздел «Решение»): …`; `объём работ описан в описании:
«Необходимо …»`; `что делать названо в заголовке задачи: «…» — …`. Когда
источник — сам заголовок: `критерий взят из заголовка задачи (N): …`.

`PASS` — найдено любое из оснований 1–5. `FAIL` — только когда нет ни одного:
нет критериев, нет ожидаемого результата, нет объёма работ, нет цели и в
заголовке нет действия. Сообщение так и говорит: «нет критериев приёмки,
ожидаемого результата, объёма работ и действия в заголовке задачи — не понять,
что делать и как проверять». Если раздел критериев есть, но бессодержателен,
`FAIL` уточняет: «<источник> есть, но ни один критерий не измерим и не описывает
результат работ…; объёма работ и действия в заголовке в задаче нет».

Зачем это: в корпусе 223 задач 101 задача (45 %) блокировалась `SA-08` только
потому, что работа описана в разделе «Задача»/«Решение», а не в «Критериях
приёмки». После версии 4 блокировок стало 85 (38 %) вместо 186 (83 %), и ни одна
задача не получила `PASS` без основания.

### `work_intent`: что делается (ось отчёта, не вердикта)

`analysis.work_intent(context)` отвечает на вопрос «что за работа», чтобы отчёт
и комментарий говорили «понято как перенос данных», а читатель не угадывал по
заголовку. Восемь intent-ов: `schema_migration` (миграция структуры БД),
`data_migration` (перенос данных), `data_export` (выгрузка), `dashboard`
(дашборд/графики), `integration` (интеграция/контракт), `refactor`
(рефакторинг/перенос кода), `test_coverage` (тесты/покрытие), `research`
(исследование/проработка).

Источники — заголовок, описание и `sections{}`, **кроме «Цели»**: строка
`*Цель:*` часто общая для эпика и даёт одинаковый ложный сигнал всем его задачам.
Веса: сильный признак заголовка `3.0`, сильный признак текста `2.0`, слабый
признак текста `1.0`; `high` — ≥ 3.0, `medium` — ≥ 2.0, иначе `low`.
Анти-признак гасит совпадение **только в своей строке**: «схема обработки
тикета» — бизнес-схема, а не схема БД.

**Миграции различаются по смыслу, а не по слову.** «Реализовать миграцию
**данных**» (`insert into`, «загрузить», «наполнить», «бэкфилл») —
`data_migration`; «реализовать **миграции**» (`alter table`, `create table`,
«создать схемы», `primary key`) — `schema_migration`. Миграционные intent-ы
повышаются до `high`, если в заголовке есть домен БД (БД, база данных, таблица,
схема, cassandra/postgres/clickhouse/mysql/elastic, данные): «описать задачи по
миграции БД» — проработка миграции, а не проработка вообще.

Результат — `validation.json → work_intent[]` (`intent`, `confidence`,
`evidence`, `source`), отсортированный по силе сигнала, затем по приоритету
каталога, затем по имени. На вердикт и числа оценки ось **не влияет**; в отчёте
она печатается строкой «Что делается: …» (§1), в комментарии — «Понято как: …»,
в CLI — `[INFO] intent: …`.

### Поля, которых нет в проекте (`fields.absent_in_project`)

`context.fields.absent_in_project` — необязательный список полей, которых в
проекте задачи **нет** (например, в проекте не используется «Команда» или
«Эпик»). Принимается строка или список; имена сравниваются нормализованно
(регистр, `ё`, пробелы). Правила `TPL-02` (Команда), `TPL-05` (Эпик), `TPL-07`
(Роль), `TPL-08` (Связи), `TPL-10` (Sprint), `TPL-11` (Story Points) отвечают
`NA` с сообщением «поле «X» отсутствует в проекте задачи — проверка не
применима». «Поля нет в проекте» и «поле не заполнено» — разные факты:
требовать заполнить несуществующее поле нельзя. Ключа нет — поведение прежнее.
Содержательные правила (`SA-*`, `CL-*`) этот список не читают.

### `SA-04`: контракт не эскалируется

`SA-04` всегда `RECOMMENDED` — в том числе когда задача меняет интеграции
(метки `api`, `contract`, `contracts`, `api-contract`, `integration`,
`integrations`, `integration-api` или оборот «изменение/правка/новая/доработка
контракта/API/интеграции» в описании). Раньше такой признак повышал severity до
`REQUIRED`; повышение отменено политикой: блокируют ровно `CL-01` и `SA-08`.

Влияние на оценку при этом не теряется:

- сообщение `SA-04` при `FAIL` содержит пометку «влияет на точность оценки (не
  блокирует)», а для интеграционной задачи — ещё и «задача затрагивает
  интеграции — контракт критичен для точности»;
- признак интеграций остаётся сигналом `integration_labels` в
  `params.derive` и виден в отчёте.

Механизм `escalate: integration` в `run_checks` сохранён для будущих правил, но
ни одно правило каталога его сейчас не использует.

### `FT-01`: когда требуется скоринг

Правило применимо, если `issue_type` ∈ {`Feature`, `New Feature`, `Фича`} или
есть метки `feature`, `toggle`, `feature-toggle`. Скоринг считается
приложенным, если найдена секция «Feature-toggle» / «Фича-тоггл» / «Скоринг
тоггла», вложение с `toggle`/`scoring` в имени, либо таблицы «Риск поломки» и
«Неопределённость» в описании. Иначе — `NA`.

### `DEP-01…DEP-03`: документация зависимостей

Проверяются только при `with_dependencies=true`. Если затронутых контрактов не
указано (`context.dependencies`), правила дают `NA`. Разделы ищутся в
`context.documentation` / `context.docs` / `context.dependencies` и в описании.

## Определение «поле заполнено»

Поле считается заполненным, если значение:

- не `null`;
- для строки — непустая строка после `strip()`, не `N/A`, `n/a`, `н/д`, `нд`,
  `none`, `null`, `нет`, `-`, `—`, `–`, `?`;
- для числа — не `0`;
- для списка/словаря — непустая коллекция.

Для `description` действует отдельный порог: `MIN_DESCRIPTION_CHARS = 200`.

## Как ищутся секции (SA-01…SA-09, TPL-09a, FT-01)

1. Приоритет — `context.sections[<key>]`, если агент уже извлёк блок.
2. Иначе — разбор `context.description`:
   - жёсткие заголовки `### Цель`, `h3. Цель`, `**Цель**`, `**Цель:**`,
     `*Цель:*`, `*Цель*:`, `{*}Цель{*}` — всегда;
   - мягкий заголовок `Цель: значение` — только если начало строки похоже на
     название раздела шаблона (иначе фраза с двоеточием рвала бы блок);
   - сравнение без учёта регистра, `ё` = `е`, с допуском хвоста
     («Сценарии / Альтернативные сценарии» матчится алиасом «сценарии»):
     заголовок совпадает с алиасом, если равен ему или начинается с него, причём
     алиас не короче 4 символов — иначе «AC» ловил бы «ACL».
3. Секция с пустым содержимым считается отсутствующей; поиск продолжается по
   следующим блокам.

Алиасы по умолчанию — `check.DEFAULT_SECTIONS` (совпадают с заголовками
`templates/sa-handoff-checklist.md`). Алиасы «объёма работ» (`analysis.WORK_SCOPE_ALIASES`)
продублированы в `DEFAULT_SECTIONS["work_scope"]`: `check` импортирует `analysis`,
обратный импорт дал бы цикл, поэтому копии синхронны вручную — расхождение ловит
`trr selftest`.

## Вердикт

| Условие | Вердикт |
|---|---|
| есть `FAIL`/`UNKNOWN` с severity `REQUIRED` | `BLOCKED` |
| есть `FAIL`/`UNKNOWN` с severity `RECOMMENDED` | `WARN` |
| иначе | `OK` |

`NA` не влияет на вердикт. `OPTIONAL` не влияет на вердикт **и** не попадает в
`gaps[]`: это гигиена полей Jira и «похвала» (`CL-06`, `CL-07`). Иначе `OK` был
бы недостижим — например, из-за пустого поля «Роль» или `clarity < 0.70`.

Политика версии 2: `BLOCKED` — только за два (`CL-01` — суть задачи непонятна,
`SA-08` — нет ни одного основания готовности: ни критериев, ни ожидаемого
результата, ни объёма работ, ни цели задачи, ни действия в заголовке). Всё
остальное — `WARN` с
влиянием на точность; оценка выдаётся всегда. `SA-04` (Контракт) входит в
«остальное»: ни метки интеграций, ни обороты «меняем контракт/API» не делают его
блокирующим.

### Штрафы модели (`gap_rules`) после версии 2

| Правило | Условие | Статус после версии 2 |
|---|---|---|
| `GR-01` | `SA-08=FAIL` | срабатывает только при `SA-08=FAIL` (нет ни одного основания готовности: критериев, ожидаемого результата, объёма работ, цели, действия в заголовке) — в корпусе это 85 задач из 223 |
| `GR-02` | `SA-04=FAIL` | не срабатывает при текущем каталоге правил: `SA-04` всегда `RECOMMENDED`, а `estimate._penalties` смотрит только `gaps[]` с severity `REQUIRED` |
| `GR-03` | `TPL-07=FAIL` | не срабатывает при текущем каталоге правил: `TPL-07` — `RECOMMENDED`, `_penalties` берёт только `REQUIRED`-пробелы |
| `GR-04` | `QA-01=FAIL` | не срабатывает при текущем каталоге правил: `QA-01` всегда `PASS` (QA считается моделью только для типов Feature/Ошибка) |

Модель из-за этого **не переобучается**: `gap_rules` — данные модели, штраф
применяется к уже посчитанной базе. Изменение — ожидаемое следствие смены
политики severities, а не дефект.

## Пробелы и вопросы

- `gaps[]` — по одной записи на `FAIL`/`UNKNOWN` с severity ≠ `OPTIONAL`,
  сортировка по `id`.
- `questions[]` — `id = "q." + id пробела`, `blocking = (severity == REQUIRED)`,
  сортировка по `id`.
- `comment_draft_path` — `comment-draft.md` в директории прогона.
- Черновик комментария (`render_comment_draft`) содержит секции «Чего не хватает
  для оценки (блокирует)», «Что стоит уточнить», «Где искать недостающее»;
  `@`-упоминания и выдуманные контакты запрещены — только роли и места.

## Переопределение шаблона

```yaml
# task-readiness-review.yaml
templates_dir: templates
override_template: .task-readiness/my-task-template.md
```

- Канонический путь ключа — **верхнеуровневый** `override_template`. Форма
  `sources.override_template` принимается только для обратной совместимости:
  `config.py` переносит значение наверх и печатает
  `[WARN] sources.override_template устарел — используйте override_template`.
- Путь относительный — считается от корня скилла; абсолютный берётся как есть.
- Заголовки файла классифицируются по ключевым словам: «Цель/Назначение» →
  `goal`, «Требовани…» → `ba_requirements`, «Контракт/API/Спецификация» →
  `contract`, «Сценари…» → `scenarios`, «Критерии/Приёмка» →
  `acceptance_criteria`, «Описани…» → `description`, «Задач…» → `task`,
  «Корректировки/Изменения/Версии» → `adjustments`, «Тестирование/Проверка» →
  `testing`, «Toggle/Тоггл/Скоринг» → `toggle`.
- Секции, которых в файле нет, сохраняют алиасы по умолчанию.
- Нечитаемый/отсутствующий файл — ошибка (`CheckError`), а не тихий откат на
  штатный шаблон: иначе проверка пойдёт по чужим правилам.
- В `validation.json` блок `template` = `{name, version, sha256}` **фактически
  использованного** файла (версия — из `version:` frontmatter, иначе `1`).

## Отклонения от CONTRACT.md

| Что | Решение | Причина |
|---|---|---|
| `checks[].evidence` | пустая строка вместо `null` | `validation.schema.json` требует `string`; `null` даёт `SCHEMA_ERROR` |
| Пункты «макет», «комментарии», DoD по отдельности | не входят в каталог | в каталоге rules version 2 их нет; добавление = бамп `RULES_VERSION` |
| `analysis` в `validation.json` / `estimate.json` | необязательное поле | артефакты до версии 2 остаются валидными; отсутствие анализа = нет блока «Что видно из задачи» |

Гейт модели — не отклонение, а норма: без `model/estimation-model.json` или без `state.model_page` команда
`check` возвращает `[BLOCKED]` и код 2 (гейт выполняет CLI-обвязка `trr check`, ядро правил модель не читает).
Если страница опубликована, но её `hash` не совпадает с `checksum` текущей модели — тот же `[BLOCKED]`
(«страница модели устарела»): страницу надо перепубликовать, иначе проверка идёт по старой модели.
