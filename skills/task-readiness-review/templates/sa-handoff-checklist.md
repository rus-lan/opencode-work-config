# Передача задачи SA → разработка (T100)

Основной процесс прод-архитектуры: `D6.2-SA. Проектирование продуктовой архитектуры`
(page_id 3905793068).

## Процесс

1. SA получает `Task`, привязанную к эпику: статус To Do, взята в спринт, оценена.
   Создавать задачу могут РО/DM/ВА/TL/SA (на основе ВА).
2. SA изучает документацию от ВА по чек-листу ревью БТ системным аналитиком
   (page_id 3943520756); вопросы уточняет у ВА и РО/DM до полной ясности; при
   нехватке артефактов БА они дорабатываются.
3. При необходимости SA консультируется с кросс-SA / системным архитектором / TL / DEV / QA
   (особенно когда возможно несколько вариантов решения).
4. SA создаёт драфт артефактов и проверяет их по чек-листу ниже.
5. SA оценивает сложность. Малые изменения без Technical Solution → шаг 15; большие
   (нужен TS) → следующие шаги. Незадокументированная логика/ручки в легаси →
   отдельные задачи на исследование и перенос.
6. SA инициирует обсуждение технической реализации с кросс-SA / SysArch / TL / QA / Dev
   (обязательно при наличии TS).
7. Ревьюеры до встречи вычитывают артефакты и оставляют комментарии.
8. SA валидирует вопросы и корректирует артефакты.
9. SA проводит встречу ревью артефактов в рамках своей Task.
10. SA корректирует артефакты после встречи.
11. SA оценивает внесённые изменения и открытые вопросы, при необходимости
    инициирует повторное ревью.
12. После финальной корректировки SA:
    1. декомпозирует задачи на разработку и заполняет их описания по шаблону ниже;
    2. в своей Task добавляет ссылки на задачи для разработки с кратким пояснением;
    3. пишет в чат команды «Ревью БА/СА», что артефакты готовы и нужен аппрув,
       со ссылкой на Task.
13. BA / SA / TL / QA вычитывают артефакты: без вопросов — «Согласовано» в
    комментариях, с вопросами — комментарии и замечания.
14. SA сам контролирует ревью: валидирует, отвечает, вносит корректировки.
15. SA проверяет критерии DoD своей Task.
16. После успешного ревью SA переводит задачу в статус DONE.

## Чек-лист задачи SA на описание требований

- [ ] Описаны PDM (опционально)
- [ ] Описаны контракты API (опционально)
- [ ] Проверен маппинг контрактов
- [ ] Добавлены ошибки методов API
- [ ] Отрисованы sequences (опционально)
- [ ] Создан драфт Technical Solution (опционально)
- [ ] Описаны доступы
- [ ] Описаны атрибуты
- [ ] Описаны фильтры
- [ ] Описан маппинг для FE

## Definition of Done задачи SA на описание требований

- [ ] Созданы и описаны все артефакты по чек-листу
- [ ] Пройдено ревью (опционально): в Task проставлен аппрув от BA и SA,
      опционально от TL и QA
- [ ] Декомпозированы и описаны задачи на разработку

## Результат и ожидания

Результат: артефакты созданы и прикреплены к Task, задачи на разработку
декомпозированы и описаны, аппрув от всех ревьюеров проставлен, Task переведена
в DONE.

Ожидания: артефакты базируются на ВА и на требованиях, согласованных с системным
архитектором; результат согласован с кросс-SA / SysArch / BA / TL / QA / Dev.

## Критерии возможности оценки артефактов разработкой

1. Понимание сценариев использования и тестирования: позитивные, негативные,
   отсутствие/невалидность входных данных.
2. Наличие дизайна по всем сценариям; используемые данные есть в контрактах.
3. При изменении схемы данных описана новая структура с пояснениями и типами.
4. Наличие связанных задач-блокеров.
5. Нет использования БЛ/ручек легаси-сервисов.
6. Нет использования БЛ/ручек без документации.
7. Учтены внешние интеграции: КК, другие сервисы, другие ИС.
8. Описана валидация.
9. Определена необходимость фича-тогла.
10. Понятна область изменений: сервис / слой / пакет.

Заголовки блоков этого файла — источник алиасов для поиска секций: правило
сравнивает заголовок без учёта регистра и `ё/е`, допускает `**Цель**`, `Цель:`,
`### Цель`. Если задан верхнеуровневый `override_template`, алиасы берутся из него
(устаревшая форма `sources.override_template` ещё принимается с `[WARN]`).

### SA-09: какие пункты обязательны

В чек-листе выше **10 пунктов**, из них **6 обязательных** и **4 опциональных** (помечены
«(опционально)»): PDM, контракты API, sequences, драфт Technical Solution. `SA-09` проверяет
именно 6 обязательных:

1. Проверен маппинг контрактов
2. Добавлены ошибки методов API
3. Описаны доступы
4. Описаны атрибуты
5. Описаны фильтры
6. Описан маппинг для FE

Отсутствие опционального пункта не даёт `FAIL` по `SA-09`; в `message` проверки
перечисляются только недостающие обязательные пункты.
