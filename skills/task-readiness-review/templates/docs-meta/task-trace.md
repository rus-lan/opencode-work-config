# Шаблон: трассировка обогащения одной задачи

Назначение шаблона: зафиксировать трассировку ОДНОЙ задачи Jira — статус,
что сделано, и обогащение doc-MR этой задачи по трём именованным точкам
(`--point code|cases|autotests`) плюс прогон на стенде. Один файл-
экземпляр на одну задачу; один активный MR документации на задачу
(`regulations/doc-as-code.md`, раздел 3.0) — задачи одного эпика
релизятся в разное время и не делят MR документации. Последовательных
публикаций одной задачи может быть несколько, каждая от свежей target;
история решения — `architecture/adr/0002-add-task-trace-document-type.md`.

Любой член команды создаёт и дополняет файл на любой стадии, вручную
или через `doc-sync update <TASK-KEY> --track pi:<EPIC-KEY>|job`;
совместимые команды — `create` и
`doc-sync enrich <TASK-KEY> --point code|cases|autotests`. Для task-trace
нужен реальный TASK-KEY; до Jira самостоятельная документация идёт в maint.
`code`/`cases`/`autotests` — рекомендуемые checkpoints по доступным фактам,
не исключительные окна записи. Пустые факты остаются N/A по таблице;
не выдумывать AC, Allure-ID, SHA или результаты прогонов.
Назначенные SA/Dev/QA отвечают за целостность и приёмку по своей области,
а не ограничивают авторство. Публикация docs допускается до выпуска service
с честным planned/draft/current в тексте; это не перевод в released.
Автор проверяет ИИ-результат; финальный MR
принимает независимый reviewer. Перед каждой записью сверить base/head;
конфликтующие параллельные правки согласует человек без silent overwrite.

Файл живёт в одном из двух мест — раскладка зависит от того, есть ли у
задачи родительский эпик:

- `pi/<EPIC-KEY>/tasks/<TASK-KEY>.md` — задача принадлежит эпику
  (`--track pi:<EPIC-KEY>`). Общее по эпику (цель, скоуп, статус) остаётся
  в `pi/<EPIC-KEY>/initiative.md` (`_meta/templates/pi-initiative.md`) —
  этот файл его не дублирует, и наоборот.
- `job/<TASK-KEY>/task.md` — задача вне эпика (`--track job`, в т.ч.
  хотфикс, инцидентная работа). Родительского `initiative.md` нет —
  секция 1 указывает `{{epic-key}} = N/A (задача вне эпика)`.

**Анти-конфликтное правило:** этот файл правит только сама задача, со
своей ветки. Файл `initiative.md` своего эпика этот файл не трогает и
наоборот — ни скиллом, ни человеком, никогда (`regulations/doc-as-code.md`,
раздел 3.4; `_meta/schema.md`, раздел 6).

## Проверенные версии и передача результатов

Для contour-2 SA готовит начальные кейсы из AC до передачи Dev, человек
принимает их как `requirements-reviewed`. Это не подтверждение реализации.
Dev обогащает те же Allure-ID; revision берётся из источника, при отсутствии
доступной revision используется hash сохранённого снимка. Изменённая версия
инвалидирует подтверждение затронутого результата. Перед Kotlin человек
отмечает `implementation-verified` для точной версии. Новые неизвестные
API/локаторы остаются draft, не угадываются. Контур 1 не создаёт новые кейсы.

Это метки evidence в существующем report.md/EXTENSIONS, не новые поля
TestOps API или enum таблицы автотестов. `sources` хранит реальные источники.
Общий final пакет включает code/unit и применимые cases/Kotlin/регресс;
раннее code review неизменённого SHA не дублируется. Deployment evidence
различает публикацию artifact, принятие chart/values diff и реальный rollout
со smoke. Новые факты поставки дополняют docs после service; ранние публикации
не запрещены. `pi/<EPIC>` группирует документы, не связывает их одним MR.

## Самопроверка (чек-лист)

- [ ] Секции идут в порядке 1–5, ничего не переставлено.
- [ ] Front-matter содержит `type: task-trace`; `id` — по правилу
      `_meta/schema.md`, раздел 3: `pi-task-<task-key в нижнем регистре>`
      для файла в `pi/<EPIC-KEY>/tasks/`, `job-<task-key в нижнем
      регистре>` для файла в `job/<TASK-KEY>/task.md`.
- [ ] `{{trace-ref}}` совпадает с реальным именем ветки doc-MR этой задачи.
- [ ] `{{epic-key}}` — либо реальный ключ эпика, либо ровно
      `N/A (задача вне эпика)`, третьего значения нет.
- [ ] `{{status}}` — ровно один токен строго из закрытого списка
      `in-progress` \| `released`, один на своей строке под заголовком
      «## 2. Статус», без обрамления и без другого текста в той же
      строке; `released` подтверждён delivery evidence и актуальными docs;
      для docs-only service = N/A с причиной, ранний draft не завершает задачу.
- [ ] Секция 4 называет точки `code`/`cases`/`autotests` — не «точка
      1/2/3» и не порядковыми номерами; прогон на стенде подписан отдельно
      как не-точка `doc-sync enrich` и относится ТОЛЬКО к прогону QA
      после мержа автотестов (`ai-autotests.md`, раздел 5, шаг 7) — не к
      самопрогону разработчика (раздел 6 там же), который в этот слот не
      пишется.
- [ ] Таблицы `cases` и `autotests` — либо реальные строки, либо ровно
      одна строка-заполнитель на таблицу (все ячейки строки — литерал
      `N/A (нет данных в источнике)`); шапка таблицы в обоих случаях не
      удаляется.
- [ ] Каждый `{{autotest-1-status}}` РЕАЛЬНОЙ строки (не строки-
      заполнителя) — значение строго из закрытого списка `generated` \|
      `green` \| `red` \| `skipped`, дословно, без обрамления backtick и
      без пояснений в той же ячейке, никогда `N/A`; `generated` держится,
      пока QA не впишет реальный результат прогона.
- [ ] Этот файл не правит `initiative.md` своего эпика и не дублирует его
      содержимое — только ссылается на общий эпик через `{{epic-key}}`.
- [ ] Постоянные факты (описание сервиса/архитектуры/бизнес-процесса) не
      продублированы в этот файл — только ссылка в секции 5, markdown-ссылкой
      (`[название раздела](путь)`) внутри `_docs`, не голым путём в backtick.
      Исключение — golden-пример в `_meta/examples/`: там цель ссылки не
      существует в реальном дереве, поэтому путь допустимо давать текстом в
      backtick с пояснением (`_meta/README.md`).
- [ ] MR кода указан обычным текстом из проверенного источника после его открытия.
      До этого стоит N/A; ранняя публикация docs допускается.

- [ ] Файл не превышает 400 строк.
- [ ] Файл лежит в `pi/<EPIC-KEY>/tasks/<TASK-KEY>.md` либо
      `job/<TASK-KEY>/task.md` и зарегистрирован в соответствующем
      `index.yaml` (`pi/index.yaml` либо `job/index.yaml`).

## Как используется скиллом

- check-id: TPL-05, refresh (5.6)
- роль в проверке: связь задачи с эпиком и уже подтверждённые факты выполнения. `TPL-05` проверяет, что задача входит в эпик, а трассировка показывает, что по задаче реально подтверждено; при перегенерации (5.6) скилл сверяет, какие разделы трассировки изменились после обновления задачи, и переносит в отчёт только подтверждённые факты. Пустая ячейка трассировки — `N/A (нет данных в источнике)`, не повод додумывать AC, Allure-ID или SHA.
