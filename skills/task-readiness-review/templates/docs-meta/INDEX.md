# Шаблоны документации сервисов и задач (`docs-meta`)

Каталог содержит отобранные нормативные шаблоны документации, на которые опирается проверка
готовности задачи: контекст задачи (5.4.1), зависимости затронутых контрактов (5.4.2) и
трассировка/перегенерация (5.6). Файлы скопированы дословно; в конце каждого добавлена секция
«Как используется скиллом» с привязкой к check-id.

## Чек-иды, на которые работают шаблоны

Идентификаторы — из действующего каталога правил (`check.py`); полный каталог с правилами и условными
severity — в `references/validation-rules.md`.

| check-id | severity | что проверяется | шаблоны |
|---|---|---|---|
| `DEP-01` | OPTIONAL (при `--with-dependencies`) | для затронутого сервиса найден раздел `service-overview` (обзор сервиса и его границы) | `service-overview.md`, `service-structure.md` (карта кода), `architecture-overview.md` (контекст ИС) |
| `DEP-02` | OPTIONAL (при `--with-dependencies`) | для затронутого контракта найдено описание логики: `logic-api`, `logic-event` или `logic-cron` | `logic-api.md`, `logic-event.md`, `logic-cron.md`, `contract-link.md` (контракт ручки) |
| `DEP-03` | OPTIONAL (при `--with-dependencies`) | для затронутого контракта найден раздел `testing-overview` (как и чем он проверяется) | `testing-overview.md` |
| `TPL-05` | REQUIRED | задача входит в эпик | `pi-initiative.md` (цель и скоуп эпика), `task-trace.md` (связь задачи с эпиком) |
| `refresh` (этап 5.6) | — (этап, не правило) | что изменилось в трассировке задачи после обновления данных | `task-trace.md` |

`DEP-01..DEP-03` выполняются только при проверке с зависимостями (`--with-dependencies`,
поле `with_dependencies` в `validation.json`); без флага они получают `status=NA` и на вердикт
не влияют.

## Отбор шаблонов

| файл | назначение | check-id | включён/исключён | почему |
|---|---|---|---|---|
| `task-trace.md` | трассировка одной задачи: связь с эпиком, статус, что сделано, AC → Allure-кейс, автотесты, прогон на стенде, затронутые постоянные разделы | `TPL-05`, `refresh` | включён | контекст задачи (5.4.1) и трассировка при перегенерации (5.6): без него не видно, что по задаче уже подтверждено, а что осталось `N/A` |
| `pi-initiative.md` | общий документ инициативы: статус, цель, скоуп, связанные постоянные разделы | `TPL-05` | включён | цель и скоуп эпика — то, с чем сверяется объём задачи; без них `TPL-05` проходит формально, а сверить объём не с чем |
| `service-overview.md` | паспорт сервиса: назначение, стек, владельцы, репозиторий, зависимости, переменные окружения | `DEP-01` | включён | ровно тот раздел, который ищет DEP-01: без паспорта неизвестны границы изменений и затронутые зависимости |
| `service-structure.md` | карта кода сервиса: дерево каталогов, точки входа, конфиги/миграции/тесты/контракты, правила структуры | `DEP-01` (карта кода) | включён | паспорт отвечает «что за сервис», карта кода — «где править»; без неё проверка видит только половину раздела |
| `architecture-overview.md` | обзор архитектуры ИС: таблица сервисов, диаграмма компонентов, внешние интеграции, потоки данных | `DEP-01` (контекст) | включён | определяет, какие сервисы затронуты, а значит для каких сервисов DEP-01 должен найти `service-overview`; расхождение с задачей — вопрос до оценки |
| `logic-api.md` | одна ручка API: метод/путь, вход, выход, ошибки, логика, побочные эффекты, контракт | `DEP-02` | включён | описание логики затронутой ручки: без него контракт не проверяем, объём правки неизвестен |
| `logic-event.md` | один топик в одном направлении: схема, условия, логика, гарантии доставки, DLQ и ретраи | `DEP-02` | включён | без схемы и гарантий нельзя оценить риск обратной совместимости события |
| `logic-cron.md` | один крон/шедулер-джоб: расписание, назначение, логика, побочные эффекты, идемпотентность, действия при сбое | `DEP-02` | включён | идемпотентность и действия при сбое определяют, безопасна ли правка джоба и насколько она объёмна |
| `contract-link.md` | заглушка на внешний контракт: система, тип, источник, дата проверки, причина, почему не скопирован | `DEP-02` (контракт) | включён | доказывает, что контракт затронутой ручки известен и сверялся, когда машиночитаемая копия невозможна |
| `testing-overview.md` | обзор автотестов ИС: репозиторий, типы тестов, запуск прогона, маршрутизация уровней, шаблоны кода | `DEP-03` | включён | без уровней и способа прогона QA оценивает вслепую, и QA-часть выходит с `confidence=low` |
| `business-overview.md` | обзор бизнес-домена ИС: назначение, пользователи и роли, ключевые процессы, глоссарий | — | исключён | не участвует ни в одной проверке: готовность задачи проверяется по полям описания и чек-листам (`TPL-*`, `SA-*`, `FT-*`), зависимости — по разделам сервиса; глоссарий и роли домена не являются разделом, наличие которого требуется для вердикта |
| `business-process.md` | один сквозной бизнес-процесс: участники, триггер, шаги, результат, сервисы, диаграмма | — | исключён | описывает процесс целиком, а не затронутый задачей контракт; ни один check-id на него не опирается — понимание процесса не проверяется формально и не влияет на вердикт |
| `adr.md` | одно архитектурное решение: статус, контекст, решение, последствия, альтернативы | — | исключён | ADR — артефакт решения (`work_kind=analysis`), а не раздел, наличие которого проверяется; отсутствие ADR-файла не делает задачу неготовой, оценка `analysis` берётся из модели |
| `runbook.md` | инцидент-сценарий: симптом, серьёзность, диагностика, решение, эскалация, пост-действия | — | исключён | в проверке готовности не участвует; единственное касание — слот `failure-runbook-link` внутри `logic-cron.md`, отдельный шаблон для этого не нужен |
| `infra-overview.md` | обзор инфраструктуры ИС: стенды, CI/CD, мониторинг и логирование, доступы | — | исключён | стенды, пайплайны и доступы не влияют на проверку контрактов и трассировку; оценка роли DEVOPS берётся из модели, а не из наличия infra-документа |
| `process-link.md` | ссылка на процессный регламент + отклонения ИС | — | исключён | нормативный документ команды, а не раздел сервиса или контракта; ни один check-id его не читает |

## Провенанс

- **Источник:** каталог `_meta` репозитория документации (подкаталог шаблонов). Перенесены 10 файлов
  из 16; версии шаблонов — по полю `template_version` в frontmatter каждого файла (1.0–3.2).
- **Дата переноса:** 2026-11-17.
- **Характер переноса:** нормативный текст скопирован дословно, включая упоминания регламентов
  (`regulations/...`), внутренние ссылки на соседние шаблоны и разделы схемы. Единственное
  добавление — секция «Как используется скиллом» в конце каждого файла. Правки в нормативный
  текст не вносились.
- **Предупреждение:** при обновлении нормативных шаблонов в репозитории документации переносить
  повторно и сверять diff. Расхождение `template_version` или `updated` в frontmatter — повод для
  повторного переноса.
- **Исключённые шаблоны не копируются.** Если в каталоге правил появится check-id, опирающийся
  на один из них, шаблон переносится заново, строка в таблице меняется на «включён», а в конец
  файла добавляется секция «Как используется скиллом».
