# Шаблон: рабочий документ инициативы

Назначение шаблона: описать то, что ОБЩЕЕ для одной инициативы
(`pi/<EPIC-KEY>/`) — цель, скоуп, статус и связь с постоянными разделами
`_docs`. Файл-экземпляр: `pi/<EPIC-KEY>/initiative.md`, один файл на одну
инициативу.

**Правится только из ветки `pi/<EPIC-KEY>/initiative`, но на любой стадии
любым членом команды — вручную или с ИИ.** Создание через `doc-sync epic
<EPIC-KEY>` — удобный checkpoint, а не исключительное право BA. BA отвечает
за цель и итог эпика; `released` требует подтверждения завершения всех задач
и независимого review SA/компетентного заместителя. Дополнять проверенные
цель, скоуп и ссылки можно между созданием и закрытием. До появления
реального EPIC-KEY самостоятельная документация ведётся в maint.
Перед правкой сверить актуальный base/head; конфликт решает человек.
Из ветки задачи этот файл не правится, единицы MR не объединяются. Один активный MR на единицу;
после мержа следующая публикация начинается от свежей target.

**Списка задач эпика в этом файле нет.** Авторитетный список — состав
каталога `tasks/` рядом с этим файлом и записи `pi/index.yaml`
(`_meta/schema.md`, раздел 10). Отдельная строка на задачу в этом файле
не заводится ни на каком этапе, ни скиллом, ни человеком — это разводит
`initiative.md` и `task-trace` на два независимых MR и убирает
merge-конфликт параллельных задач эпика на одном файле; история решения
— `architecture/adr/0002-add-task-trace-document-type.md` и
`0003-correct-task-list-and-point-naming.md`.

**Трассировка обогащения каждой отдельной задачи (AC → Allure-кейс,
автотесты, MR кода, прогон на стенде) сюда не пишется вообще.** Она живёт
в отдельном файле `pi/<EPIC-KEY>/tasks/<TASK-KEY>.md` — тип `task-trace`,
шаблон `_meta/templates/task-trace.md`, заводится командой `doc-sync
create <TASK-KEY> --track pi:<EPIC-KEY>` (любой сотрудник после получения TASK-KEY, из ветки задачи). Постоянные факты (описание
бизнес-процесса, архитектуры, сервиса, API и т.д.), которые приносит
задача, тоже не переносятся ни в этот файл, ни в `tasks/` — они пишутся в
свои постоянные разделы (`business/`, `architecture/`, `services/`,
`infra/`, `operations/`, `testing/`) тем же MR задачи.

## Таблица слотов

| Слот | Источник факта | Формат | Лимит | Если факта нет |
|---|---|---|---|---|
| `{{epic-key}}` | ключ эпика Jira: то же значение, что и имя ветки `pi/<EPIC-KEY>/initiative` репозитория `_docs` | литерал, как в источниках, регистр и разделители не менять | как в источнике | — (файл без ключа не создаётся) |
| `{{initiative-title}}` | Jira-эпик на стадии «задача на SA» | краткая формулировка сути инициативы | ≤ 80 символов | — |
| `{{status}}` | стадия жизненного цикла инициативы (`regulations/doc-as-code.md`); в `released` переводит сотрудник после подтверждения BA/владельца на последней задаче эпика, независимое ревью SA/заместителя (`regulations/doc-as-code.md`, раздел 4); подтверждённые факты можно дополнять на любой стадии | закрытый список: `in-progress` \| `released` | закрытый список | — (статус обязателен всегда) |

| `{{scope}}` | там же | 1–2 абзаца: что входит в инициативу и что явно не входит | ≤ 800 символов | `N/A (нет данных в источнике)` |
| `{{permanent-section-1}}` / `{{permanent-file-1}}` | ожидаемый охват постоянных разделов на бутстрапе (стадия «задача на SA») и итоговый список при закрытии эпика (BA) — не обновляется на каждую отдельную задачу; постоянные правки конкретной задачи ссылаются из секции 5 её файла `tasks/<TASK-KEY>.md`, не отсюда | markdown-ссылка `[название раздела](относительный путь внутри _docs)` (не за пределы `_docs` — регламенты упоминаются обычным текстом пути, не ссылкой) | 1 строка на пункт | если постоянных правок ещё не было — `N/A (нет данных в источнике)` |

## Самопроверка (чек-лист)

- [ ] Секции идут в порядке 1–3, ничего не переставлено.
- [ ] Front-matter содержит `id: pi-<epic-key в нижнем регистре>`,
      `type: pi-initiative`.
- [ ] `{{status}}` — значение строго из закрытого списка `in-progress` \| `released`.
- [ ] `{{epic-key}}` в тексте файла совпадает с именем папки `pi/<EPIC-KEY>/`, именем ветки и ключом эпика в Jira.
- [ ] В файле нет таблицы или списка задач эпика — только фиксированное примечание про `tasks/` под заголовком, слово в слово как в шаблоне.
- [ ] Секция 3 ссылается на постоянные разделы только markdown-ссылками (`[название раздела](путь)`) внутри `_docs`, не голым путём в backtick и не ссылкой на `regulations/` за пределами `_docs`. Исключение — golden-пример в `_meta/examples/`: там цель ссылки не существует в реальном дереве (пример лежит вне `pi/<EPIC-KEY>/`), поэтому путь допустимо давать текстом в backtick с пояснением (`_meta/README.md`).
- [ ] Постоянные факты (описание сервиса/архитектуры/бизнес-процесса) не продублированы в этот файл — только ссылка на файл, где они реально лежат.
- [ ] Трассировка обогащения любой задачи (Allure-кейсы, автотесты, MR кода, прогон на стенде) НЕ в этом файле ни в каком виде — только в `tasks/<TASK-KEY>.md` этой задачи.
- [ ] Правка этого файла сделана из ветки `pi/<EPIC-KEY>/initiative` и это создание или обновление фактов на любой стадии; released подтверждён владельцем эпика и независимым reviewer. Правка из ветки задачи — ошибка при любых обстоятельствах, независимо от того, кто и через какой скилл её сделал.
- [ ] Файл не превышает 400 строк.
- [ ] Файл лежит в `pi/<EPIC-KEY>/initiative.md` и зарегистрирован в `pi/index.yaml`.

## Как используется скиллом

- check-id: TPL-05
- роль в проверке: `TPL-05` требует, чтобы задача входила в эпик; цель и скоуп эпика — то, с чем сверяется объём задачи. Если эпик указан, а `initiative.md` нет или цель/скоуп не заполнены, проверка формально проходит, но сверить объём не с чем — это уходит в вариативность и снижает уверенность.
