# Эталон формата: комментарий «Результаты оценки»

Шаблон-образец, а не подставляемый файл: тело собирает
`report.render_estimate_comment(run_dir)`, а `publish.build_comment`
дописывает в первую строку маркер идемпотентности
`task-readiness-review:estimate:<TASK-KEY>` (в угловых скобках-комментариях
HTML, чтобы не рендериться в Jira).

* `ref` записи в `state.published[]`: `<TASK-KEY>#estimate`
* файл тела в каталоге прогона: `jira-estimate.md`
* пакет ручной публикации: `actions/jira-estimate.md`

Правила формата — «только полезное»:

* никаких пробелов, дампа провенанса и инструкций по перегенерации — это
  предмет комментария валидации;
* таблица ролей: `Роль | SP | Диапазон | Уверенность | Основание`, где
  «Основание» — короткая строка `бакет <role>/<issue_type>/<work_kind>, n=N,
  эталон есть|эталона нет`; для QA `source=derived` — `расчёт модели, бакет …`;
  для `source=jira` — `QA Estimation из Jira`;
* «на чём базируется» — 3–6 пунктов: бакет + base + фактор, множитель
  параметров, gap-штрафы, дополнительные ресурсы, отсутствие ролей в эталоне,
  QA расчётом модели;
* пункт «дополнительные ресурсы» печатается только когда в `estimate.json` есть
  блок `resources` (правило `RS-01`): ресурсы (`allure`, `e2e` и подобные) дают
  `+N SP` при `mode add` либо «оценку по верхней границе» при `mode upper_bound`;
* «похожие задачи» — 2–3 ближайших с SP и cosine, с явной оговоркой, что это
  ориентир (`справочно, числа не меняет` либо `диапазон расширен по <KEY>`);
* блок похожих задач не печатается, если `similar_tasks[]` пуст;
* объём — до ~25 строк.

## Оценка <TASK-KEY> — <заголовок задачи>

**Итого: <N> SP** (диапазон <A>–<B>, уверенность <high|medium|low>) · Dev: <роль> <N> SP · QA: <N> SP (<источник>) | QA: <объяснение из qa_scope>

| Роль | SP | Диапазон | Уверенность | Основание |
|---|---|---|---|---|
| <роль> | <N> | <A>–<B> | <high|medium|low> | бакет <role>/<issue_type>/<work_kind>, n=<N>, эталон есть |
| QA (расчёт модели) | <N> | <A>–<B> | <...> | расчёт модели, бакет QA/<issue_type>/<work_kind>, n=<N>, эталона нет |

### На чём базируется оценка

- бакет <role>/<issue_type>/<work_kind>: base <N>, фактор ×<F>
- множитель параметров ×<M> (weight <w>, heat <h>, connectivity <c>)
- штраф <GR-XX>: +<N> шага к оценке
- дополнительные ресурсы: <allure, e2e> → +<N> SP (mode add)
- нет данных по <BA/SA/DEVOPS/…> в эталоне — база только из спринтов
- QA посчитан моделью (QA Estimation в Jira не заполнена)

### Похожие задачи

- **<KEY>** «<заголовок>» — <N> SP (cosine <0.00>)
- справочно, числа не меняет (adjust_range выключен)

При `adjust_range: true` и расширении диапазона соседями последняя строка
блока заменяется на `диапазон расширен по <KEY>`.
