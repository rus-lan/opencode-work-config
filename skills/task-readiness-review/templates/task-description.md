# Описание задачи на разработку (T100)

Нормативный шаблон: 11 обязательных полей задачи в Jira. За наполнение отвечает
автор задачи; поля 9.1 и 9.2 — подпункты «Основного описания».

## 1. Проект

Указать проект. Для T100 — `E001 Инструменты оператора`.

## 2. Команда

Указать команду-владельца: `T100 ERM`.

## 3. Тип задачи

Один из типов Jira:

| Тип | Когда |
|---|---|
| New Feature | новая функциональность или изменение существующей |
| Task | разработка без кодинга и тестирования (например, ресерч) |
| Bug | описание бага для разработки |
| Tech debt | техдолг, рефакторинг или осознанно вынесенная из New Feature доработка |

## 4. Заголовок задачи (summary)

Формат: `[метка действия/сервиса][метка статуса] Действие Объект Частица Что Где`.

| Метка действия\сервиса | Метка действия\статуса | Действие | Объект | Частица | Что (бизнес-объект) | Где (опционально) |
|---|---|---|---|---|---|---|
| [cc app] [cc bot api] … [erm] | [research] … [blocked] | Реализовать, Проанализировать, Изменить, Исправить, Создать, Подключить, Описать | api, метод, сервис, интерфейс | для, по, … в | вопросам получения списка заказов, модального окна добавления комментария | на странице клиента, в секции заказа, на странице поиска |

Пример: `[erm][blocked] Реализовать api для получения списка заказов на странице клиента.`

## 5. Эпик

Указать эпик. Все задачи реализуются внутри эпика.

## 6. Приоритет

| Priority | SLA для багов | Причины постановки |
|---|---|---|
| Блокирующий | 1 день | блокирует флоу получения/оставления контента либо деструктивно влияет на продукт |
| Критический | 1 неделя | не блокирует целевой флоу, но критически влияет на основной путь пользователя; «as soon as possible» |
| Высокий | 1 месяц | значимо влияет на пользовательский опыт |
| Средний | 1 квартал | потенциально влияет на небольшую долю пользователей |
| Низкий | — | nice to have, выполняется в свободное от приоритетных задач время |

## 7. Роль

Указать роль: `FE`, `BE`, `QA`, `SA`, `BA`.

## 8. Связь с другими задачами (links)

Указать связи: блокеры, зависимости, дубликаты, «related to».

## 9. Основное описание задачи

Формат зависит от типа задачи.

### Формат New Feature

- **Контекст:** предыстория так, чтобы внешнему коллеге было понятно, что делаем.
- **Цель:** что хотим достичь в итоге.
- **Макет:** ссылка на Figma + ответственный дизайнер.
- **Задача:** основные пункты реализации, состояния AS IS и TO BE. Раздел — самостоятельное
  основание готовности (`SA-08`): если «что надо сделать» описано здесь, задача проверяема даже без
  отдельного раздела критериев.
- **Функциональные требования:** подробные требования, логика бэкенда (api), ссылки на техописание в Confluence.
- **Критерии приёмки:** пункты, по которым задача принимается. Раздел эквивалентен
  «Ожидаемому результату» (см. формат Bug) — терминология у команд разная, достаточно
  одного из двух. Главное: по формулировке понятно, как система должна работать в
  нормальном состоянии.

### Формат Bug

- **Проблема:** суть проблемы и влияние на продукт.
- **Окружение:** платформа, девайсы, билд и особенности.
- **Шаги воспроизведения:** конкретный набор шагов.
- **Фактический результат:** что происходит сейчас.
- **Ожидаемый результат:** как должно быть. Эквивалент «Критериев приёмки» —
  раздел засчитывается как критерии приёмки (`SA-08`), если описывает наблюдаемое
  поведение системы в нормальном состоянии.

Если какого-то поля шаблона в проекте задачи **нет** (например, «Команда», «Эпик» или «Sprint»), это не
пробел задачи: такие поля перечисляются в `fields.absent_in_project`, и соответствующие проверки
(`TPL-02/05/07/08/10/11`) отвечают `NA` — «поле отсутствует в проекте задачи, проверка не применима».

### 9.1. Внесение корректировок в задачу

1. Задача описана, но не оценена и не взята в работу → правки в основное описание.
2. Задача описана и оценена, но не взята в работу → правки в описание + вопрос
   разработчику, влияют ли правки на оценку; при влиянии и вне спринта оценка
   снимается, при влиянии и в спринте — корректируется с разработчиком и
   согласуется с Product Owner.
3. Задача в работе → правки по согласованию с разработчиком; если разработчик не
   готов делать их в текущей задаче — отдельная задача, а в Confluence правка
   вносится цветом.
4. Задача выполнена/в тестировании → правки только отдельной задачей, в Confluence
   цветом.

Версионность в Confluence: в начале страницы таблица «Версия — ссылка на задачу в
Jira — краткое описание»; по тексту пометка **Версия N** перед добавленным,
удалённым или отредактированным фрагментом.

### 9.2. Комментарии к задаче

Комментарии — для обсуждения вопросов по задаче. При адресации вопроса нужно
тегать сотрудника. Комментарии нельзя удалять и нельзя использовать вместо
описания изменений (для этого 9.1).

## 10. Поле Sprint

Указать спринт `Estimation`, если задача готова к оценке.

## 11. Поле Story Points

Значение вручную не указывается: проставляется командой на Planning Poker.

## Как используется скиллом

Проверки полноты этих полей — `check.CHECKS`:

| Поле шаблона | check-id |
|---|---|
| Проект | TPL-01 |
| Команда | TPL-02 |
| Тип задачи | TPL-03 |
| Заголовок | TPL-04 |
| Эпик | TPL-05 |
| Приоритет | TPL-06 |
| Роль | TPL-07 |
| Связь с другими задачами | TPL-08 |
| Основное описание (>= 200 символов) | TPL-09 |
| 9.1 Корректировки | TPL-09a |
| Sprint | TPL-10 |
| Story Points | TPL-11 |

Этот файл — шаблон по умолчанию для блока `template` в `validation.json`
(`name`, `version`, `sha256` считаются по нему). Если в
`task-readiness-review.yaml` задан верхнеуровневый `override_template`, вместо него
берётся пользовательский файл и его заголовки определяют секции SA-проверок.
Устаревшая форма `sources.override_template` ещё принимается, но печатает `[WARN]`.
