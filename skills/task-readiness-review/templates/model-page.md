## 1. Назначение и границы применимости

Страница объясняет, как скилл проверяет готовность задачи и как получает оценку в
Story Points: какие источники использует, по какой шкале считает, что означают вердикт,
диапазон и уверенность в отчёте.

Что страница описывает: нормативную шкалу и матрицу уровней эталона, бакеты эталона с
цитатами, статистику закрытых спринтов, калиброванную модель по бакетам, провенанс
каждого числа, правила штрафа за пробелы и параметры множителя.

Чего страница не делает: не оценивает конкретную задачу (это делает
`/task-readiness-review estimate`) и не заменяет оценку команды.

Границы: оценка строится только на данных, которые скилл реально прочитал из источников
ниже. Если источник недоступен или поле пустое, скилл сообщает пробел и снижает
уверенность, а не подставляет правдоподобное число.

Оценка считается отдельно по каждой роли, для которой есть работа; итог — сумма ролей.

### 4.2 Виды работ

Вид работ (`work_kind`) выбирает агент по смыслу и типу задачи; он определяет, из какого
бакета берётся база.

| work_kind | Как определяется | Что значит для оценки |
|---|---|---|
| `implementation` | новый функционал или доработка существующего | база — бакет реализации роли |
| `research` | исследование, spike, прототип без готового решения | база — исследовательский бакет роли |
| `bugfix` | исправление ошибки с воспроизводимым дефектом | база — бакет ошибки роли |
| `tech_debt` | технический долг без нового поведения | база — бакет tech debt роли |
| `analysis` | анализ данных и требований без кода | база — бакет анализа роли |
| `testing` | тестирование как отдельный вид работ (QA) | база — бакет тестирования роли |
| `unknown` | тип задачи не сопоставлен | база ближайшего бакета роли; уверенность не выше `medium` |

## 5. Формула: base → observed (median) → factor (clamp) → params_multiplier → expected (nearest scale) → range (p25/p75) → gap penalties (max +{{gap_penalty_max_steps}})

Цепочка расчёта одна и та же для всех ролей; меняются только бакеты.

1. **base** — значение эталона для пары «роль × вид работ». Если в эталоне роли нет, база
   берётся из статистики спринтов ({{base_fallback_source}}).
2. **observed** — медиана Story Points по бакету спринтов при `n >= {{min_sample_n}}`;
   иначе шаг пропускается.
3. **factor** — `clamp(observed / base, {{factor_clamp_min}}, {{factor_clamp_max}})`. Нет
   данных — `factor = 1.0`, `confidence = low`.
4. **params_multiplier** — `clamp(1 + Σ coef × (param − baseline), {{factor_clamp_min}},
   {{factor_clamp_max}})`, где `param` — `weight`, `heat`, `connectivity` задачи, а
   `baseline` — профиль бакета (`params_profile`) или `estimation.params.defaults`.
   Строки выборки содержат только `labels` и `issue_type`, поэтому профиль бакета обычно
   «ограниченный» (`sample_limited`) и множитель равен `1.0`; это видно в провенансе
   бакета.
5. **expected** — `nearest_scale(base × factor × params_multiplier)`: ближайшее значение
   шкалы; при равном расстоянии берётся большее.
6. **range** — `[nearest_scale(p25 × factor × params_multiplier),
   nearest_scale(p75 × factor × params_multiplier)]`, границы не выходят за шкалу.
7. **gap penalties** — `+1` шаг шкалы за каждый REQUIRED-пробел, максимум
   `+{{gap_penalty_max_steps}}` шага. Штраф расширяет верхнюю границу и `expected`;
   нижняя граница не опускается.
8. **QA** — только для типов задач из `validation.qa_required_issue_types`
   (по умолчанию Feature/Ошибка): ожидание берётся из бакета QA Estimation
   (поле Jira `jira.fields.qa_estimation`), а не из общей шкалы. У остальных
   типов QA-записи нет — проверку результата выполняет исполнитель.

Итог по задаче: `total.expected` — сумма ожидаемых значений ролей, `total.range` — сумма
нижних и сумма верхних границ.

## 7. Как валидируется задача

Проверка идёт по **содержанию** задачи (понятность, измеримость, сценарии, связи, границы,
область) и по шаблону описания как гигиене. У каждого правила есть стабильный `check-id` и
severity; полный список — в машинном зеркале правил (`{{validation_rules_path}}`).

| check-id | severity | что проверяется |
|---|---|---|
| `CL-01` | REQUIRED | суть задачи понятна (`analysis.clarity.score ≥ 0.35`) |
| `CL-02` | RECOMMENDED | сценарии описаны; для «Ошибки» — ≥ 2 шага воспроизведения |
| `CL-03` | RECOMMENDED | границы объёма понятны |
| `CL-04` | RECOMMENDED | связи и интеграции описаны |
| `CL-05` | RECOMMENDED | мало маркеров неопределённости |
| `CL-06` | OPTIONAL | область задачи определима |
| `CL-07` | OPTIONAL | описание хорошее (понятность ≥ 0.70) |
| `TPL-01`, `TPL-02`, `TPL-04`, `TPL-05`, `TPL-06`, `TPL-10` | OPTIONAL | проект, команда, заголовок, эпик, приоритет, спринт |
| `TPL-03`, `TPL-07`, `TPL-09` | RECOMMENDED | тип задачи, роль, длина основного описания (`{{min_description_chars}}` символов) |
| `TPL-08`, `TPL-09a`, `TPL-11` | RECOMMENDED | связь с другими задачами, корректировки (9.1), Story Points |
| `SA-01`, `SA-02`, `SA-05`, `SA-06` | RECOMMENDED | цель, требования БА, описание решения, задача |
| `SA-04` | RECOMMENDED (не блокирует) | контракт: есть и где описан |
| `SA-07` | RECOMMENDED | сценарии и альтернативные сценарии |
| `SA-08` | REQUIRED | есть ≥ 1 измеримый критерий приёмки |
| `SA-09` | RECOMMENDED | чек-лист SA: 6 обязательных пунктов из 10 (4 опциональных) |
| `QA-01` | RECOMMENDED (всегда `PASS`) | QA Estimation: пусто — считает модель |
| `FT-01` | RECOMMENDED | скоринг feature-toggle для нового функционала |
| `DEP-01` | OPTIONAL при проверке с зависимостями | раздел `service-overview` затронутого сервиса |
| `DEP-02` | OPTIONAL при проверке с зависимостями | описание логики контракта: `logic-api`, `logic-event` или `logic-cron` |
| `DEP-03` | OPTIONAL при проверке с зависимостями | раздел `testing-overview` для затронутого контракта |

Короткие идентификаторы — действующий каталог правил; полный каталог с условными
severity — в `references/validation-rules.md`.

Вердикт: `BLOCKED` — есть REQUIRED-пробел (`FAIL` или `UNKNOWN`; блокируют только `CL-01` и
`SA-08`); `WARN` — есть `FAIL`/`UNKNOWN` у RECOMMENDED; `OK` — иначе. `OPTIONAL` вердикт не
меняет (гигиена полей и «похвала»). `NA` ставится, когда правило неприменимо к задаче;
`UNKNOWN` — когда данных для проверки нет.

## 8. Как читать отчёт

- **Вердикт** — можно ли оценивать задачу сейчас. `BLOCKED` значит, что сначала нужно
  закрыть блокирующие пробелы; число всё равно считается, но помечается как ненадёжное.
- **Ожидаемо (sp)** — наиболее вероятное значение роли в шкале.
- **Диапазон** — нижняя и верхняя границы по статистике бакета; шире диапазон — меньше
  определённости, а не «больше работы».
- **Уверенность** — `high`: есть база эталона и выборка не меньше `{{min_sample_n}}`;
  `medium`: есть только одно из двух; `low`: нет ни того, ни другого.
- **Сценарии (min/base/max)** — `optimistic` (нижняя ветка бакета), `base` (расчётное
  значение), `pessimistic` (верхняя ветка плюс штраф за пробелы).
- **Вариативность** — список причин, по которым число может сдвинуться, с указанием
  правила и эффекта в шагах шкалы.
- **Провенанс** — у каждого числа есть источник: бакет эталона, бакет статистики или
  правило модели. Число без провенанса в отчёт не попадает.

## 9. Ограничения

- Оценка не заменяет оценку команды: она показывает, что следует из данных, и где данных
  не хватает.
- При `n < {{min_sample_n}}` бакет помечается как недостаточный, а оценка —
  `confidence=low`.
- Если эталон или спринты недоступны, скилл не считает «на глаз»: он выдаёт `BLOCKED` и
  список того, что нужно получить (`.task-readiness/DATA-REQUIREMENTS.md`).
- Модель не учитывает людей, отпуска, зависимости между задачами и внешние блокеры.
- Значения шкалы дискретны: оценка не может быть «между» двумя значениями, поэтому
  реальная неопределённость выражается диапазоном и уверенностью.
