# jira-e001-metrics-report

Генератор аналитического HTML-отчёта по метрикам PI (Initiative) и Epic проекта **E001** из Jira (project.samokat.ru) на данных **Cedrus** (Trino). Отчёт воспроизводит структуру и методологию эталона `results/jira_e001_metrics_2026Q3.html`.

## Когда использовать

- Построить отчёт по ТТМ PI / CR PI / LT Epic / CR Epic за период или квартал
- Показать списки закрытых Epic / PI, в т.ч. «одиночных» (без PRCON-связи)
- Сверить цифры с дашбордом по метрикам E001
- Разбивка метрик по кварталам / месяцам, динамика

## Параметры

| Параметр | Обязателен | По умолчанию | Пример |
|---|---|---|---|
| `START` (дата начала периода, обе границы) | да | 01.01.текущего года | `2026-01-01` |
| `END` (дата конца, НЕ включая) | да | 01.01.следующего года | `2026-08-01` |
| `OUT` (путь к выходному HTML) | нет | `results/jira/jira_e001_metrics_<YYYY>Q<NN>.html` | `results/jira/jira_e001_q3.html` |
| `FORMAT` | нет | `report` | `report` / `dashboard` |

Диапазон — полуоткрытый `[START, END)`: `resolved >= START AND resolved < END`. Кварталы вычисляются из даты `resolved`.

## Целевые метрики (план, из OKR PTL E001, H2 2026)

Источник: [Цели PTL Кармакова H2-2026](https://space.samokat.ru/pages/viewpage.action?pageId=4476576137) (Confluence ECOMCS). Цели **зависят от квартала отчёта** — для «Цели против факта» берутся целевые значения того квартала, к которому относится отчёт (по `resolved`):

| Метрика | Q3-2026 | Q4-2026 |
|---|---|---|
| ТТМ PI Single | 70 дней | 60 дней |
| CR PI | 80% | 80% |
| LT Epic | 45 дней | 45 дней |
| CR Epic | 80% | 80% |

- Для отчётов, попадающих в несколько кварталов, показывай цели по каждому кварталу отдельно.
- Для периодов **до Q3-2026** целевые значения неизвестны — запроси у пользователя или укажи в отчёте как «цель не задана».
- Полный список OKR PTL — `memory/MEMORY.md`, ссылки — `docs/common-info/product_techstream.md`.

## Источники данных (Cedrus)

Таблицы лежат в каталоге `datalake_smkt` schema `prsd_service_desk`:

- **`jira_issue_4`** — текущий снимок задач: `projectkey`, `issuetypename`, `statusname`, `resolutionname`, `resolved`, `created`, `enddate`, `baselineenddate`, `startdate`, `assigneeusername`, `summary`, `updated`, `linkedissues`.
- **`jira_issue_history_hist`** — история изменений: `issuekey`, `fieldname` (`statusName`), `oldvalue`, `newvalue`, `changetime`. Надёжный источник статусов.

> **Доступ (основной):** MCP-сервер `cedrus` (`mcp-cedrus_execute_query`). Если токен истёк, попросить пользователя обновить авторизацию.

> **Доступ (валидация):** MCP-сервер `atlassian` (`mcp-atlassian_jira_get_issue`, `mcp-atlassian_jira_search`) — живой Jira API (project.samokat.ru). Используется как **независимая проверка** статуса задач, когда снимок Cedrus вызывает сомнение. Особенно важно: если история/снимок Cedrus отстаёт (напр. задача кажется незакрытой), подтверди фактический статус через Jira API. Пример: E001-29150 в снимке Cedrus = `ready to deploy`, но живой Jira = `Done` → реально закрыт 26.06. Поиск: `issuekey = E001-XXXX`.
>
> **`resolved` из снимка `jira_issue_4` — НЕ истина по дате закрытия** (22.09.2026, полная сверка 71 закрытой задачи — 58 Epic + 13 PI — через `jira_get_issue_dates`: у всех 15 просроченных Epic `resolved` снимка ≠ live `resolution_date`, напр. E001-28950: снимок 08.27, live 07.14). Публичные даты закрытия, месячная динамика и когорты — только live Jira (`jira_get_issue_dates` → `resolution_date`, +03:00). Массовая сверка всех задач отчёта: `delegate_task` (один JSON-ряд на ключ: `created`/`resolution_date`) + прямая выборочная проверка 10–13 задач; новые закрытия после среза (live > срез) — отдельной строкой «попадут в перевыпуск».

## Методология (важно — придерживаться точно)

1. **Выборка.** Только проект `E001`, типы `Initiative` (PI) и `Epic`. Статус по снимку `statusname` (регистр: `lower()`).
2. **Закрытые = только `Done`.** PI и Epic со статусом `Cancelled` **исключаются** из всех счётчиков. Учитываются задачи со статусом `done` И попавшие в период по `resolved`.
3. **ТТМ PI Single** — закрытые `Done`-инициативы **без связки с PRCON** (в `linkedissues` нет задач проекта `PRCON`). Сумма длительностей рабочих статусов по истории в **минутах**, затем перевод в дни и **округление по итогу** (не по сегменту). Исключаются значения вне диапазона **14–365** дн (для среднего).
4. **CR PI** — доля «в срок»: `enddate <= baselineenddate + 2 дня`. Только PI с обеими датами.
5. **LT Epic** — сумма времени по истории в статусах `ba, ready for sa, sa, ready for dev, development, to test, testing`, в минутах с округлением по итогу. Исключаются значения вне **1–365** дн.
6. **CR Epic** — как CR PI, для Epic.
7. **Расхождения с дашбордом**: снимок `jira_issue_4` может отставать от истории (`statusname` = `ready to deploy`, но история = `done`). Если история показывает `done`, а снимок не `done` — задача реально закрыта и должна войти (напр. E001-29150: `ready to deploy → done` 26.06). Всегда сверяй статус по истории `jira_issue_history_hist` (последняя **непустая** запись `statusname`).
8. **Прогнозные ТТМ PI / LT Epic** (для незакрытых задач) — метод **«календарный калиброванный»**:
   - Выборка: только E001, типы Initiative/Epic, статус не `done` и не `cancelled`, **`enddate IS NOT NULL` И `startdate IS NOT NULL`** (задачи в работе). Backlog/незапущенные (startdate=NULL) **исключаются** — время ожидания не входит в ТТМ/LT, прогноз по ним завышается.
   - Плановые календарные дни: `cal_days = date_diff('day', startdate, enddate)`. При отсутствии `startdate` запасной вариант НЕ применять (не считать от `created`) — задача просто исключается как незапущенная.
   - Коэффициент калибровки: `K = медиана(фактический рабочий ТТМ/LT ÷ календарные дни)` по **закрытым** E001-задачам (факт из истории, календарь = `startdate→enddate`). Регистрируется раз в период. Репорные значения (снимок): `K_PI = 0.31`, `K_Epic = 0.58`.
   - **Прогноз = `cal_days × K`**, округление к целым дням.
   - Агрегация: медиана и среднее по задачам; плюс таблица по конкретным задачам (прогноз, календарные дни, статус, исполнитель).
   - Ограничение: у многих задач `enddate` = веха конца квартала (2026-09-30 / 2026-12-31), а не реальный дедлайн — это завышает среднее (малосодержательно). В прогноз обязательно исключать задачи, «закрытые по истории» (напр. E001-29150), даже если снимок ещё не `done`.
   - Последние расчётные значения (снимок 07.08.2026): PI n=14, медиана 17.7, среднее 29.3; Epic n=22, медиана 44.1, среднее 69.3.

## Рабочий процесс

### 1. Определи параметры
Спроси (или выведи из контекста) `START` и `END`. Если не указаны — по умолчанию текущий год. Определи формат: если пользователь просил «dashboard», «панель», «дашборд» — ставь `FORMAT=dashboard`; иначе — `report`.

### 2. Выполни SQL-запросы
SQL лежит в `references/queries.md` — параметризуй их переменными `{START}` / `{END}` (полуоткрытый диапазон по `resolved`). Нужные запросы:

- `epic_done_by_month` — закрытые Done Epic по месяцам (TLT/CR)
- `epic_june_detail` (или обобщённый `epic_detail`) — детализация Epic за период
- `epic_reconcile_history` — сверка статуса снимка vs последней непустой записи истории (поиск «закрыт по истории, но не в снимке»)
- `pi_done_by_quarter` — Done PI по кварталам (CR)
- `pi_ttm_quarter` — ТТМ PI Single по кварталам
- `pi_single_prcon` — список одиночных (без PRCON) PI
- `priod_totals` — итоговые агрегаты
- (опционально, прогноз) `forecast_calibration`, `forecast_aggregates`, `forecast_list` — калибровка K, медиана/среднее прогнозных ТТМ/LT, список задач в работе (см. queries.md §8)

Выполняй каждый через `mcp-cedrus_execute_query`. Не выдумывай цифры — всегда из запроса.

**Валидация через mcp-atlassian** (когда это важно): для проверки статуса подозрительных задач (расхождение снимок/история или счётчик не бьётся с живым дашбордом) используй `mcp-atlassian_jira_get_issue` — он даёт фактический текущий статус/резолюцию из живого Jira. Это особенно ценно для задач, где снимок Cedrus отстаёт.

### 3. Собери HTML-отчёт
Два формата вывода — выбирай по `FORMAT` (или контексту запроса):

**A. `report` (полный отчёт).** Шаблон — `references/template.html`. Это рабочий эталон за Q1–Q3 2026: сохраняй его стили/разметку/разделы, но **заменяй** контент (заголовки периода, цифры, списки, графики) данными за выбранный `{START}`–`{END}`. Если детализация по месяцам большая — вынеси в `<details>` блоки (как «Июнь 2026 — детализация»). Числа всегда из SQL-запросов, не из шаблона. Обязательные разделы: методика, сводка «Цели против факта», разбивка tech/product, списки закрытых Epic и PI (+ одиночные без PRCON), метрики по кварталам, динамика по месяцам, рекомендации, ключевые выводы.

**B. `dashboard` (компактная панель).** Шаблон — `references/dashboard-template.html`. Одностраничная панель для быстрой оценки: KPI-карточки против целей с прогресс-барами и статусом ✓/✗, 4 графика трендов по месяцам (Chart.js), квартальная разбивка, tech vs product, топ-просроченные PI, топ-долгие Epic, ключевые выводы, баннер методологии. Сохраняй структуру/стили/CSS шаблона, заменяй данные за период. Сводные цифры (ТТМ/CR/LT) должны согласовываться с полным отчётом.

**Обязательные разделы отчёта:**
- Методика расчёта (таблица с ТТМ/CR/LT, способ, исключения, итоги)
- Сводка «Цели против факта» (карточки): ТТМ PI, CR PI, LT Epic, CR Epic — цели по кварталу отчёта (Q3-2026: 70/80/45/80; Q4-2026: 60/80/45/80, см. раздел «Целевые метрики»)
- Разбивка tech (ekarmakov) / product
- Список закрытых Epic (детализация по месяцам, если применимо)
- Список закрытых PI по кварталам + список одиночных (Single, без PRCON)
- Метрики в разрезе кварталов (Q1/Q2/Q3)
- Динамика по месяцам (графики Chart.js)
- Рекомендации + ключевые выводы

**Опционально — прогнозные метрики** (если нужен forward-looking взгляд на не закрытые задачи):
- 2 KPI-карточки «Прогнозный ТТМ PI» и «Прогнозный LT Epic» (задачи в работе с enddate+startdate) с медианой/средним/`n`, прогресс-баром и статусом против целей квартала (Q3-2026: ТТМ 70 / LT 45; Q4-2026: ТТМ 60 / LT 45).
- Две таблицы по конкретным задачам (PI и Epic): прогноз, календарные дни, статус, исполнитель — желательно в `<details>`. Пишутся только по запущенным (startdate не NULL); backlog исключается.
- Баннер методологии с формулой `прогноз = (enddate − startdate) × K` и значениями K.

> **Проверка консистентности.** Сводные цифры (Итого Done, LT, CR) должны согласовываться по всему отчёту: таблица «по месяцам» = сумма месяцев = Итого = сводные карточки. Если в одном месте цифра меняется (напр. добавлен эпик по истории) — обнови везде и пометь причины в заметке.

### 4. Валидируй и сохрани
- Выведи файл в `OUT` (по умолчанию `results/jira/`).
- Проверь баланс HTML-тегов (парсером): `div, table, tr, td, th, details, summary, span`.
- Отчёт пользователю: краткое резюме + путь к файлу.

## Триггеры «огибких» запросов
Пользователь может просить «покажи закрытые эпики за июнь», «почему июнь = 18 а не 17», «разбей ПИ по кварталам», «сделай dashboard/дашборд/панель по E001», «добавь прогнозный ТТМ/прогнозный LT» (forward-looking по незакрытым задачам с enddate). Это тоже запуск skill'а — просто выбираешь нужный фрагмент отчёта/запроса или формат (dashboard), но всегда по той же методологии и тем же таблицам.

## Публикация в Confluence (ECOMCS/Reports)
Подстраница под «Reports» (id 4533061339, space ECOMCS), MCP `atlassian` (mcp-atlassian, Docker-контейнер `mcp-atlassian-1-mcp-atlassian-1`, корень `/app`).
- **Стилизация работает:** инлайн-стили в storage-формате сохраняются полностью (цвета, border-radius, pill, banner, таблицы). Конвертация из HTML-отчёта: классы → инлайн-стили (токены из `:root` в HTML-отчёте), гриды KPI → таблицы с `border-spacing:14px`, `details` → макро `expand`.
- **Ловушка 1 — голый `<br>` ломает `update_page`** (ошибка «No space or no content type...»). Любой валидный storage без `<br>` проходит (проверено 84 КБ). Замените `<br>` на два отдельных `<div>`/`<p>`.
- **Ловушка 2 — Confluence санитайзер вырезает `<div>` внутри `<td>`** (полоски-бары теряют fill). Бары делайте вложенными `<table>`: внешняя 3 ячейки (lbl 150px / track / value 120px, `font-weight:600`), track = вложенная таблица 2 ячейки (fill `width:N%` + spacer `width:100−N%`, `table-layout:fixed`, `height:20px`), на внутренней таблице — `border-radius:6px;overflow:hidden` для скруглённых концов, как в исходнике.
- **Ловушка 3 — без `table-layout:fixed` на внешней таблице** ячейка track схлопывается под содержимое и секция выглядит «как 3 отдельных колонки» (в HTML там `flex:1`). Внешней bar-таблице обязателен `table-layout:fixed`; у track-ячейки НЕ задавать `width` (она возьмёт остаток).
- **Ловушка 4 — тема Confluence накладывает бордеры на ВСЕ `td`** (локальные HTML-предпросмотры этого не показывают!). У «декоративных» таблиц (bar-ряды, KPI-карточки-таблицы) явно указывать `border:none` на каждой ячейке, иначе видны серые линии, разрезающие бары на «3 колонки».
- **Ссылки на Jira-задачи переживают санитайзер** (и в `<p>`, и внутри `<td>`): оборачивать ключи в исходном HTML `<a href="https://project.samokat.ru/browse/KEY" target="_blank">KEY</a>` (regex `(?<![A-Za-z0-9/_-])(E001-\d+|PRCON-\d+)(?![A-Za-z0-9-])`; «H2-2026» — не задача, не связывать). Confluence сам добавит `rel="noopener noreferrer"`. Контент, вставляемый ПОСЛЕ конвертера (макро-панели секций 8/9), оборачивать отдельным проходом в их генераторе — иначе двойное/пропущенное.
- **Команда эпика — по полю Jira «Команды» (`customfield_17207`, multiselect), НЕ по ключевым словам в названии** (22.09.2026: атрибуция по summary дала фиктивную строку «Без тега» 13/58; по полю заполнено у всех 58, T083=16 вместо 10). JQL: `jira_search` c `fields=customfield_17207`; 2 эпика могут стоять в двух командах (учитывать в первой). По-эпиковая выгрузка: `results/jira/q3_epic_team_field.json`.
- **`<ul>` внутри `<td>` и inline-`margin-bottom` на `<li>` сохраняются** (в отличие от `<div>` в `<td>` и голых `<br>`) — так делают построчные разбивки в ячейках «Комментарий» (по команде T100/T006/T102/T083/без тега) и «воздух» между пунктами в панелях (margin 14px).
- **`baselineenddate` в Jira — неизменяемое поле** (первоначальное обязательство; 22.09.2026, подтверждено пользователем повторно). В отчёте НЕ давать «актуализировать baseline» / «per-quarter baseline» как рекомендацию. Второй показатель CR PI (без дрейфа): CR по PI с baselineenddate в отчётном квартале (E001 Q3: 6/8 = 75% vs общий 46.2%).
- **CR PI всегда разбивать на три**: общий (все PI) / single (без PRCON-связи) / в PRCON (1+ связей) — отдельные KPI-карточки + разбивка в секции PI (22.09.2026: общий 46.2% (6/13) скрывал, что single 28.6% (2/7) и в PRCON 66.7% (4/6)). Проверять: single + в PRCON = общий.
- **Баг Jira по `baselineenddate` (старт = день baseline, системный)**: переход **Backlog→Implementing** на форме предзаполняет одним значением «сегодня» пучок дат — `Start date`, `End date`, `Baseline start date`, `Baseline end date`, `Concept Design *`, `Acceptance *` (в changelog это ОДНА запись, `from=None`, и для `End date` даже ПЕРЕЗАПИСЫВАЕТ ранее установленный дедлайн). После перехода менеджер почти всегда вручную возвращает `End date` на реальный дедлайн (через ~40 сек отдельной записью), но `Baseline end date`/`Baseline start date` остаются на дне старта → baseline-интервал схлопывается в 0 дней. Классификация: `baseline start == baseline end == first_work == день перехода в Implementing`, при `End date` позже. Известные случаи: E001-29986 (Q3, 08-12: End был 09-30 переписан на 08-12 затем возвращён), E001-30704 (Q4, 09-22). Q4 tech-инициативы в Backlog (E001-30702/30703/30632/30650/30651) получат тот же баг при взятии в работу. В отчёте такие PI исключать из знаменателя CR (для baseline-в-квартале и с учётом бага) и фиксировать baseline на `End date`. В отчёте (v30) показывать ДОПОЛНИТЕЛЬНЫЙ столбец «CR с учётом бага» с исключением таких PI из знаменателя (E001 Q3: общий 46.2%→60.0% (6/10), single 28.6%→40.0% (2/5), в PRCON 66.7%→80.0% (4/5), baseline-в-кварале 75%→85.7% (6/7)); базовая метрика против неизменяемого baseline — без изменений.
- **Популяция Epic в отчёте — только измеряемые** (LT в окне 1–365 дн); неизмеряемые (LT=0: контейнеры, миграции, доки, подготовительные) исключаются из ВСЕХ секций (KPI, динамика, команды, списки) и явно перечисляются с пояснением в одном месте (сношка) (22.09.2026: 50 измеряемых из 58 Done; CR Epic на этой базе 36/50=72.0%, а не 43/58=74.1%).
- Файл для `content_file` должен лежать **в контейнере**: `docker cp file.html mcp-atlassian-1-mcp-atlassian-1:/app/` (корень macOS для контейнера недоступен; `/app` внутри контейнера только на чтение из-за ownership uid 501 — новые файлы писать `docker cp`, удалять не удаётся, но и не нужно).
- Вложение исходного HTML: `confluence_upload_attachment` с **`content_id`** (НЕ `page_id`) и `file_path=/app/<имя_файла>` (после `docker cp`). Имя вложения = basename пути: если docker cp под другим именем — создаётся дубль-вложение (удалить `confluence_delete_attachment(attachment_id)`), поэтому копировать прямо под целевым именем.
- `confluence_update_page` требует **`title`** (текущий заголовок взять из metadata `confluence_get_page`) + `content_file` + `content_format="storage"`. После публикации — `confluence_get_page` с `convert_to_markdown=false` и JSON-парсингом spillover-файла: `inner = json.loads(outer['result'])`, контент в `inner['metadata']['content']['value']` (в `inner['content']` — null). Confluence нормализует числа в стилях (`12px` → `12.0px`) — string-чеки margin делать по нормализованному виду.
- Проверка после публикации: `confluence_get_page` → spillover, string-чеки по ключевым элементам (KPI-значения, цвета pill/banner, бары, секции).
- **Apple python3 3.9 (macOS `/usr/bin/python3`) иногда падает `SyntaxError: Non-UTF-8 code` на ВЕРНОМ UTF-8-файле с кириллицей** (22.09.2026, `gen_panels2.py`): файл декодируется и `py_compile` проходит, но прямой запуск падает. Фикс — `# -*- coding: utf-8 -*-` первой строкой или `python3 -X utf8`.
